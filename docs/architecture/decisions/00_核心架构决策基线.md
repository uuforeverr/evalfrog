# Workflow Platform 核心架构决策基线

> 状态：Accepted Baseline
>
> 日期：2026-08-06
>
> 范围：核心闭环、领域术语、身份体系、定义生命周期、运行状态模型及职责边界

## 1. 文档目的

本次重构的目标不是第一阶段建设一个功能全面的 Workflow Platform，而是建立一个：

- 核心闭环最小；
- 领域术语稳定；
- 身份与生命周期明确；
- Definition、Runtime、Scheduling、Execution 边界清晰；
- 可以长期演进但不过度设计的平台内核。

本文只记录已经确认的架构决策。尚未冻结的纯实现细节进入实施计划和对应里程碑评审，不得被误写成当前领域约束。

记录纪律：每组讨论经确认冻结后，必须先更新对应的既有模块文档并完成冲突扫描，再进入下一组讨论；同一模块优先增量更新现有文档，不为每轮讨论重复新建文件。

## 2. 第一阶段核心闭环

```text
Human Web / Agent CLI 创建或修改 IR
→ 保存 Workflow Draft
→ 校验 IR
→ Draft Test
→ 发布不可变 Published Version
→ 正式创建 Workflow Run
→ Engine 推进 Node Run
→ Scheduler 创建并派发 Node Attempt
→ Worker 执行 Attempt
→ Engine 根据 Attempt Result 继续推进
→ Workflow Run 进入终态
→ Runtime Error 通过 Source Map 定位回 IR
```

第一阶段优先保证该闭环正确、可恢复、可追踪，不以节点类型数量和外围功能数量作为完成标准。

## 3. 核心领域术语

### 3.1 Workflow

`Workflow` 是长期稳定的业务身份和定义容器，不直接代表某份可执行内容。

它可以同时拥有：

- 一个可变 Draft；
- 多个不可变 Published Version；
- 一个当前 Active Version；
- 多个基于不同版本创建的 Workflow Run。

“已发布”描述的是 Published Version，不是 Workflow 本体的状态。

### 3.2 Draft

`Draft` 是 Workflow 当前可变的逻辑编辑头，权威内容为 IR；已经保存成功的 Draft Revision 本身不可变。

Draft：

- `workflow_drafts` 保存当前 Revision Pointer，并使用 `draft_revision` 做乐观并发控制；
- 每次服务端接受保存都创建新的不可变 `workflow_draft_revisions` 记录，再原子更新 Current Draft Pointer；
- 允许暂时不完整或无法通过编译；
- 可以由 Human Web 或 Agent CLI 修改；
- 只能用于测试，不能用于正式运行。

第一阶段每个 Workflow 只维护一个 Draft，不支持多 Draft 分支和实时协同编辑。

### 3.3 Published Version

`Published Version` 是一次不可变发布产生的生命周期身份，并以一对一关系引用不可变 Execution Snapshot。IR、DSL、Source Map 和 Compiler Manifest 在领域上仍属于该 Published Version 的发布产物包，物理上统一保存在其 Execution Snapshot 中。

它至少包含：

```text
version_id
workflow_id
version_number
source_draft_revision
execution_snapshot_id
change_log
created_by
created_at
```

Published Version 创建后，其 `execution_snapshot_id` 和对应 Snapshot 的 IR、DSL、Source Map、Compiler Manifest 与 Definition Hash 均不得修改。

### 3.4 Execution Snapshot

`Execution Snapshot` 是 Runtime 唯一可以执行的不可变定义身份。它不是新的业务版本或发布状态，而是 Test Run 与 Production Run 共同使用的执行内容包：

```text
snapshot_id
project_id
workflow_id
origin_kind
origin_id
ir_snapshot
dsl_snapshot
source_map
compiler_manifest
ir_hash
dsl_hash
source_map_hash
definition_hash
created_at
```

`origin_kind/origin_id` 记录 Snapshot 来自确定 Draft Revision 的测试编译，或来自确定 Published Version。相同 `draft_revision + compiler_manifest` 产生完全相同内容时可以复用 Snapshot；复用必须以全部内容 Hash 和编译身份一致为前提。

每个 Workflow Run 只以 `snapshot_id` 绑定执行定义。`purpose=test/production` 影响入口权限和来源校验，不改变 Runtime 的读取和执行方式。

### 3.5 IR

IR 是 Human 和 Agent 共用的编辑态权威来源：

- 可读、可增量修改；
- 使用稳定逻辑 ID；
- 允许半成品；
- 保存用户和 Agent 的编辑语义；
- 不包含队列、Worker、Lease 等运行基础设施信息。

节点坐标等共享画布布局属于 IR 的 `layout`，其变化会形成新的 Draft Revision；Compiler 不读取 Layout，因此布局变化可以不改变 DSL。缩放、当前选择和滚动位置等个人会话状态不进入 IR。

### 3.6 DSL

DSL 是 Compiler 根据确定 IR 生成的强约束执行定义：

- 结构完整；
- 引用和必填配置已经解析；
- 只供 Runtime 使用；
- 不作为 Human 或 Agent 的长期编辑对象；
- 只能由服务端 Compiler 生成并写入 Execution Snapshot；
- 自包含执行语义，Runtime 不再读取 IR 或 Node Description；
- 固化内部 Operation Version、受管资源解析结果和 Retry/Timeout 等执行策略；
- 不包含 Layout、Title、Kafka Topic、Worker 地址或其他编辑态与基础设施信息。

### 3.7 Source Map

`Source Map` 是编译产物的一等组成部分，负责将 Runtime 位置映射回 IR：

```text
Execution Node / Edge / Field
→ IR Node / Edge / Relative Field
→ Web 画布位置或 Agent 修改目标
```

Source Map 第一阶段必须覆盖：

- Execution Node 到 IR Node；
- Execution Edge 到 IR Control Edge；
- DSL 输入、输出或配置字段到 IR Relative Field；
- 数据引用错误到具体 Node Input Field。

### 3.8 Workflow Run

`Workflow Run` 表示对一个确定不可变执行定义的一次运行。

所有 Run 创建后都必须固定绑定一个 `snapshot_id`。Production Run 的 Snapshot 必须由 Published Version 引用；Test Run 的 Snapshot 必须由指定 Draft Revision 编译产生。

Run 不能在执行过程中跟随 Draft 或 Active Version 变化。

### 3.9 Node Run

`Node Run` 表示一个 Execution Node 在一次 Workflow Run 中的逻辑执行。

一个 Node Run 可以包含多个 Node Attempt，但最终只有一个逻辑结果。

### 3.10 Node Attempt

`Node Attempt` 表示 Scheduler 派发并由 Worker 实际执行的一次物理尝试。

重试、重新投递、Worker 崩溃和 Lease 失效都会形成明确的 Attempt 历史，不能覆盖旧 Attempt。

## 4. 身份体系

| 身份 | 稳定范围 | 用途 |
|---|---|---|
| `workflow_id` | Workflow 全生命周期 | Workflow 业务身份 |
| `draft_revision_id` | 单个不可变 Draft Revision | 全局不可变机器身份 |
| `draft_revision` / `revision_number` | 单个 Workflow Draft 内 | 乐观并发控制与人类可读修订序号 |
| `version_id` | 单个 Published Version | 全局不可变机器身份 |
| `version_number` | 单个 Workflow 内 | Human、Web、CLI 使用的单调递增版本号 |
| `snapshot_id` | 单个不可变执行内容包 | Runtime 唯一执行定义身份 |
| `definition_hash` | 单个定义产物 | 内容完整性与执行定义一致性校验 |
| IR `node.id`（领域中称 `logical_node_id`） | Workflow 定义内，跨版本尽量稳定 | 编辑、Diff、Copy、错误定位 |
| IR `edge.id`（领域中称 `logical_edge_id`） | Workflow 定义内，跨版本尽量稳定 | 控制边编辑、Diff、错误定位 |
| `execution_node_id` | 单个执行产物内 | DSL 与 Runtime 执行身份 |
| `execution_edge_id` | 单个执行产物内 | DSL 依赖边身份 |
| `run_id` | 单次运行 | Workflow Run 身份 |
| `node_run_id` | 单次节点逻辑运行 | Node Run 身份 |
| `attempt_id` | 单次物理执行 | Node Attempt 身份 |

### 4.1 Logical ID 不变量

修改以下内容不能改变 IR `node.id`：

- 节点标题；
- 节点参数；
- 画布坐标；
- 节点数组顺序；
- 重新发布。

控制边必须具有稳定 `logical_edge_id`，不能只依赖数组下标定位。

每个 Node 的同名 Input 最多存在一项，因此第一阶段通过以下稳定路径定位数据引用，不引入独立 Binding ID：

```text
/nodes/{node_id}/inputs/{input_name}
```

### 4.2 Logical ID 与 Execution ID

概念上必须区分 Logical ID 和 Execution ID。

第一阶段保持一个 IR Node 编译为一个 Execution Node，但二者必须使用不同命名空间和不同 ID。Execution ID 由 Compiler 离线、确定性生成；未来一个复合 IR Node 展开为多个 Execution Node 时，通过 Source Map 保存一对多来源关系，无需改变 IR 身份体系。

### 4.3 数据库机器 ID 与 Project 隔离

以下平台机器身份统一使用应用侧生成的 UUIDv7，并以 PostgreSQL `uuid` 存储：

```text
workflow_id
draft_revision_id
version_id
snapshot_id
run_id
node_run_id
attempt_id
event_id
```

IR Node/Edge 的 Logical ID 不适用该规则，仍由 Web 或 Agent 按 IR 约定离线生成。UUIDv7 不依赖中心数据库序列，支持多 Control Plane 实例与未来分库，同时相较完全随机 UUID 更有利于 B-Tree 持续写入。

`draft_revision/version_number/attempt_seq/retry_count/recovery_count/state_version` 使用各自作用域内的单调整数，不使用平台全局业务序列。

所有 Definition 与 Runtime 主表必须包含 `project_id NOT NULL`。即使机器 ID 已全局唯一，租户关系仍使用 `project_id + entity_id` 复合唯一约束和复合外键校验，Repository 与 API 的标准读取也必须携带 `project_id`；普通租户数据访问不得仅凭实体 ID 绕过 Project 边界。

## 5. 定义生命周期

### 5.1 Draft 保存

```text
读取 Draft revision N
→ Human 或 Agent 修改 IR
→ 使用 expected_revision=N 保存
→ 成功生成 revision N+1
```

如果当前 Revision 已变化，保存必须返回 Revision Conflict，不允许静默覆盖。

### 5.2 Draft Test

Draft Test 的语义是：

```text
选择确定 draft_revision
→ 读取该 Revision 的 IR 与内部 catalog_revision
→ 校验和编译
→ 创建或复用不可变 Execution Snapshot（origin=draft_test）
→ 创建 purpose=test 的 Workflow Run
```

测试开始后，即使 Draft 被继续编辑，本次测试仍执行原 Revision 对应的快照。

### 5.3 Publish

`publish` 永远自动激活新版本，但 Published Version 与 Active Version 在数据模型上保持独立概念。

发布流程：

```text
检查 expected_draft_revision
→ 校验 IR
→ 使用该 Draft 绑定的 Catalog Revision 编译 DSL 与 Source Map
→ 对 IR、DSL、Source Map 执行 Canonicalize 并计算各自 Hash
→ 使用三个内容 Hash 与 Compiler Manifest 计算 definition_hash
→ 在数据库事务中分配 version_number
→ 创建不可变 Execution Snapshot（origin=published）
→ 创建引用该 Snapshot 的不可变 Published Version
→ 更新 workflow.active_version_id
→ 写入 Publish Audit Record
```

发布必须支持 Idempotency Key。相同发布请求重试时必须返回第一次创建的 Version，不能重复递增版本号。

### 5.4 Latest Version 与 Active Version

- Latest Version：最后创建的 Published Version；
- Active Version：正式调用未指定版本时解析到的默认版本。

第一阶段发布会自动令新版本成为 Active Version，但二者仍保留独立身份与字段。

### 5.5 正式运行

正式运行只能使用 Published Version。

```text
调用 workflow_id
→ 解析 active_version_id
→ Active Version 不存在：返回 WORKFLOW_NOT_PUBLISHED
→ 创建 Run
→ Run 固定保存 Active Version 对应的 snapshot_id
```

Run 创建后不受后续 Publish、Activate 或 Rollback 影响。

平台内部或有权限的 API 可以显式运行历史 Published Version；普通入口默认使用 Active Version。

### 5.6 Rollback

Rollback 只修改 `workflow.active_version_id` 指向某个历史 Published Version：

- 不修改历史 Version 内容；
- 不删除新 Version；
- 不重新编号；
- 不影响已经创建的 Run。

### 5.7 Copy Workflow

Copy 必须指定确定的来源 Published Version：

```text
source_workflow_id + source_version_number
→ 解析 source_version_id
→ 读取 source_version.execution_snapshot.ir_snapshot
→ 创建新的 workflow_id
→ 创建 Draft revision 1
→ 保存 cloned_from_version_id
```

Copy 后的新 Workflow：

- 没有 Published Version；
- `active_version_id` 为空；
- 必须重新测试和发布后才能正式运行；
- 不复制 Run、Node Run、Attempt 和发布版本号历史。

Copy 直接复制 IR Snapshot，不通过 DSL 反编译。

### 5.8 发布产物完整性 Hash

```text
ir_hash         = Hash(Canonical Full IR，包含 Layout)
dsl_hash        = Hash(Canonical DSL)
source_map_hash = Hash(Canonical Source Map)
definition_hash = Hash(ir_hash + dsl_hash + source_map_hash + compiler_manifest)
```

`compiler_manifest` 至少包含 `compiler_version`、`catalog_revision` 和 `policy_revision`。创建时间、创建人等非确定性字段不参与 Hash。只修改 Layout 时，`ir_hash` 和 `definition_hash` 改变，`dsl_hash` 与 `source_map_hash` 保持不变。

### 5.9 Definition 与 Runtime 持久化边界

第一阶段关系模型按生命周期拆分，不使用一张通用状态表混装定义与运行数据：

```text
Definition
├─ workflows
├─ workflow_drafts
├─ workflow_draft_revisions
├─ workflow_versions
└─ workflow_execution_snapshots

Runtime
├─ workflow_runs
├─ node_runs
├─ node_attempts
├─ node_output_values
├─ outbox_events
└─ inbox_events
```

`workflow_runs` 只引用 `snapshot_id` 作为执行定义外键；Runtime 不使用 `version_id` 或 `draft_revision` 分支选择定义内容。Published Version 与 Draft Revision 只作为 Snapshot 的来源和审计信息。

`node_output_values` 与高频更新的 `node_runs` 分表。Output 行记录 `node_run_id`、产生它的 `attempt_id` 和受大小限制的 Inline JSON；`node_runs.effective_attempt_id` 指向唯一被 Engine 接受的 Attempt。只有 Output 的 `attempt_id` 与 `effective_attempt_id` 匹配时，该 Output 才能被下游读取，失效或迟到 Attempt 不得覆盖最终有效值。

Definition 与 Runtime 主表均携带 `project_id`。未来水平分片的稳定路由维度为：

```text
Definition: project_id + workflow_id
Runtime:    project_id + run_id
```

需要与业务写入原子提交的 Outbox 必须和对应 Definition 或 Runtime 数据位于同一数据库分片和事务中；不能先写中心 Outbox 再跨分片提交业务状态。Redis 与 Kafka 不创建新的权威定义或运行事实。

### 5.10 核心写入事务与 Outbox/Inbox

Draft 保存事务：

```text
检查 expected_revision
→ 插入 immutable Draft Revision N+1
→ CAS 更新 workflow_drafts.current_revision
```

Revision 冲突直接失败，不自动合并，也不原地覆盖历史 Revision。

Publish 的校验与编译可以在数据库事务外基于不可变 Draft Revision 完成；最终提交必须在单一事务中：

```text
检查 Publish Idempotency Key
→ 再次确认目标 Draft Revision
→ 插入或复用内容与编译身份完全一致的 Execution Snapshot
→ 分配 version_number
→ 插入 Published Version
→ 更新 workflow.active_version_id
→ 写 Publish Audit Record
```

Snapshot 被复用时不修改其 `origin_kind/origin_id`；Published Version 到 Snapshot 的关系提供新的发布使用来源。Snapshot ID 与 Version ID 均可预先生成。相同 Publish 请求重试必须返回第一次创建的 Version，不能重复递增版本号。

第一阶段没有 Definition Event Topic，也不为 Draft Save/Publish 写入没有消费者的 Definition Outbox。Execution Snapshot 按 `snapshot_id` 不可变缓存，不需要失效事件；Production CreateRun 从 PostgreSQL 解析 Active Version。未来只有出现明确的外部发布订阅、异步搜索索引等消费者时，才重新引入 Definition Event 与对应 Outbox。

CreateRun 只建立运行身份，不在 API 事务内初始化整张执行图：

```text
校验启动权限并解析 snapshot_id
→ 检查 CreateRun Idempotency Key
→ 插入 workflow_run(state=pending)
→ 保存 input_json、purpose、deadline_at
→ 写 RunCreated Outbox
```

Engine 消费 RunCreated 后，通过 Inbox 去重并锁定/CAS Pending Run，在第一阶段使用一个数据库事务完成运行前兼容性检查、批量初始化全部 Node Run、推进 Start、将 Run 置为 `running` 并写入后续 Outbox。`UNIQUE(run_id, execution_node_id)` 保证崩溃重试不会重复初始化；不得暴露只初始化半张图的 Running Run。

M5 实现补充：TestDraft 编译在 `workflow_draft_test_snapshots` 保存不可变 `draft_revision_id ↔ snapshot_id` 关系，创建 Run 时同时携带确定的 `draft_revision_number + snapshot_id` 并精确验证该关系。由于 Execution Snapshot 可按 Definition Hash 被 Test 与 Publish 复用，来源校验不能只判断 Snapshot 的 `origin_kind`，也不能通过 IR/Catalog 内容近似反推关系。Production CreateRun 仍在事务中从 `workflow.active_version_id` 解析 Published Version 与 Snapshot。Run 最终只保存统一 Snapshot Binding，Runtime 推进不再读取 Draft/Version。

Attempt 完成分为两个权威事务：

```text
Attempt Coordinator:
校验 attempt_id + attempt_seq + fencing_token
→ Attempt 进入终态
→ 写 node_output_values Output Candidate
→ 写 Completion Outbox

Engine:
Inbox 去重并确认 Current Attempt
→ CAS 推进 Node Run
→ 成功时设置 effective_attempt_id
→ 推进下游状态
→ 写状态推进 Outbox
```

Outbox Event 只携带 `event_id/project_id/aggregate_type/aggregate_id/event_type/occurred_at/trace_id` 等轻量身份与定位信息，不携带完整 DSL、Workflow Context 或 Node Output。消费者收到事件后重新读取数据库权威状态。Inbox 至少使用以下唯一约束：

```text
UNIQUE(consumer_name, event_id)
```

Kafka 按至少一次投递；业务效果通过 Inbox、CAS、状态机和 Fencing 幂等化。Execution Snapshot 一旦被 Published Version 或 Workflow Run 引用，第一阶段禁止物理删除。未来 Definition 与 Runtime 分库后，`snapshot_id` 可以成为由 Definition Service 保证的逻辑引用，不要求跨数据库物理外键。

### 5.11 PostgreSQL 表级约束与索引基线

Definition 表的最小身份与唯一约束：

```text
workflows
  PK workflow_id
  UNIQUE(project_id, workflow_id)
  active_version_id nullable

workflow_drafts
  UNIQUE(project_id, workflow_id)
  current_revision
  state_version

workflow_draft_revisions
  PK draft_revision_id
  UNIQUE(project_id, workflow_id, revision_number)
  ir_json JSONB
  catalog_revision

workflow_execution_snapshots
  PK snapshot_id
  UNIQUE(project_id, workflow_id, definition_hash)
  ir_json / dsl_json / source_map_json / compiler_manifest_json JSONB

workflow_versions
  PK version_id
  UNIQUE(project_id, workflow_id, version_number)
  execution_snapshot_id
  source_draft_revision_id
```

Runtime 表的最小身份与唯一约束：

```text
workflow_runs
  PK run_id
  project_id / workflow_id / snapshot_id
  purpose / state / state_version
  input_json / workflow_output_json
  termination_intent / deadline_at

node_runs
  PK node_run_id
  project_id / run_id / execution_node_id
  state / state_version
  current_attempt_id / effective_attempt_id
  selected_route / priority / ready_at / next_retry_at
  UNIQUE(project_id, run_id, execution_node_id)

node_attempts
  PK attempt_id
  project_id / run_id / node_run_id / attempt_seq
  state / retry_count / recovery_count
  lease_token / lease_owner / lease_expires_at
  executor_build / error_json
  UNIQUE(project_id, node_run_id, attempt_seq)

node_output_values
  PK(project_id, attempt_id)
  node_run_id / value_json / size_bytes / created_at
```

Output 不增加无语义的 `output_id`；`node_runs.effective_attempt_id → node_output_values.attempt_id` 决定唯一有效 Output。Task 不增加独立身份字段，固定 `task_id = attempt_id`。

第一阶段只为已经确定的访问路径建立索引：

```text
Scheduler Ready:
  (project_id, priority DESC, ready_at, node_run_id)
  WHERE state = 'ready'

Retry Timer:
  (next_retry_at, node_run_id)
  WHERE state = 'retry_wait'

Attempt Lease Recovery:
  (lease_expires_at, attempt_id)
  WHERE state = 'running'

Run Query:
  (project_id, state, updated_at)

Outbox Relay:
  (available_at, event_id)
  WHERE published_at IS NULL

Inbox:
  UNIQUE(consumer_name, event_id)
```

第一阶段不为 IR、DSL、Source Map、Input/Output 建通用 JSONB GIN 索引；这些不可变或按身份访问的文档不承担任意 JSON 搜索职责。第一阶段也不启用 PostgreSQL Table Partition：先以 `project_id` 作为所有 Repository 的路由前提，并保留 `created_at` 供未来归档；规模需要时优先按 Project 分库，单库历史数据确有压力后再评估按时间归档或分区。

## 6. IR/DSL 双向关系决策

第一阶段不实现 DSL → IR Decompiler。

原因是所有平台创建的 Execution Snapshot 都必须同时保存：

```text
ir_snapshot
dsl_snapshot
source_map
compiler_metadata（至少包含 compiler_version、catalog_revision 与 policy_revision）
```

因此：

- Copy 和二次编辑读取 IR Snapshot；
- Runtime 读取 DSL Snapshot；
- Runtime Error 使用 Source Map 定位 IR；
- DSL 不嵌入 IR，二者作为 Execution Snapshot 的同级产物保存。

只有未来导入外部 DSL，或迁移缺失 IR 的历史数据时，才重新评估 Decompiler。

禁止创建只有 DSL、没有 IR Snapshot 和 Source Map 的 Execution Snapshot 或 Published Version。

## 7. Human Web 与 Agent CLI

Human Web 和 Agent CLI 是同一 Definition Domain 的两个 Adapter，必须使用同一套 IR Schema、Validator、Compiler 和发布语义。

```text
Human Web ─┐
           ├→ Definition API → Draft IR → Validate/Test/Publish
Agent CLI ─┘
```

### 7.1 Web

Web 画布负责：

- 编辑 IR Node、Control Edge、Input 和 Layout；
- 保存 Draft；
- 发起 Draft Test；
- 发布 Version；
- 根据结构化 Runtime Error 高亮具体 IR 位置。

### 7.2 CLI

Agent CLI 负责：

- 本地创建和修改相同 Schema 的 IR；
- Copy 指定 Published Version 的 IR；
- 本地快速校验和预览；
- 使用 `base_revision` 上传 Draft；
- 发起服务端 Draft Test；
- 发布并正式运行。

CLI 本地校验只用于快速反馈，服务端在 Test/Publish 时仍是最终权威。CLI/Agent 可以上传 IR、触发服务端 Validate/Compile，并下载或检查服务端生成的 DSL、Source Map 和编译诊断；不得上传客户端生成的 DSL 作为可执行定义，也不得上传自制 Source Map 覆盖平台产物。Runtime 只执行平台 Compiler 生成、完整校验并固化进 Execution Snapshot 的 DSL。

未来若确需离线编译，只能另行设计包含 `IR + DSL + Source Map + Compiler Manifest + Catalog Revision + Content Hash + 平台可信签名` 的受信任 Compiled Bundle；该能力不属于第一阶段，普通 CLI DSL Upload 不作为其兼容入口。

### 7.3 调用 Principal 与运行身份

Web、CLI 和 API 不形成三套授权身份。第一阶段外部调用 Principal 只有：

```text
User             人类用户
Service Account  自动化系统或 Agent
```

Agent 是调用方式而不是特殊权限主体；CLI 可以代表 User 或 Service Account，二者使用相同的 Project 权限模型。Engine、Scheduler、Worker 等内部组件使用独立 Workload Identity 和内部接口授权，不参与 Project RBAC。

运行时必须区分“谁发起”与“以什么身份执行”：

```text
requested_by_principal_id  用于鉴权入口与审计
execution_identity_id      Project Execution Identity，用于 HTTP/RPC 运行时授权
```

Workflow Run 不继承发布者或启动者的个人 Connection/Service 权限；人员离职、Token 轮换或发起者权限变化不能改变运行身份。`run_purpose=test/production` 作为 Project Execution Identity 授权判断的一部分。

### 7.4 最小 Project 权限

| 权限 | 能力 |
|---|---|
| `workflow.read` | 读取 Workflow、Draft 与 Published Version |
| `workflow.write` | 创建、复制、保存 Draft 与发起服务端校验 |
| `workflow.test` | 创建 Draft Test Run |
| `workflow.publish` | 发布并自动激活新 Version |
| `run.create` | 使用 Active Version 创建正式 Run |
| `run.read` | 查看 Run、Node Run、Attempt 与错误 |
| `run.cancel` | 请求取消 Run |
| `connection.use` | 在 Test/Publish 时绑定 Connection |
| `service.use` | 在 Test/Publish 时绑定 RPC Service |
| `project.admin` | 管理 Project 成员、角色与受管资源 |

权限是授权判断的稳定单位；Viewer、Editor、Publisher、Operator、Owner 等 Role 只是可配置的权限集合，领域代码不得直接判断 Role 名称。User 与 Service Account 使用同一套权限。显式运行历史 Published Version 需要 `run.create + workflow.publish`；普通正式调用只需要 `run.create`，不要求调用者再次拥有 Snapshot 中每个 Connection/Service 的作者权限。

### 7.5 Web、CLI 与 API 的统一命令面

第一阶段逻辑命令固定为：

| 逻辑命令 | 关键输入 |
|---|---|
| `CreateWorkflow` | 名称、初始 IR |
| `Get/ListWorkflow` | Project、Workflow 查询条件 |
| `GetDraft` | Workflow |
| `SaveDraft` | `base_revision + IR` |
| `ValidateDraft` | 确定 Draft Revision |
| `CopyPublishedVersion` | 来源 Workflow + Version |
| `TestDraft` | Draft Revision + Input |
| `PublishWorkflow` | Draft Revision |
| `CreateRun` | Active Version + Input |
| `CreateHistoricalVersionRun` | 确定 Version + Input |
| `Get/ListRun` | Run 查询条件 |
| `CancelRun` | Run ID |
| `List/DescribeNodeType` | Node Description |
| `List/DescribeConnection` | 当前 Principal 可见的脱敏描述 |

Web 和 CLI 只是同一 Application Command/API 的 Adapter，不能具有绕过服务端权限、Validator 或 Compiler 的私有入口。CLI 命令空间与上述逻辑命令一一对应，例如：

```text
workflow create/list/get/copy
workflow draft pull/push/validate/test
workflow publish
workflow run/start/status/list/cancel
node-type list/describe
connection list/describe
```

第一阶段 `CopyPublishedVersion` 只支持同一 Project；跨 Project Copy 需要重新绑定 Connection、Service 与权限，不进入最小闭环。

### 7.6 Draft Save 与完整校验分离

Draft Save 必须允许 Web 自动保存尚未完成的画布：保存只要求 JSON 可解析、IR 外壳合法并满足文档大小与安全限制；完整拓扑、Binding、类型和受管资源问题以结构化 Diagnostics 返回或记录，不阻止保存该 Draft Revision。Draft 因此可以处于不可 Test/Publish 状态。

`TestDraft` 与 `PublishWorkflow` 必须对确定 Draft Revision 执行完整、服务端权威校验；存在 Error 级 Diagnostic 时不得编译执行快照或发布。

### 7.7 Connection/Service 双重授权

Draft Save 可以保存尚未解析或当前 Principal 不可用的 `connection_ref/service_ref`，但诊断不得泄露不可见资源是否存在。Test/Publish 时同时检查：

```text
调用 Principal 具有 connection.use / service.use
+ Ref 能解析为 Project 可用的稳定内部 ID
+ Project Execution Identity 对该资源及 run_purpose 有权限
```

Compiler 将 Ref 固化为稳定内部 ID，但不把 Secret、Credential 或动态地址写入 DSL。Runtime 每次调用时使用 Project Execution Identity 再次校验资源启用状态、`run_purpose`、HTTP Method、规范化后的最终路径或 RPC Operation，并动态取得当前 Credential。授权撤销和资源禁用必须立即约束旧 Published Version；不可变 Snapshot 不等于永久冻结外部访问权。

Draft Test 可能产生真实外部副作用，因此 Connection/Service Policy 可以分别允许 `test` 与 `production`。

### 7.8 外部命令幂等

以下命令必须携带 `Idempotency-Key`：

```text
CreateWorkflow
SaveDraft
CopyPublishedVersion
TestDraft
PublishWorkflow
CreateRun
CreateHistoricalVersionRun
Connection Mutation
```

幂等作用域固定为：

```text
project_id + command_name + target_scope + idempotency_key
```

服务端必须先鉴权，再查询幂等结果；记录规范化 Request Hash。相同 Key 与相同请求返回第一次创建的资源，相同 Key 与不同请求返回 `IDEMPOTENCY_KEY_REUSED`。Publish Key 随 Published Version 保留，Run/Test Key 随 Workflow Run 保留，Save Key 随 Draft Revision 保留。`CancelRun` 是状态幂等操作，重复请求返回当前取消结果，不产生第二次状态推进。

### 7.9 统一错误契约

Web 与 Agent 共用机器可读错误结构：

```json
{
  "error": {
    "code": "DRAFT_REVISION_CONFLICT",
    "message": "Draft revision has changed",
    "retryable": false,
    "request_id": "req_...",
    "trace_id": "trace_...",
    "details": {
      "expected_revision": 12,
      "current_revision": 13
    },
    "locations": [
      {
        "logical_node_id": "call_customer_api",
        "ir_path": "/nodes/call_customer_api/inputs/relative_path"
      }
    ]
  }
}
```

`code` 是客户端可依赖的稳定契约，客户端不得解析 `message` 作程序判断。Validation 可以返回多个 Diagnostic/Location；Runtime Error 继续通过 Source Map 返回 IR Node、Edge 或字段路径。不可见的跨 Project 资源统一表现为 `RESOURCE_NOT_FOUND`，不得泄露其是否存在。

| HTTP Status | 错误类别 |
|---:|---|
| `400` | 请求格式错误 |
| `401` | `UNAUTHENTICATED` |
| `403` | `PERMISSION_DENIED` |
| `404` | `RESOURCE_NOT_FOUND` |
| `409` | Revision、状态、Idempotency 冲突或 Workflow 未发布 |
| `413` | IR/Input/Output 超限 |
| `422` | IR 校验、编译或受管资源绑定失败 |
| `429` | 调用限流 |
| `500/503` | 内部错误或临时基础设施不可用 |

HTTP Status 只表达传输层错误类别，领域处理必须以稳定 Error Code 为准。

## 8. Workflow Run 状态模型

### 8.1 Definition Reference

所有执行共用 Workflow Run 模型，通过以下维度区分：

```text
run_purpose:
  test
  production

definition_source:
  draft_snapshot
  published_version
```

合法性约束：

```text
run_purpose=production
必须满足 definition_source=published_version
```

### 8.2 Workflow Run 状态

```text
pending
running
succeeded
failed
canceled
timed_out
```

合法主路径：

```text
pending → running → succeeded | failed | canceled | timed_out
pending → canceled
```

Workflow Run 不使用 `retrying` 状态；节点重试期间 Workflow Run 仍为 `running`。

取消请求使用 `cancel_requested_at` 表达用户意图。在在途节点停止或结算前，Run 仍是 `running`；最终才进入 `canceled`。UI 可以从该字段派生“正在取消”。

取消、失败和超时统一写入首次成功即不可覆盖的终止意图：`termination_kind/termination_requested_at/termination_cause`。第一个通过数据库锁或 CAS 写入的终止意图胜出；后续竞争事件不得改变最终状态种类。

### 8.3 Node Run 状态

```text
pending
ready
queued
running
retry_wait
succeeded
failed
timed_out
skipped
canceled
```

主路径：

```text
pending → ready → queued → running → succeeded
                              ├→ retry_wait → ready
                              ├→ failed
                              ├→ timed_out
                              └→ canceled

pending → skipped
pending → canceled
ready   → canceled
queued  → canceled

Control Node：
pending → succeeded | failed | skipped | canceled
```

唯一约束：

```text
UNIQUE(run_id, execution_node_id)
```

Workflow Run 开始时初始化全部 Node Run，以支持恢复、审计和完整观察。

Start、End、Branch 具有 Node Run 但不创建 Attempt。Start 持久化 `workflow_input` 后直接成功；Branch 原子持久化 `selected_route` 后直接成功；End 将 `workflow_output` 与 Workflow Run `succeeded` 在同一事务中持久化。

### 8.4 Node Attempt 状态

```text
queued
running
succeeded
failed
timed_out
canceled
lost
```

主路径：

```text
queued → running → succeeded | failed | timed_out | canceled | lost
queued → canceled
```

唯一约束：

```text
UNIQUE(node_run_id, attempt_seq)
UNIQUE(task_id)
```

`attempt_seq` 对每次物理执行单调递增，用于审计和 Fencing；`retry_count` 只计算由业务错误触发的重试；`recovery_count` 单独计算 Worker、Lease 或基础设施故障后的恢复执行。三者不得混用。

`lost` 表示 Worker、Lease 或任务所有权失效，不等于 Node Run 已经失败，也不自动消耗业务重试预算。恢复执行受独立的最大恢复次数和 Workflow Deadline 约束。

## 9. Engine、Scheduler、Worker 状态所有权

### 9.1 Engine

Engine 是 Workflow Run 和 Node Run 语义状态的唯一拥有者，负责：

- 初始化 Workflow Run 与全部 Node Run；
- 根据依赖和分支计算 Ready/Skipped；
- 根据 Attempt Result 推进 Node Run；
- 判断是否重试；
- 推进下游节点；
- 决定 Workflow Run 最终状态。

Engine 是可恢复、事件驱动的状态推进器，不需要单个进程从开始到结束持续持有整个 Run。

### 9.2 Scheduler

Scheduler 只处理已由 Engine 判定为 `ready` 的 Node Run：

- 选择本次允许执行的 Ready Node；
- 获取调度许可；
- 创建 Node Attempt；
- 通过统一领域操作将 Node Run 从 `ready` 推进到 `queued`；
- 将任务交给任务传输层。

Scheduler 不解释 Branch 条件，不决定下游 Skipped，不判断 Workflow 是否成功。

Scheduler 可以水平扩展，但所有实例必须共享 Redis 中的项目公平状态，并通过数据库 CAS 竞争 Node Run。公平身份只有 `project_id`；每个实例独立维护一套本地项目轮转状态是错误实现，因为它无法形成全局项目公平性。

### 9.3 Worker

Worker 只执行一个 Node Attempt：

```text
本地执行槽可用后领取 Task
→ 调用 Attempt Coordinator ClaimAttempt
→ Coordinator CAS: queued → running 并建立 Lease
→ ACK Task
→ 通过 Execution Context 接口加载输入和执行配置
→ 调用 Executor
→ 调用 Attempt Coordinator CompleteAttempt
```

Worker 不持有 Workflow 数据库凭证，也不直接读取或更新 Workflow、Node Run、Attempt、Definition 等关系表。

Worker 不能直接修改：

- Workflow Run 最终状态；
- Node Run 最终语义状态；
- 下游 Node Run；
- Retry 计划；
- Published Version。

### 9.4 Attempt Coordinator

Attempt Coordinator 是 Control Plane 内部的逻辑模块，对 Worker 提供：

```text
ClaimAttempt
HeartbeatAttempt
CompleteAttempt
```

它拥有 Attempt 的数据库 CAS、Lease、Fencing、Output 持久化和 Completion Outbox 写入。第一阶段它可以与其他 Control Plane 模块部署在同一进程中，但接口和状态所有权必须独立。

## 10. Retry、Timeout 与 Failure

### 10.1 Retry

第一阶段支持：

```text
max_attempts
max_recoveries
attempt_timeout
retry_backoff
retryable_error_codes
```

`max_attempts` 只约束初次业务执行和业务重试，不把基础设施恢复执行计入其中；`max_recoveries` 独立限制连续 Lost 恢复，Workflow Deadline 始终是最终上限。

第一阶段 Retry、Timeout 不进入 IR，也不作为 Node Input。Compiler 根据内部 Node Catalog 默认值和 Project Policy 解析最终策略，并将其固化进 Execution Snapshot 的 DSL；作者暂不覆盖这些策略。

Worker 只报告结构化 Attempt Result。Engine 判断是否 Retry，并由 Engine Timer 在数据库中的 `next_retry_at` 到期后将 Node Run 从 `retry_wait` 推进为 `ready`；Scheduler 只为 `ready` Node Run 创建新 Attempt。Retry Timer 不依赖 Kafka Delay Topic。

Worker 不在进程内 Sleep 后自行重试。

### 10.2 Node Timeout

Node Attempt 超时后：

- 允许重试：Node Run 进入 `retry_wait`；
- 不允许重试或重试耗尽：Node Run 进入 `timed_out`；
- 默认令 Workflow Run 进入 `failed`，错误码为 `NODE_TIMEOUT`。

### 10.3 Workflow Timeout

只有整个 Workflow 超过 Workflow Deadline 时，Workflow Run 才进入 `timed_out`，并取消所有未完成 Node Run 和 Attempt。

### 10.4 第一阶段失败策略

第一阶段采用 fail-fast：

- 节点失败后可以按策略重试；
- 重试耗尽或错误不可重试时停止派发新节点；
- 等待或取消在途节点；
- Workflow Run 进入 `failed`。

第一阶段不支持失败分支、自定义兜底输出和“继续执行并收集多个失败”。

## 11. 并发、一致性与幂等不变量

1. Workflow Run、Node Run、Attempt 都具有 `state_version` 或等价 CAS 条件。
2. 状态转换必须通过明确领域操作完成，不能由任意模块直接更新状态字符串。
3. 任务与事件按至少一次处理，业务层必须容忍重复消息。
4. 任务身份为：

   ```text
   task_id = attempt_id
   ```

5. Worker 收到重复 Task 时必须通过 Attempt Coordinator 幂等 Claim；Worker 不直接查询数据库。
6. `ClaimAttempt` 必须在同一事务中完成 `queued → running`、Lease/Fencing 建立和 Worker 能力校验。
7. Worker 只有在本地执行槽可用且 `ClaimAttempt` 已持久化成功后才 ACK Task；ACK 不等待节点执行完成。
8. Attempt 终态、带 `attempt_id` 的 Inline JSON Output Candidate、Completion Outbox 必须由 Attempt Coordinator 写入同一数据库事务；只有 Engine 后续接受并设置 `effective_attempt_id` 后该 Output 才对下游可见。
9. 过期 Worker Result 必须通过 `current_attempt_id + attempt_seq + lease_token` 拒绝。
10. Engine 消费 Completion Event 时使用 Inbox 去重，并通过数据库状态与 CAS 推进语义状态；Kafka 顺序只可作为优化，不能成为正确性前提。
11. 无法执行的 Poison Task 必须先留下持久化错误；若能识别 Attempt，必须将其结算后才能最终 ACK/Reject，不能令 Attempt 永久停在 `queued`。
12. 外部副作用使用稳定的逻辑幂等键：

   ```text
   execution_idempotency_key = run_id:execution_node_id
   ```

   Attempt 重试时该逻辑幂等键保持不变。

### 11.1 Engine 信号与恢复

Engine 消费 `RunCreated/RunCancelRequested/AttemptCompleted/AttemptLost/RetryDue/RunDeadlineReached` 等唤醒信号。事件不是权威状态；Engine 必须通过 Inbox 去重、重新读取数据库、按 Workflow Run 加锁或 CAS，并在同一事务中提交状态转换与下游 Outbox。

CreateRun 使用 Idempotency Key 在一个事务中创建 `pending` Run、保存 `snapshot_id`、Input 与 `deadline_at` 并写入 RunCreated Outbox；API 事务不初始化 Node Run。Engine 通过 Inbox 去重，在第一阶段使用一个事务幂等初始化所有 Node Run、预检全部 Operation Version、推进 Start 并将 Run 置为 `running`。不支持的 Operation 必须在任何 Node 执行前以 `RUNTIME_OPERATION_UNSUPPORTED` 失败。

后台恢复模块只补发唤醒信号，不绕过状态机：Engine Timer 处理 Retry Due，Deadline Scanner 处理 Workflow Deadline，Attempt Reaper 处理 Lease 过期，Completion/Run Reconciler 修复遗漏事件和长期无进展状态。Engine 以数据库中的 Attempt Result 为权威，不信任 Kafka Event 携带的结果副本。

### 11.2 Run 终止与成功条件

首次写入终止意图后，Engine 停止产生新的 Ready Node，将尚未执行的 Node Run 取消，并请求取消在途 Attempt；待 Attempt 终态或 Lease 失效后，Run 进入 `canceled/failed/timed_out` 中与意图对应的终态。

Workflow Run 只有在 End Node succeeded、没有终止意图、所有 Node Run 均为终态且 Workflow Output 已持久化时才能进入 `succeeded`。End 成功、Workflow Output 与 Run succeeded 必须在同一数据库事务中提交。

## 12. Runtime Error 定位不变量

运行错误必须是结构化数据，至少包含：

```text
error_code
phase
retryable
run_id
snapshot_id
definition_hash
execution_node_id
dsl_field（适用时）
execution_edge_id（适用时）
ir_node_id（Source Map 增强后）
ir_edge_id（适用时，Source Map 增强后）
ir_field（适用时，Source Map 增强后）
attempt_id
expected / actual（适用时）
message
```

Runtime Error 必须能够映射到：

- 具体 IR Node；
- 具体 IR Control Edge；
- 具体 Node Input；
- 具体参数、输入或输出字段。

Worker 只需报告 Execution ID、可选的相对 `dsl_field` 和结构化错误；Control Plane 使用 Source Map 增强为 IR 位置。Web 使用该信息定位并高亮画布元素；Agent CLI 使用相同信息进行机器可读修复。

## 13. Engine 激活、数据依赖与 Skipped 语义

### 13.1 Control Dependency 与 Data Dependency

Control Edge 表达节点所在的控制路径是否被激活；`source=ref` 的 Node Input 表达目标节点依赖哪个上游 Output。后者在领域语义上仍属于 Data Dependency，但不再建模为独立 Binding 对象。

Compiler 构建的有效执行依赖由两者共同组成：

```text
Execution Dependencies
= Control Dependencies
∪ Data Dependencies
```

Scheduler 不解释上述依赖，只消费 Engine 已经判定为 `ready` 的 Node Run。

### 13.2 必填数据引用的静态安全条件

如果 Target Node 的必填输入引用 Source Node 的输出，发布校验必须同时保证：

1. Source Node 是 Target Node 的控制流上游；
2. Source Output 与 Target Input 均存在；
3. 两端数据类型兼容；
4. 该引用不会形成执行依赖环；
5. Target 被激活时，Source 一定也会被激活。

第五条使用以下语义表达：

```text
Active(Target) ⇒ Active(Source)
```

仅仅存在 `Source → ... → Target` 路径不够。如果 Target 可能通过另一条激活路径运行，而 Source 位于未选择分支，则该 Ref Input 不安全。

不满足上述约束时必须在发布阶段返回结构化错误，不能将错误延迟到 Runtime：

```text
error_code = UNSAFE_DATA_BINDING
source_node_id
target_node_id
ir_node_id = {target}
ir_field = inputs.{input}
```

第一阶段不支持 Optional Reference、分支数据自动合并、缺失值默认表达式和 Lazy Reference。

### 13.3 Node 激活判断

Engine 等待节点的所有直接 Control Input 完成结算，然后执行：

```text
所有进入控制边均 inactive
→ Node Run = skipped

至少一条进入控制边 active
→ Node 被激活
→ 等待必填 Data Dependency
→ 数据源成功后 Node Run = ready
```

一旦节点被激活，就不得再进入 `skipped`。

```text
activated node
→ ready
→ queued
→ running
→ succeeded | failed | timed_out | canceled
```

### 13.4 Skipped 的唯一语义

`skipped` 只表示没有任何 Active Control Path 到达该节点，通常由未选择的 Branch 产生。

Skipped 会沿只有 inactive 入边的路径继续传播。如果一个节点同时存在其他 active 入边，该节点仍被激活，不进入 `skipped`。

以下情况不能使用 `skipped`：

| 情况 | Node Run 处理方式 |
|---|---|
| 上游最终失败导致 Run fail-fast | `canceled`，reason=`RUN_FAILED` |
| 用户取消 Workflow Run | `canceled`，reason=`RUN_CANCELED` |
| Workflow 超时 | `canceled`，reason=`RUN_TIMED_OUT` |
| Scheduler 暂时没有资源 | 保持 `ready` |
| Worker 尚未领取任务 | 保持 `queued` |
| 必填输入在 Runtime 缺失 | `failed`，并报告编译器或数据契约不变量异常 |

Engine 的节点判断顺序为：

```text
Control Input 是否全部结算？
├─ 否：保持 pending
└─ 是
   ├─ 没有 active Control Input：skipped
   └─ 至少一个 active Control Input
      ├─ 必填 Data Dependency 未完成：保持 pending
      ├─ 必填 Data Source 成功：ready
      └─ 必填 Data Source 最终失败：Run fail-fast
```

### 13.5 第一阶段 Control Graph 约束

第一阶段采用单入口、单出口的有向无环控制图：

1. 每个 Workflow 恰好包含一个 Start 和一个 End。
2. Start 没有入边，End 没有出边。
3. 每个 Node 都必须从 Start 可达，并且能够沿控制边到达 End。
4. 普通 Node 成功后激活其全部出边，因此可以形成并行执行路径。
5. Branch 是排他分支，每次求值必须且只能选中一个 Route；必须声明 Default Route，避免无匹配路径。
6. Branch 被选中的 Route 对应出边为 active，其他 Route 对应出边为 inactive；同一 Route 可以对应一条或多条出边。
7. 多入边 Node 使用隐式 OR-Join：等待全部直接入边完成结算，至少一条 active 时只激活一次；第一阶段不增加 Join Node。

Branch 只操作一个显式 `value` Input，Case 按顺序使用受类型约束的有限 Operator，第一个匹配 Route 胜出；不支持任意表达式、函数或隐藏数据引用。路径缺失或 Operator 类型不匹配会令 Branch 失败，不能静默进入 Default Route。

### 13.6 分支输出限制

由于第一阶段不支持 Optional Reference 和分支数据自动合并，单一 End 只能引用在所有可能激活路径上都必然产生的数据：

```text
End 引用 Source
⇒ Active(End) ⇒ Active(Source)
```

因此不同排他分支各自产生的结果不能直接汇合为 Workflow Output。需要该能力时，未来必须显式引入 Data Merge/Select 语义，不能让 Runtime 猜测缺失值或临时选择某个分支结果。

## 14. Scheduler 一秒时间桶 FIFO 与 Topic Queue Window

### 14.1 调度顺序

Engine 在数据库中将 Node Run 推进为 `ready`，提交后尽力登记到 Scheduling Redis。Scheduler 先执行有界 FIFO 准入，再将任务交给 Kafka：

```text
Database Ready Node
→ 1s Ready Bucket + Project Load Selection
→ Redis Inflight Reservation
→ Database Transaction: ready → queued + Attempt + Outbox
→ Outbox Relay
→ Kafka
→ Worker
```

不能将所有 Ready Node 直接写入 Kafka 后再由 Worker 检查项目配额，否则大项目可以提前占满消息积压，项目公平性也会退化为消费端竞争。

Ready Node 的权威事实源是数据库。Redis 只维护可重建的 Ready/Load/Topic Occupancy 索引，Kafka 只传输已经通过准入的 Attempt。

### 14.2 当前冻结规则

- Builtin 与 Sandbox 分别选择候选，但共享跨资源类 `Project Load = Reservation + Queued + Running`；
- `ready_at` 使用 PostgreSQL 事务时间并截断为一秒 UTC 时间桶；先按时间桶升序，同桶内按 Project Load、最近准入序号、Project 内 Priority、精确 ReadyAt、Node Run ID 选择；
- Topic Queue Window 由 Worker 最近实际完成速率 EWMA 乘约五秒缓冲并按 Profile 上下界夹取；Worker Slot 不参与公式；
- Topic Occupancy 只包含未确认 Reservation 与 Queued Attempt。Claim 释放 Topic 占用但保留 Project Load，Attempt 终态释放 Project Load；
- Scheduling Redis 首版使用单逻辑同槽 Lua 原子维护 Candidate、Project Load/Last Granted、Topic Window/Occupancy、Reservation 与紧凑 Inflight，不使用固定 Lane、Credit、Grant 或每秒公平 Epoch；
- Redis 使用 `noeviction`、显式 `maxmemory` 与高/恢复水位；Redis 丢失后从 PostgreSQL Ready、Queued、Running 重建新 Generation 后恢复准入。

完整排序、生命周期和验收规则以 [01_分布式调度与Worker执行边界](./01_分布式调度与Worker执行边界.md) 第 11 节为准。

### 14.H1 历史方案：等权 Max-Min（已由 14.2 取代）

第一阶段公平调度的唯一身份是 `project_id`，不设置 `project_priority`、`project_weight` 或固定 30% 配额。Node Type、Resource Class、Worker Pool 和 Kafka Topic 都不产生第二套公平份额。

每个 Scheduling Epoch 根据有 Ready Node 的竞争项目集合，使用等权 Max-Min Fairness 动态计算项目基础额度：若有 `N` 个需求充足的竞争项目，每个项目基础份额约为总派发容量的 `1/N`；需求不足项目释放的容量由其他项目等权借用。新竞争项目加入后，超出新份额的项目停止获得新额度，但不抢占已经运行的 Attempt。

`inflight = queued + claimed + running`；其中成功 Claim 后持久状态计入 `running`，不新增独立 Node Run 状态。`ready` 和 `retry_wait` 不占 Inflight。第一阶段每个节点调度成本统一视为 1；未来若任务成本差异需要计量，可在不改变公平身份和状态所有权的前提下升级额度算法。

当 Scheduler 选中一个 Project 后，项目内部按以下稳定顺序选择 Ready Node：

```text
priority DESC
ready_at ASC
node_run_id ASC
```

相同 Priority 下等价于 FIFO；这里只保证派发顺序，不保证完成顺序。多 Scheduler 实例通过 Redis 共享项目轮转和额度状态，不能各自在本地独立计权。

Task Contract 携带由 Runtime Routing Policy 解析出的 `resource_class`。第一阶段最小资源类为 `builtin` 与 `sandbox`；IR/DSL 不得写入 Kafka Topic 名称。Resource Class 只用于 Worker 执行兼容性和安全路由，不参与项目公平计算。

Kafka 不按项目创建 Topic 或 Consumer Group。项目公平性在 Scheduler 内完成，Kafka 使用按 Resource Class 划分的共享 Topic。

### 14.H2 历史方案：Redis Lane/Credit（已由 14.2 取代）

Redis 使用固定数量的逻辑 Scheduling Lane 分散高频调度状态：

```text
lane_id = stable_hash(project_id) % lane_count
```

Lane 不是 Redis 实例或 Kafka Partition。同一 Project 的 Ready 索引、轮转位置、Inflight Reservation 和临时额度归入同一个 Lane，并通过 Redis Cluster Hash Tag 共置。`lane_count` 是预配置的容量参数，Redis 扩容通过 Slot 迁移完成，不改变稳定映射；未来改变 Lane 数量必须版本化迁移。

每个 Scheduling Epoch，Control Plane 内带 Lease/Fencing 的 Credit Balancer 根据各 Lane 汇总的竞争项目、需求、Inflight 和全局派发窗口，批量分配 Lane Credit。每个 Task 的项目选择、Credit 扣减和 Reservation 建立完全在 Lane 内原子完成；跨 Lane 只低频汇总、发放、回收和再平衡 Credit，不在每次 Task 准入时访问单个全局热点 Key。

Redis 不保存独立 Permit 领域对象，而是使用预生成的 `attempt_id` 作为短期 Inflight Reservation 身份。

概念结构：

```text
sched:{lane_id}:project:{project_id}:inflight
  ├─ attempt_id_1
  ├─ attempt_id_2
  └─ attempt_id_3
```

Scheduler 通过 Redis 原子操作完成：

```text
Attempt 已存在 Reservation
→ 幂等返回成功

Project 当前 Epoch 额度或 Global Dispatch Window 已用尽
→ 拒绝准入

否则
→ 添加 attempt_id Reservation
```

释放使用 Attempt ID 幂等删除，不能只执行无身份的计数器 `DECR`，避免重复 Completion Event 将计数减成负数。

获取 Reservation 后，Scheduler 在数据库事务中：

```text
CAS: Node Run ready → queued
+ 创建 Node Attempt
+ 保存 attempt_id
+ 写 NodeTask Outbox
```

数据库事务失败时立即释放 Reservation；Scheduler 在 Reservation 后、数据库事务前崩溃时，由 TTL 和 Reconciler 清理孤儿 Reservation。

数据库中的 `queued/running` Attempt 才是权威运行事实，Redis Reservation 只承担高频原子准入和快速计数。

### 14.H3 历史方案：Slot Dispatch Window（已由 14.2 取代）

Kafka 前设置全局有界 `dispatch_window`：

```text
admitted = queued + claimed + running
admitted <= dispatch_window
```

只有已经取得 Project Credit 且目标 Worker Pool 具有可用容量的 Attempt 才能进入 Kafka。`dispatch_window` 只允许接近 Worker 短期消化能力的任务进入传输层，并可包含少量缓冲；其余 Node Run 保持数据库权威的 `ready` 状态。禁止深度预派发，否则大项目会提前占满 Kafka 积压，后加入项目无法重新公平排序，取消和额度调整也会被架空。

### 14.3 Redis 故障与重建

Redis 不可用或刚恢复时，第一阶段默认 Fail Closed：

```text
暂停新的 Node Admission
→ 已运行 Worker 继续执行
→ Engine 继续处理完成事件
→ 新节点保留在 ready
→ 从数据库 Ready、queued/running Attempt 重建 Candidate、Project Load 与 Topic Occupancy
→ 恢复 Scheduler
```

Redis 丢失不能导致 Workflow、Node Run 或 Attempt 丢失，也不能令系统在未重建配额时无上限派发。未来可以增加显式的数据库准入降级模式，但不属于第一阶段默认路径。

## 15. Execution Context、Node Output 与 Redis Hot Cache

### 15.1 逻辑变量池

Workflow Execution Context 在领域上不是可由任意节点修改的共享全局 Map，而是不可变值的集合：

```text
Run Input
Node A Final Output
Node B Final Output
Node C Final Output
```

下游节点只能通过显式 Ref Input 读取上游输出。上游 Node Run 成功后，其最终有效 Output 不再修改；Retry Attempt 只有被 Engine 接受并写入 `node_runs.effective_attempt_id` 后，对应 `node_output_values` 才能成为下游可见输出。

### 15.2 权威值与缓存分层

```text
PostgreSQL = 第一阶段权威值
Redis      = Active Run Hot Cache
```

第一阶段所有 Node Input/Output 均为受大小限制的 Inline JSON：

- 持久化到数据库；
- 同时缓存到 Redis；
- 下游优先从 Redis 批量读取；
- Cache Miss 时从数据库回源并回填；
- 超过明确大小上限时以 `OUTPUT_SIZE_LIMIT_EXCEEDED` 失败，不能无限扩大数据库 JSON 和 Redis Value。

第一阶段不建设 Artifact Store，也不在当前表结构中预设 Artifact 多态字段。大型值与文件存储作为未来扩展，通过新的 Value Reference 能力引入，不改变已经发布 Workflow 的 IR/DSL 语义。

Secret 明文不得进入普通 Execution Context Cache。

### 15.3 Output 写入顺序

Node Attempt 成功时：

```text
Attempt Coordinator Database Transaction:
  Attempt → succeeded
  + 写带 attempt_id 的 Inline JSON Output Candidate
  + 写 Completion Outbox

Commit
→ Completion Event 触发 Engine
→ Engine CAS 接受当前 Attempt
  + Node Run → succeeded
  + 设置 effective_attempt_id
  + 写状态推进 Outbox
→ 回填 Redis Effective Output Cache
→ Engine 推进下游 Node Run
```

迟到、被 Fencing 拒绝或不再是当前执行身份的 Attempt 即使留下 Output Candidate，也不得成为 `effective_attempt_id`。Redis 写入失败不能回滚已经成功提交的 Node Attempt 或 Node Run；下游读取 Cache Miss 时通过 `effective_attempt_id` 从 PostgreSQL 回源，因此 Redis 故障不影响运行正确性。

Kafka Task 只携带身份和定位信息，不携带完整 Workflow Context：

```text
project_id
run_id
snapshot_id
node_run_id
attempt_id
attempt_seq
definition_hash
resource_class（仅执行路由，不参与公平计算）
```

Worker 通过 Definition/Execution Context 接口加载节点定义和输入，可以优先命中 Redis Hot Cache；Cache Miss 由这些接口回源 PostgreSQL，Worker 不直接访问 Workflow 数据库。

### 15.4 Redis Run Read Model

Workflow Run 和 Node Run 的状态转换先提交数据库，再异步更新 Redis Read Model。

Redis 可以缓存：

```text
Workflow Run Status
Node Run Compact Status
节点总数与各状态计数
当前运行节点
最新错误摘要
updated_at
```

普通 Web/CLI 进度查询优先读取 Redis；强一致查询、状态推进和审计读取数据库；Redis Miss 时从数据库重建。

Engine 不能使用 Redis Status Cache 作为状态转换依据。

### 15.5 Redis 的冻结职责

| Redis 角色 | 数据特点 | 丢失后的处理 |
|---|---|---|
| Definition Cache | Execution Snapshot/DSL 高频读取、不可变 | 从数据库重建 |
| Execution Context Cache | Active Run Input/Output 高频读取 | 从数据库回源 |
| Run Read Model | Web/CLI 高频状态查询 | 从数据库重建 |
| Scheduling State | FIFO Ready Index、Project Load、Topic Window/Occupancy、Reservation、紧凑 Inflight | 从数据库重建后恢复准入 |

### 15.6 Scheduling Store 与 Cache Store

Redis 在代码和配置上拆成两个逻辑接口：

```text
Scheduling Store
  Ready Bucket / Active Project / Project Load
  Topic Window / Occupancy / Reservation / Inflight

Cache Store
  Execution Snapshot Cache
  Execution Context Cache
  Run Read Model
  Web 瞬时通知
```

Scheduling Store 丢失后虽然可由 PostgreSQL 重建，但在重建完成前必须暂停新准入；其内存策略不得自动淘汰调度状态。Cache Store 中的数据全部可以回源或重建，允许通过 TTL 与淘汰策略回收。生产环境使用不同 Redis Endpoint 隔离内存策略、容量和故障域；本地开发与最小测试环境允许共用 Endpoint。物理隔离不等于必须使用 Redis Cluster：每个 Endpoint 第一阶段可以是高可用主从部署，容量需要时再分别扩展为 Cluster。

Execution Context Cache 第一阶段采用“一个 Run 一个 Redis Hash”，保存 Run Input 与已经被 `effective_attempt_id` 接受的 Node Output，支持下游批量 `HMGET`。系统以大量并发 Run 为主要扩展维度；未来只有单 Run 本身成为热点时才评估分段 Hash。

### 15.7 Redis 生命周期与实时通知

Redis 只冻结生命周期关系，不在架构基线中固定具体秒数：Execution Snapshot 使用长 TTL 与随机抖动；Active Run Context 和 Run Read Model 在 Run 活跃期保留、终态后保留诊断/查询窗口；未确认 Reservation 只覆盖 Redis Reserve 到 PostgreSQL Dispatch 的短窗口，已确认 Inflight 由 Claim/终态回调和权威校准清理。具体 TTL、校准间隔和 Lease 秒数属于根据容量与 SLO 调整的运维参数。

Redis TTL 不是业务计时器。TTL 到期不得直接改变 Workflow Run、Node Run 或 Attempt 状态；Retry、Timeout、Deadline 和 Lost 判定仍以 PostgreSQL 权威字段与对应扫描器为准。

Kafka 继续承担持久、至少一次的领域事件和运行唤醒。Redis Pub/Sub 只承担 WebSocket Gateway 的瞬时“状态可能已变化”通知；通知丢失后由 Web/CLI 重新读取 Run Read Model 或数据库恢复。第一阶段不使用 Redis Streams，也不将其列为默认演进路线；只有未来出现明确的、短窗口可恢复 Web 通知需求时才重新评估，且不得用于驱动 Engine、Scheduler 或保存权威状态。

### 15.8 DB-First、缓存预热与 Write-Behind 边界

Workflow 核心权威数据禁止采用 Redis Write-Behind。Draft Revision、Published Version、Execution Snapshot、Workflow/Node/Attempt 状态、Lease/Fencing、Effective Output、Idempotency、Outbox/Inbox、权限与审计均必须先通过 PostgreSQL 事务或 CAS 持久化；Redis 不得先确认这些业务事实再异步落库。

Effective Node Output 使用以下模式：

```text
PostgreSQL 持久化 Output Candidate
→ Engine 接受 Attempt 并提交 effective_attempt_id
→ Post-Commit Best-Effort Eager Fill 到 Redis Run Context Hash
→ Cache Miss 时从 PostgreSQL 批量回源并回填
```

缓存预热发生在数据库提交之后，可以由本地 Post-Commit Hook 或 Outbox/Projection 异步完成，不属于 Write-Behind。Redis 写入失败或超时不回滚 Node Success，也不阻塞 Workflow 推进；下游第一次 Cache Miss 最多回源一次，后续仍从 Redis 高频读取。

允许明确有损、可丢失、可重建且不参与状态机裁决的数据使用 Redis Only 或批量 Write-Behind，例如运行进度百分比、短期日志尾部、在线 Presence、Cache Hit 统计和非计费监控聚合。若同类数据用于计费、强配额、合规审计或故障追责，则升级为权威数据，必须进入 PostgreSQL、Kafka 或专门的持久化系统。

第一阶段不建设通用 Redis Write-Behind Framework。需要可靠异步接收、重放和批量持久化的数据优先使用 Kafka；Scheduling Ready/Load/Topic/Reservation/Inflight 是 Redis 原生的可重建协调状态，不是等待异步写回 PostgreSQL 的 Write-Behind 数据。

## 16. 已冻结的不变量摘要

1. Draft 可测试，但正式运行只能使用 Published Version。
2. Draft Test 将确定 Draft Revision 编译为不可变 Execution Snapshot，并以 `snapshot_id` 创建 Run。
3. Published Version 一对一引用包含不可变 IR、DSL、Source Map、Hash 和 Compiler Manifest 的 Execution Snapshot。
4. `publish` 永远自动激活新版本。
5. 没有 Active Version 时禁止正式调用。
6. Run 创建后只以 `snapshot_id` 绑定执行定义，不跟随 Draft、Published Version 或 Active Version 变化。
7. Rollback 只切换 Active Version 指针。
8. Copy 复制指定 Published Version 的 IR，不反编译 DSL。
9. 第一阶段不实现 DSL → IR Decompiler。
10. Human Web 和 Agent CLI 使用同一 IR、Validator、Compiler 和 Definition Service。
11. Node 与 Control Edge 使用稳定 Logical ID。
12. Workflow Run、Node Run、Node Attempt 是三个不同生命周期对象。
13. Engine 决定工作流语义，Scheduler 分配 Ready Task，Worker 只执行 Attempt。
14. Workflow Run 不使用 `retrying` 状态。
15. Node Retry 由 Engine 决定，Engine Timer 到期后推进为 `ready`，Scheduler 只负责后续派发。
16. 第一阶段采用 fail-fast。
17. 消息按至少一次处理，依靠 CAS、幂等、Outbox 和 Fencing 保证正确性。
18. Runtime Error 必须无损定位回 IR 节点、边或字段路径。
19. 必填数据 Source 必须是 Target 的控制流上游，并满足 `Active(Target) ⇒ Active(Source)`。
20. `skipped` 只表示控制路径未激活；节点一旦被激活就不得进入 `skipped`。
21. 因 Run 失败、取消或超时而未执行的节点进入 `canceled`，并记录明确原因。
22. Ready Node 以数据库为权威，只有通过 Scheduler 准入的 Attempt 才进入 Kafka。
23. 调度先按一秒 `ready_at` 时间桶 FIFO；同桶内以跨资源类 Project Load 和最近准入序号打散并发突发。
24. Project Load 定义为 `Reservation + Queued + Running`；Topic Occupancy 定义为 `Reservation + Queued`，Claim 只释放后者。
25. Redis 使用单逻辑同槽 Ready/Load/Topic/Reservation/Inflight 状态和 Lua 原子 Reserve；首版不使用固定 Lane、Credit 或每秒公平 Epoch。
26. Redis 故障时默认暂停新准入，从数据库 Ready、Queued、Running 重建新 Generation 后恢复。
27. Workflow Context 是不可变 Node Output 集合，不是共享可变 Map。
28. 第一阶段 Input/Output 使用有大小上限的 Inline JSON，持久化到 PostgreSQL 并缓存到 Redis；超限直接失败，Artifact Store 留作未来扩展。
29. 下游节点优先从 Redis 读取热输入，Cache Miss 回源权威存储。
30. Workflow/Node 状态先写数据库，再异步更新 Redis Run Read Model。
31. Engine 状态推进不能依赖 Redis Cache。
32. Kafka Task 只携带身份和定位信息，不携带完整 Workflow Context。
33. Control Plane 与 Worker Plane 可以独立水平扩展；第一阶段采用模块化 Control Plane 加独立 Worker Pool，不拆成大量微服务。
34. Engine 是无固定 Run 归属的事件驱动状态推进器；任一实例都可通过 Inbox、数据库状态和 CAS 安全接管。
35. 多 Scheduler 实例共享 Redis Candidate、Project Load、Topic Occupancy 与 Reservation 状态，并以数据库 CAS 作为 `ready → queued` 的最终裁决。
36. Kafka 是 TaskBus 和运行事件的传输实现，但普通 Consumer Group 与 Share Group 属于可替换的基础设施适配选择。
37. Task 在 Worker 本地执行槽可用且 Claim 事务成功后 ACK；执行完成通过独立 Completion Outbox/Event 链路返回。
38. Worker 不直连 Workflow 数据库，只通过 Attempt Coordinator 与 Execution Context 等内部接口工作。
39. `attempt_seq`、`retry_count`、`recovery_count` 分别表达物理执行序号、业务重试预算和基础设施恢复次数。
40. Node Type、Resource Class、Kafka Topic 和 Kafka Physical Partition 是四个不同概念，不能相互等同。
41. 第一阶段资源类为 `builtin` 与 `sandbox`；Builtin Pool 执行 HTTP/RPC，Sandbox Pool 执行 Code，并通过进程内 Executor Catalog 解析处理器，不使用中心化 Node Type `switch-case`。
42. 同一资源类的 Worker Pool 在第一阶段保持能力同构；Sandbox Worker 只编排每个 Attempt 的隔离运行环境，不在主进程内执行用户代码。
43. Kafka 按 Resource Class 设置逻辑 Topic；Topic 内使用多个 Physical Partition 扩展吞吐，不按 Node Type 或 Project 建 Topic。
44. Task Partition Key 使用 `attempt_id` 分散负载；任务顺序不作为执行正确性的前提。
45. 全局先按一秒 Ready 时间桶 FIFO；同桶内比较 Project Load/最近准入序号，Project 内再按 `priority DESC, ready_at ASC, node_run_id ASC` 派发。
46. 第一阶段 Control Node 固定为 Start、End、Branch，Task Node 固定为 Code、HTTP、RPC；暂不提供 SQL Node。
47. Start、End、Branch 由 Compiler/Engine 解释，不创建 Worker Task；Code、HTTP、RPC 才通过 Scheduler、Kafka 和 Worker 执行。
48. Code Node 只能在无网络、无数据库、无 Secret、受资源配额限制的沙箱中执行算法、数据处理、规则逻辑和批准的小模型推理。
49. HTTP Node 只允许使用 Project 有权访问的 `connection_ref + relative_path`，不接受任意完整 URL；认证 Secret 不进入 IR、DSL、Task 或日志。
50. RPC Node 只能调用 Service Catalog 中登记且授权的 `service_ref + operation`，不能充当任意地址和方法的 RPC 隧道。
51. Workflow 中节点的稳定身份是 IR `node.id`，在领域和 Runtime Error 中称 `logical_node_id`；IR 只暴露无版本号的 `node.type`，Executor Build Version 只记录在 Attempt 中用于审计。
52. Web 与 Agent 只消费无版本号的 Node Description；节点契约版本、Catalog Revision 和 DSL Operation Version 是平台内部机制。
53. Draft Revision 内部绑定 `catalog_revision`；已有 Draft 不静默升级 Node，升级必须产生新 Draft Revision；新建 Node 使用当前 Node Description。
54. Published Version 固定 `execution_snapshot_id`；Snapshot 固定 IR、DSL、Source Map、Compiler Version 和 Catalog Revision，后续 Node Description 更新不得改变旧版本执行语义。
55. IR 使用扁平 JSON；Node 统一包含 `id/type/title/inputs/outputs`，不包含 `params` 或用户可见 Node Version。
56. Input 使用列表，每项包含 `name/data_type/source`；Literal 使用 `value`，Ref 使用 `ref_node/ref_output`。
57. Output 使用 `name/data_type` 列表；同一 Node 内 Input Name 和 Output Name 分别唯一。
58. Control Edge 使用稳定语义 ID，结构为 `id/source/target/route?`，不使用 Source/Target Port；`route` 只用于 Branch 出边。
59. Layout 属于 IR 并参与 Draft 变化判断，但不编译进 DSL。
60. 第一阶段 Control Graph 是单 Start、单 End 的 DAG；所有 Node 必须从 Start 可达并能到达 End。
61. Branch 是带 Default Route 的排他分支，每次只能选择一个 Route；普通 Node 的多出边表示并行激活。
62. 多入边 Node 采用隐式 OR-Join，等待全部入边结算后至多激活一次，不新增 Join Node。
63. 第一阶段不合并排他分支结果；End 只能引用在其所有可能激活路径上必然产生的数据。
64. 第一阶段 `data_type` 只支持 `string/integer/number/boolean/object/array`；除 `integer → number` 外不做隐式类型转换，Ref 只能引用完整命名 Output。
65. Runtime 必须校验 Worker 的真实 Output 顶层类型；不匹配时以 `OUTPUT_TYPE_MISMATCH` 失败并定位到 IR Output。
66. 第一阶段 Retry、Timeout 使用 Catalog 默认值与 Project Policy，并在编译时固化进 DSL，不进入 IR，也不允许作者覆盖。
67. 第一阶段 Workflow 根输入和根输出固定为 JSON Object；Start 输出 `workflow_input`，End 接收必填 `workflow_output`。
68. Branch 通过单一显式 `value` Input 操作六种顶层类型，Case 按顺序匹配有限 Operator；`number` 使用 Decimal 比较，非法路径或类型令 Branch 失败。
69. Code Node 永远只支持 Python，系统将命名数据 Input 打包为一个 JSON Object，并要求 `main(inputs)` 返回与命名 Output 声明完全一致的 JSON Object；沙箱规格固定且不可由作者覆盖。
70. HTTP Node 只通过 Literal `connection_ref` 加 `relative_path` 调用 JSON API；认证由 Connection 注入，默认只接受 `2xx`，唯一 Output 是包含状态码、响应头和 Body 的 `response: object`。
71. RPC Node 对作者固定表达为 Literal `service_ref + operation`、Object `request` 和 Object `response`；协议、认证和内部 Operation Revision 由平台解析并固化进 DSL，非幂等且结果不确定的调用不得盲目 Recovery。
72. DSL 是 Compiler 生成的自包含不可变运行产物，使用独立且确定性生成的 Execution ID，不携带 IR Logical ID；Compiler 可以将 IR Input 重组为 Operation Config 与 Runtime Input，并固化 Operation Version 和执行策略。
73. Source Map 使用 Key-Value Map 保存 Execution Node/Edge 到 IR Node/Edge 的映射，并按 Execution Node 保存 `DSL Relative Field → IR Relative Field`；Field 缺失时回退到 Node，Source Map 不进入 Kafka Task。
74. Draft Test 与 Publish 使用同一条确定性 Compiler 流水线；第一阶段不做节点融合、删除或重排，保持 IR Node 与 Execution Node 一对一。
75. DSL Operation 固定为 `control.start/end/branch@1` 与 `task.python/http/rpc@1`；Runtime 在 Run 开始前检查全部 Operation Version，旧 Published DSL 不自动重新编译。
76. 受管资源在 Publish 时解析为稳定内部 ID；Secret、动态地址和凭证不进入 DSL，Runtime 仍可解析 Connection、Service Discovery 和身份信息。
77. Execution Snapshot 保存 `ir_hash/dsl_hash/source_map_hash/definition_hash`；Full IR Hash 包含 Layout，因此只改变布局时 DSL Hash 不变而 Definition Hash 改变。
78. Compiler Validation 返回有上限且稳定排序的结构化错误列表；错误使用 IR Node、Edge 和 Relative Field 定位。
79. CreateRun 使用 Idempotency Key；Engine 通过数据库锁/CAS 和 Inbox 处理唤醒事件，事件仅用于通知，数据库状态始终是权威。
80. Start/End/Branch 具有 Node Run 但没有 Attempt；Branch 持久化 `selected_route`，End Output 与 Run succeeded 同事务提交。
81. `retry_wait → ready` 由 Engine Timer 负责，Scheduler 永远只处理已经 `ready` 的 Task Node。
82. Cancel、Failure、Timeout 通过首次写入即胜出的终止意图串行化；后台 Timer/Reaper/Reconciler 只补发信号，不绕过 Engine 状态机。
83. 每次成功保存 Draft 都创建不可变 Draft Revision，并以乐观锁原子更新 Current Draft Pointer；不得原地覆盖历史 Revision。
84. Definition 与 Runtime 使用独立关系表；`workflow_runs` 不使用 `version_id/draft_revision` 多态外键读取定义。
85. Node Output 与 Node Run 分表，只有 `node_runs.effective_attempt_id` 指向的 Attempt Output 才能被下游读取。
86. Definition 与 Runtime 主表都携带 `project_id`；未来分别按 `project_id + workflow_id` 和 `project_id + run_id` 路由分片。
87. Outbox 必须与对应业务状态位于同一数据库分片和事务；Redis 与 Kafka 不创建权威定义或运行事实。
88. CreateRun 事务只创建 Pending Run 与 RunCreated Outbox；Engine 在独立事务中初始化完整 Node Run 集合，不暴露半初始化 Running Run。
89. Outbox 只发送轻量唤醒与定位信息，消费者重新读取数据库；Inbox 以 `consumer_name + event_id` 去重。
90. Execution Snapshot 被 Published Version 或 Run 引用后第一阶段禁止物理删除；未来分库时由 Definition Service 保证逻辑引用。
91. 平台机器身份统一使用应用侧 UUIDv7；作用域序号继续使用单调整数，IR Logical ID 不受该规则影响。
92. 所有租户关系携带 `project_id` 并使用复合约束；普通 Repository/API 查询不得只按实体 ID 访问租户数据。
93. 第一阶段只建立 Ready、Retry、Lease Recovery、Run、Outbox 和 Inbox 的确定访问路径索引，不建立通用 JSONB GIN 索引。
94. 第一阶段不启用 PostgreSQL Table Partition；未来优先按 Project 分库，时间分区仅在单库历史数据压力明确后评估。
95. Redis 在逻辑上拆分 Scheduling Store 与 Cache Store，生产环境使用不同 Endpoint；这不要求第一阶段直接建设 Redis Cluster。
96. Execution Context Cache 第一阶段使用一个 Run 一个 Redis Hash，只缓存已接受的 Effective Output；单 Run 分段留作出现实际热点后的扩展。
97. Redis 只冻结数据生命周期，不固定具体 TTL 秒数；Redis TTL 不得承担 Retry、Timeout、Deadline 或 Lost 等业务计时语义。
98. Kafka 承担持久事件，Redis Pub/Sub 只做可丢失的 Web 瞬时通知；第一阶段不使用 Redis Streams。
99. Workflow 核心权威数据禁止 Redis Write-Behind；Effective Output 先提交 PostgreSQL，再以 Best-Effort 方式预热 Redis，Miss 时回源。
100. Redis 缓存写入失败不得回滚 Node Success 或阻塞 Workflow 推进；运行进度、日志尾部、Presence 和非精确监控等有损数据可以 Redis Only 或批量聚合。
101. 第一阶段不建设通用 Redis Write-Behind Framework；需要可靠异步持久化的数据优先使用 Kafka。
102. 第一阶段 Kafka 只设置 Builtin Task、Sandbox Task 和 Runtime Event 三个逻辑 Topic，不设置 Definition Event Topic。
103. Draft Save/Publish 不写无消费者的 Definition Outbox；Publish Audit 与 Snapshot、Version、Active Pointer 在同一 PostgreSQL 事务中持久化。
104. 第一阶段 Kafka 使用普通 Consumer Group；Share Group 仅保留在 TaskBus Adapter 的未来替换能力中。
105. Kafka Message 使用带 `message_version` 的独立 JSON DTO；Task/Runtime Event 分别以 `attempt_id/run_id` 分区，不携带完整 DSL、Context、Output 或 Secret。
106. 新项目正式命名为 `EvalFrog`，仓库名和 CLI 命令统一使用小写 `evalfrog`；项目独立建仓，不以 smart-workflow 代码库为改造基础。
107. 第一阶段只有四类后端可执行程序：`evalfrog` CLI、`evalfrog-control-plane`、`evalfrog-worker-builtin` 和 `evalfrog-worker-sandbox`；Human Web 作为独立前端构建产物。
108. Control Plane 采用模块化单体：同一代码库和部署单元内保持明确模块接口与状态所有权，同时允许无状态多副本；后续拆分部署不得改变领域边界。
109. Control Plane 按 Access/Resources、Definition/IR/Catalog/Compiler、Runtime/Engine/Attempt/Context、Scheduling、Eventing/Recovery/Projection 划分逻辑模块，不使用横向 `controller/service/dao` 大包混装领域逻辑。
110. Execution Context Gateway 是 Runtime 内部的显式只读边界，统一为 Worker 装配不可变 Operation、Run Input、Effective Output 和受 Resource Class 限制的资源信息，并封装 Cache-Aside 与 PostgreSQL 回源。
111. 第一阶段 External API 与 Worker API 均使用版本化 HTTP/JSON；Kafka 继续使用独立、版本化的 JSON Message DTO。传输方式是 Adapter，不进入领域状态机。
112. Worker API 至少包含 Claim、Heartbeat、Complete 与 LoadExecutionContext；Worker 不因同进程部署、缓存命中或性能优化而获得 PostgreSQL 访问权。
113. 代码依赖固定从 Interface/Transport Adapter 指向 Application Module，再指向 Domain Model/Port；PostgreSQL、Redis、Kafka、Sandbox Adapter 反向实现 Port，领域模块不得导入基础设施实现。
114. 普通 Task Node 的扩展路径为 Node Catalog Contract + Compiler Handler + Executor + Routing Policy，不修改 Engine 或 Scheduler；Control Node 扩展才允许修改 Compiler 与 Engine。
115. M10 的 Human Web 与 Agent CLI 是同一个版本化 External API 的两个客户端；二者只能提交或读取 Authoring IR、Draft/Version 元数据和 Run Read Model，不能上传或依赖 DSL、Source Map、Execution Snapshot 或 Runtime 持久化实体。
116. Run Command（Draft Test、Production Create、Cancel）只返回最小 `run_id/purpose/state/created_at` DTO；客户端必须读取 Run Read Model 获取当前状态、Node 状态和经 Source Map 增强后的错误位置，避免把权威持久化结构变成公共契约。
117. Run Read Model 由 PostgreSQL Runtime 表和绑定的不可变 Source Map 投影生成；Cache Redis 只保存该投影的短生命周期副本。任何 Run/Node 状态提交后 Best-Effort 删除该缓存并发布 Redis Pub/Sub wake-up，失败不得回滚 PostgreSQL 事务。
118. Web 进度通知使用可丢失 SSE/Pub/Sub 唤醒且不承载状态；客户端首次订阅、每次收到 wake-up 和断线重连后均重新 GET Run Read Model，因此 Redis Pub/Sub 消息丢失不会改变正确性。
119. Run Cancel 只在 PostgreSQL 中记录 `cancel_requested_at` 并在同一事务写入 `RunCancelRequested` Outbox；Engine 仍是唯一推进 Run/Node 终态的所有者。取消在图初始化前到达时，Engine 可直接把 Pending Run 收敛为 Canceled。

## 17. 已确认的实现架构

### 17.1 项目与部署单元

项目名称为 `EvalFrog`，建议对外定位为：

```text
EvalFrog — CLI-first Enterprise Workflow Runtime
```

新项目独立建仓，不复用 smart-workflow 的包结构、数据库模型或运行时实现。旧项目仅作为问题样本和架构经验来源。

第一阶段部署形态：

```text
Human Web
evalfrog CLI
evalfrog-control-plane（模块化单体，可多副本）
evalfrog-worker-builtin（独立扩缩容）
evalfrog-worker-sandbox（独立扩缩容）
PostgreSQL / Scheduling Redis / Cache Redis / Kafka
```

Control Plane 使用同一套代码和一个镜像。默认可以启动全部内部角色；未来可通过进程 Role 只启用 API、Runtime Consumer、Scheduler、Relay/Recovery 或 Projection，但这只是部署选择，不形成新的领域模型或服务间协议。

### 17.2 代码模块边界

建议的顶层模块为：

| 模块 | 状态与职责所有权 |
|---|---|
| `access` | Principal、Project Permission、Project Execution Identity |
| `resources` | Connection、RPC Service、Secret Reference 元数据与授权 |
| `definition` | Workflow、Draft Revision、Published Version、Execution Snapshot |
| `ir` | IR 数据结构、解析、Canonicalize 和基础诊断 |
| `catalog` | Node Description、内部契约版本和能力描述 |
| `compiler` | IR 校验、DSL、Source Map、Compiler Manifest |
| `runtime` | Run、Node Run、Attempt 的领域模型和状态转换 |
| `runtime/engine` | 激活、Branch、Retry、终止意图与 Run 终态推进 |
| `runtime/attempt` | Claim、Heartbeat、Complete、Lease、Fencing、Output Candidate |
| `runtime/context` | Worker 只读 Execution Context 装配与 Cache-Aside |
| `scheduling` | 一秒时间桶 FIFO、Project Load、Topic Queue Window 与 Reservation |
| `eventing` | Outbox/Inbox、Kafka Message DTO 与 Relay/Consumer 基础设施 |
| `recovery` | Retry Timer、Deadline Scanner、Attempt Reaper、Reconciler |
| `projection` | Run Read Model 与 Web 瞬时通知 |
| `worker` | 通用 Worker Runtime、Executor SPI 与本地 Backpressure |

这些是代码边界，不要求第一阶段逐个拆成微服务。模块间优先使用进程内 Port；跨进程边界只存在 External API、Worker API 和 Kafka Message Contract。

### 17.3 Execution Context Gateway

Worker 通过以下逻辑操作获取执行材料：

```text
LoadExecutionContext(attempt_id, fencing_identity)
→ immutable operation
→ resolved execution policy
→ Run Input
→ accepted upstream Effective Outputs
→ resource-class-scoped connection/service material
```

Execution Context Gateway：

- 只读，不推进 Run、Node Run 或 Attempt 状态；
- 先读 Cache Redis，Miss 时回源 PostgreSQL 并回填；
- 只读取 `effective_attempt_id` 对应 Output；
- 对 Builtin 与 Sandbox Resource Class 返回不同权限范围；
- 不向 Code Sandbox 暴露 Network、Database 或 Secret；
- 不把完整 Context 放入 Kafka Task。

### 17.4 接口与依赖方向

第一阶段 External API 与 Worker API 使用版本化 HTTP/JSON，Kafka Message 使用版本化 JSON DTO。领域代码只依赖 Transport-neutral Port，因此未来增加 gRPC Adapter 不改变状态模型。

代码依赖遵守：

```text
HTTP / CLI / Kafka Adapter
          ↓
Application Module
          ↓
Domain Model + Port
          ↑
PostgreSQL / Redis / Kafka / Sandbox Adapter
```

禁止：

- API Handler 直接访问 Repository；
- Compiler 访问 PostgreSQL、Redis 或 Kafka；
- Runtime 读取 Draft、IR 或 Node Description 执行；
- Scheduler 解释 Branch、Retry 或 Run 成功条件；
- Worker 导入 Definition/Runtime Repository；
- Kafka/HTTP DTO 直接复用数据库实体；
- 使用全局 `service`、`common`、`utils` 包绕过模块所有权。

### 17.6 M3 Definition 生命周期实现落点

M3 已按本文冻结边界完成以下实现，不新增另一套生命周期语义：

- Draft 使用可变 Pointer 指向不可变 Revision，SaveDraft 通过期望 Revision 做 PostgreSQL 乐观并发控制；
- Draft 保存只要求有界 IR 外壳，Validate、Test Snapshot 与 Publish 使用 Draft 绑定的 Catalog Revision 和同一 Compiler Pipeline；
- Publish 在授权后优先查询已完成的 Idempotency Result，使客户端超时重放不依赖资源当前状态；并发首次请求仍在事务内用 Advisory Lock、Request Hash 与唯一约束收敛；
- Snapshot、Published Version、Active Pointer、Publish Audit 与 Idempotency Result 在一个 PostgreSQL 事务提交；任何注入失败都整体回滚；
- Published Version 不可变，已被 Version 引用的 Snapshot 由外键和 Trigger 禁止更新、删除；未引用的 Test Snapshot 可作为后续回收对象；
- Connection/RPC Service 同时校验作者 Permission 与 Project Execution Identity Grant，Compiler 只接收稳定 Resource Binding，不接收 Secret 或 Endpoint；
- 第一阶段没有 Definition Event Topic、Definition Outbox、Redis Definition 写路径或 DSL Upload；PostgreSQL 是 Definition 权威来源。

### 17.7 M4 Runtime Domain 与 Engine 实现落点

M4 已将本文第 8-13 节的运行语义实现为无基础设施依赖的领域模型和确定性 Engine，不改变已冻结状态所有权：

- Run、Node Run、Attempt 状态字段保持私有，只能通过显式领域操作和 State Version 推进；
- CreateRun 绑定 `snapshot_id + definition_hash + definition_source`，Production 只接受 Published Version；Engine 深拷贝并只解释 DSL，不读取 IR、Draft、Definition 或 Catalog；
- Start、End、Branch 具有 Node Run 但不创建 Attempt；所有 Control Input 结算后才执行隐式 OR-Join，一旦激活不得 Skipped；
- Branch 按顺序执行六种 JSON 顶层类型的冻结 Operator，使用十进制数值和递归 JSON 结构相等语义，路径/类型错误形成结构化 Runtime Failure；
- Attempt Coordinator 语义先记录 Attempt 终态与 Output Candidate，Engine 再独立处理 Completion；Task 成功结果通过 Current Attempt 与 DSL Output Contract 后才能设置唯一 Effective Attempt/Output；旧 Attempt、重复 Completion 和迟到 RetryDue 不得改变当前语义状态；
- 业务 Attempt 与 Recovery 独立计数，Retry Decision 固化 `next_retry_at`，提前或迟到的 RetryDue 均幂等；失败、取消、Workflow Deadline 竞争时首个 Termination Intent 胜出；
- Run Success 要求 End 激活、无 Termination Intent、全部非 End Node 为 Succeeded/Skipped，并把 End、Workflow Output、Run Succeeded 建模为一个不可分领域操作；Run 终止同样要求全部 Node Run 已结算；
- Runtime Failure 已携带 Run、Snapshot、Definition Hash、Execution Node/Edge、Attempt、Phase 和 DSL Field 坐标；IR 坐标继续由 Source Map 在接口层增强；
- M4 Harness 不是内存版生产 Repository，不模拟 Kafka/Scheduler/Worker；其用途是让 M5 PostgreSQL/CAS 实现复用已验证语义。

### 17.8 M11 Recovery、观测与人工介入边界

M11 将恢复统一定义为“基于 PostgreSQL 当前事实的 durable wake-up”，而不是第二个状态机。Retry Timer、Deadline Scanner、Attempt Reaper 和 Reconciler 都可以多副本运行：前者三个扫描权威的 `retry_wait`、`deadline_at`、Lease 事实，Reconciler 只发现遗漏的 `RunCreated`、Cancel、Completion 或 Lost 唤醒；它们只在一个 PostgreSQL 事务内重新确认条件、写 Runtime Outbox 与安全 Audit，绝不直接改写 Run、Node Run 或 Attempt 语义状态。Engine 仍通过 Inbox、行锁/CAS 和领域状态机成为唯一推进者。

时间裁决使用 PostgreSQL `clock_timestamp()`，绝不依赖 Kafka Event 的历史 `occurred_at` 或 Redis TTL。这样延迟/乱序的 `RunCreated` 不会在 Deadline 后初始化节点，延迟的 `RetryDue` 也不会复活过期 Run。若取消请求在 Deadline 之前已经持久化，则该取消意图获胜；若取消在 Deadline 之后才提交，则 Deadline 获胜。尚未初始化 Node Run 的 Pending Run 可以合法收敛为 `canceled` 或 `timed_out`，业务失败仍不得发生在任何节点执行之前。

`workflow_runs.trace_id` 是 Run 的持久化根关联 ID。创建、Task Outbox、Worker Completion、Reaper、Recovery Wakeup、Engine 消费与 Audit 都保留该 ID；调度器不得用自身临时 Trace 覆盖它。Metrics 只能使用有界的 `source/event_type/outcome/group/topic` 标签，`project_id/run_id/attempt_id/trace_id` 只能进入结构化日志或 Audit。日志和诊断明确排除 Workflow Input/Output、Secret、Lease Token 与 Executor stderr。

诊断是只读的 PostgreSQL 派生视图，返回安全 Run 摘要、Attempt 元数据和最多 100 条安全 Audit；它不进入普通 Run Projection Cache。人工 Replay 也不是任意 Kafka 注入：仅 Project Admin 可以请求系统重新检查一个受枚举约束、仍然 actionable 的 Run/Attempt 事实，系统仍会以 Outbox + Inbox/CAS 收敛。DLQ 是有毒消息的运维线索，不能被当作绕过数据库状态机的重放入口。

M11/M12 的告警原始事实为：两类未发布 Outbox 的最大年龄、按 Consumer Group/Topic 采样的 Kafka Lag、Lease Lost 次数、`ready → queued` 延迟、Topic Queue Window/Occupancy、Worker Completion EWMA、Scheduling Redis 重建结果，以及 Recovery Wakeup 结果。阈值由 Profile/SLO 运维配置决定，不写死为领域语义；Scheduling Redis 重建失败继续 Fail Closed，Cache Redis 丢失继续 Cache-Aside 回源。Kafka 的临时网络失联、`COORDINATOR_NOT_AVAILABLE`、`NOT_COORDINATOR` 以及需要 rejoin 的 `REBALANCE_IN_PROGRESS`/generation/member 信号属于 transport/group-coordination 边界：Kafka adapter 在同一 Consumer 生命周期内退避重试并重新 join group，不能让 Control Plane 或 Worker 因 Consumer Rebalance 退出；协议、认证、Topic 配置和 static member fencing 等不可重试错误仍必须暴露为进程故障。由于 Scheduling Redis 中的 Ready、Load、Topic、Reservation 与 Inflight 都是可重建协调状态，第一阶段部署不启用 AOF/RDB 持久化；持久化磁盘抖动不得反向破坏调度热路径，Redis 重启后的唯一正确路径仍是 PostgreSQL 重建。调度热路径使用有界 500ms Redis 操作窗口；Reserve 以调用方生成的 `attempt_id` 幂等，运输超时重试返回同一 Reservation，不得二次消费 Candidate、Project Load 或 Topic 空位。线上查询使用短 PostgreSQL `statement_timeout`，但 Migration 在单独获取的 Advisory Lock 连接和本地事务内显式关闭该语句超时；Migration Lock Timeout 仍约束等待其他迁移者的时间，避免 Schema DDL 因短在线查询时限而中途失败。
