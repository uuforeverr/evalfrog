# 节点模型与执行能力边界

> 状态：已冻结的架构决策基线
>
> 范围：第一阶段 Node Type、权限边界、Worker 路由和版本演进
>
> 前置基线：[00_核心架构决策基线.md](./00_核心架构决策基线.md)、[01_分布式调度与Worker执行边界.md](./01_分布式调度与Worker执行边界.md)

## 1. 设计目标

第一阶段不建设功能全面的节点生态，只提供完成核心闭环所需的最小节点集合。扩展能力来自稳定的通用节点外壳、版本化类型契约和 Executor 边界，不来自给单个通用节点授予所有权限。

核心原则是：

```text
高风险能力必须显式建模为专用 Node Type
通用 Code Node 必须保持低权限
```

## 2. 第一阶段节点集合

```text
Control Node
├─ start
├─ end
└─ branch

Task Node
├─ code
├─ http
└─ rpc
```

第一阶段不提供 SQL Node。未来如果需要数据库访问，应新增具有数据源授权、SQL 校验和审计能力的专用节点或 Data Access Service，不能通过扩大 Code Node 权限实现。

### 2.1 Control Node

Start、End、Branch 由 Compiler 和 Engine 解释，不创建 Node Attempt，不进入 Kafka，也不分配给 Worker。

- Start：将 Run Input 引入执行图；
- End：形成 Workflow Output 并参与 Run 结束判断；
- Branch：使用受限且确定性的条件表达式选择 Active Control Path。

Branch 不执行任意用户代码。新建一种控制流语义仍可能要求 Compiler 和 Engine 升级，因此 Control Node 属于受控扩展。

第一阶段 Workflow 根输入和根输出都固定为 JSON Object。Branch 通过一个显式 `value` Input 操作六种顶层类型，并使用按类型限制的确定性 Operator；其完整契约见 Control Graph 基线。

### 2.2 Task Node

Code、HTTP、RPC 产生 Node Attempt，并经过统一执行链路：

```text
ready
→ Engine 创建 Attempt 与 Task Outbox
→ queued Attempt + NodeTask Outbox
→ Kafka
→ Worker
→ Executor
→ Attempt Coordinator
→ Completion Event
→ Engine
```

新增普通 Task Node 不应修改 Engine 中央拓扑算法。平台需要在内部 Node Catalog 中增加版本化契约、Compiler Handler、Executor 和 Runtime Routing Policy；Web 与 Agent 只消费不暴露内部版本号的 Node Description。

## 3. 能力与权限矩阵

| Node Type | Executor | Resource Class | 允许能力 | 默认禁止 |
|---|---|---|---|---|
| Code | CodeExecutor | `sandbox` | 算法、数据转换、规则、小模型本地推理 | 网络、数据库、Secret、宿主机访问 |
| HTTP | HttpExecutor | `builtin` | 访问已授权 HTTP Connection | 任意完整 URL、未授权内网、任意 Secret |
| RPC | RpcExecutor | `builtin` | 调用已登记且授权的 Service Operation | 任意地址、端口和未登记方法 |

能力边界由平台执行策略强制实施，不能只依赖用户提交的 IR 配置。

## 4. Code Node 沙箱

### 4.1 允许场景

Code Node 用于：

- 简单算法；
- JSON、文本、表格等数据处理；
- 确定性或近似确定性的规则逻辑；
- 使用平台批准模型的轻量本地推理；
- 产生结构化 Output 或受控 Artifact。

### 4.2 默认禁止能力

Code Node 不得：

- 访问数据库或取得数据库凭证；
- 发起 HTTP、RPC 或其他网络连接；
- 读取 Secret；
- 访问宿主机文件系统；
- 启动未授权子进程；
- 在运行时安装或下载任意依赖；
- 将修改持久化到共享运行环境。

### 4.3 强制资源边界

每个 Code Attempt 在隔离环境中执行，并由平台强制限制：

```text
CPU
Memory
Execution Timeout
Temporary Disk
Process Count
Output Size
Package Allowlist
Network = Deny
Secret Access = Deny
```

第一阶段只有一套固定沙箱规格。CPU、内存、执行时间、临时磁盘、进程数和输出大小都由平台规定，Human 和 Agent 不能在 IR 中申请或覆盖；超限直接产生结构化失败。

Sandbox Worker 主进程只创建、监控、取消和销毁隔离环境，不直接加载用户代码，也不把自身凭证或网络权限传入沙箱。

### 4.4 Python 输入输出契约

Code Node 永远只支持 Python，因此 IR 不包含 `language`。`source_code` 是保留 Input，必须是 Literal String；其他数据 Input 可以是 Literal 或 Ref。执行前系统按 Input Name 将所有数据 Input 打包成一个 JSON Object，但不把 `source_code` 放入该对象。

固定入口为：

```python
def main(inputs):
    return {
        "output_name": output_value
    }
```

返回值必须是一个 JSON Object，其顶层字段与 IR `outputs` 的命名声明完全一致。Code 可以声明多个 Output；每个返回字段分别执行顶层类型校验，使下游可以直接按 Output Name 引用，而不需要嵌套字段 Ref。

Draft Test 和 Publish 必须检查 Python 语法、`main(inputs)` 入口、源码大小和显式禁止的 Import。Runtime 必须检查返回值及固定资源限制。结构化错误至少包括：

```text
CODE_SYNTAX_ERROR
CODE_ENTRYPOINT_INVALID
CODE_IMPORT_FORBIDDEN
CODE_RUNTIME_ERROR
CODE_OUTPUT_NOT_OBJECT
CODE_OUTPUT_MISSING
CODE_OUTPUT_UNDECLARED
OUTPUT_TYPE_MISMATCH
SANDBOX_CPU_LIMIT_EXCEEDED
SANDBOX_MEMORY_LIMIT_EXCEEDED
SANDBOX_EXECUTION_TIMEOUT
SANDBOX_OUTPUT_TOO_LARGE
```

源码错误必须定位到 `/nodes/{node_id}/inputs/source_code`，并尽可能携带 `source_line` 和 `source_column`。语法、业务代码异常、输出契约错误和资源超限不可业务重试；Worker Lost 等基础设施故障仍按 Recovery 处理。

### 4.5 小模型推理

第一阶段只允许引用平台批准的 `model_ref`：

```text
Approved Model Artifact
→ 以只读方式注入沙箱
→ 本地推理
```

Code 不得在运行时从网络下载模型。GPU 或大型模型推理未来可以使用新的 Resource Class 或专用 Node Type，不改变 Code Node 的基础安全语义。

### 4.6 M9 实现与部署不变量

M9 以 `Sandbox Orchestrator` Port 隔离 CodeExecutor 与 OCI 运行时：Sandbox Worker 只传递源码和已解析的 JSON 输入，不导入或执行用户 Python。Worker 使用受限的私有 HTTP Controller Client；只有独立的 Sandbox Runtime Controller 可以拥有 OCI/Docker 凭据，并为每个 Attempt 创建具标签的短生命周期容器，在完成、取消或超时后强制清理和扫除遗留容器。

固定 `python-sandbox-v1` 资源规格为 `0.50 CPU / 128 MiB Memory / 32 PIDs / 16 MiB tmpfs / 1 MiB protocol output`。容器始终使用 `--network none`、只读根文件系统、`no-new-privileges`、Capability Drop、无 Host Mount、非 root 用户和固定 Python 3.12 digest 镜像。执行环境重做入口与 Import 白名单校验；Go 侧发布校验只做确定性语法、入口和显式 Import 预检，不能被误认为安全边界。

普通 Docker `runc` 仅用于本地与 CI 的协议验证；`production-default` 强制 `runsc` 和 digest-pinned 镜像。普通业务 Worker 不得挂载 Docker root socket：本地 Compose 的唯一 socket 使用者是独立 Controller 服务，生产环境则部署在专用的 hardened sandbox node。Worker→Controller 使用私有 HTTPS 和 Secret-Manager 注入的服务令牌；如部署平台要求，mTLS 由该网络边界或其 sidecar 实施。容器启动失败只报告无敏感信息的 `SANDBOX_RUNTIME_UNAVAILABLE`；stderr、源码、输入和宿主凭据均不进入 Runtime Error、Kafka 或遥测。

`AttemptResult.dsl_field` 允许 Executor 报告 `operation.config.source_code`，Control Plane 再用 Source Map 定位 IR 的 `inputs.source_code`。可安全披露的 `source_line/source_column` 被保存在结构化错误详情；运行时错误不会回传源码或输入内容。

目前 DSL 的 `model_artifact` 表达仍保持不变，但由于尚未建设授权、校验和只读注入的 Artifact Runtime Port，M9 对其明确返回 `MODEL_ARTIFACT_UNAVAILABLE`。在该 Port 完成前，不允许临时 Host Mount 或网络下载来伪造“小模型推理”。

## 5. HTTP Node

### 5.1 地址模型

HTTP Node 第一阶段只支持：

```text
connection_ref + relative_path
```

不接受任意完整 URL，也不允许通过相对路径、重定向或编码绕过 Connection 的 Origin 和网络策略。

概念 IR Node：

```json
{
  "id": "create_order",
  "type": "http",
  "title": "创建订单",
  "inputs": [
    { "name": "connection_ref", "data_type": "string", "source": "literal", "value": "customer_api" },
    { "name": "method", "data_type": "string", "source": "literal", "value": "POST" },
    { "name": "relative_path", "data_type": "string", "source": "literal", "value": "/v1/orders" },
    { "name": "body", "data_type": "object", "source": "ref", "ref_node": "build_order", "ref_output": "result" }
  ],
  "outputs": [
    { "name": "response", "data_type": "object" }
  ]
}
```

Connection 是 Project 范围内受管理且可授权的资源，至少包含：

- 固定 Base URL 与允许的网络范围；
- 认证策略和 Secret Reference；
- 允许的 Project、HTTP Method 或路径范围；
- TLS、代理和重定向策略；
- 请求与响应大小上限。

Publish 时校验调用者是否有权引用 Connection；Runtime 使用 Project Execution Identity 再次解析和授权。Secret 明文不进入 IR、DSL、Kafka Task、Execution Context 或普通日志。

### 5.2 Input/Output 契约

第一阶段 HTTP Node 只作为 JSON API Client：

| Input | 必填 | 允许来源 | 约束 |
|---|---:|---|---|
| `connection_ref` | 是 | Literal | Project 内已授权 Connection |
| `method` | 是 | Literal | `GET/POST/PUT/PATCH/DELETE` |
| `relative_path` | 是 | Literal/Ref | 以 `/` 开头，不含 Scheme、Host、Fragment 或 Query |
| `query` | 否 | Literal/Ref | Object，由 Executor 统一编码 |
| `headers` | 否 | Literal/Ref | Object，不得覆盖受保护 Header |
| `body` | 否 | Literal/Ref | 六种非 Null JSON 顶层类型之一 |
| `accepted_statuses` | 否 | Literal | Integer Array，缺省为全部 `2xx` |

第一阶段不支持文件上传、Form、Streaming 或任意二进制 Request/Response。认证信息由 Connection 注入，`connection_ref` 不允许动态 Ref。

唯一 Output 固定为 `response: object`：

```json
{
  "status_code": 201,
  "headers": { "Content-Type": "application/json" },
  "body": { "order_id": "O-1001" }
}
```

空 Body 使用嵌套 `null`。命中 `accepted_statuses` 时 Node succeeded；否则以 `HTTP_STATUS_ERROR` 失败，并只保存经过脱敏和截断的响应摘要。

### 5.3 安全边界

HttpExecutor 必须防止：

- SSRF；
- 访问 Loopback、云 Metadata 和未授权私网；
- DNS Rebinding；
- 重定向逃逸 Connection Origin；
- 超大请求或响应；
- Secret 泄漏到错误信息和 Trace。

结构化错误至少包括：

```text
HTTP_CONNECTION_NOT_FOUND
HTTP_CONNECTION_FORBIDDEN
HTTP_METHOD_NOT_ALLOWED
HTTP_INVALID_RELATIVE_PATH
HTTP_PROTECTED_HEADER
HTTP_REQUEST_INVALID
HTTP_NETWORK_ERROR
HTTP_TIMEOUT
HTTP_STATUS_ERROR
HTTP_RESPONSE_TOO_LARGE
HTTP_RESPONSE_INVALID_JSON
HTTP_REDIRECT_FORBIDDEN
```

### 5.4 重试边界

HTTP Retry 仍由 Engine 根据编译进 DSL 的 Node Retry Policy 决定。第一阶段该策略来自 Node Catalog 默认值和 Project Policy，不由作者在 IR 中覆盖。GET 等幂等操作可以按策略重试；具有副作用的请求只有在目标支持稳定 Idempotency Key 或契约明确允许时才可自动重试。

## 6. RPC Node

RPC Node 只调用平台 Service Catalog 中登记的服务和操作：

```text
service_ref + operation
```

它不是允许用户输入任意地址、端口和方法的通用 RPC 隧道。

Service Catalog 至少描述：

```text
service_ref
operation
request_schema
response_schema
protocol
service discovery
authentication policy
allowed projects
idempotency capability
```

RpcExecutor 负责服务发现、序列化、短期身份注入、Deadline 和 Trace Context 传播、响应反序列化及结构化错误转换。具体采用 gRPC、Dubbo 或其他协议属于 Executor 实现选择，不进入 IR 通用结构。

### 6.1 Input/Output 契约

```json
{
  "id": "create_invoice",
  "type": "rpc",
  "title": "创建发票",
  "inputs": [
    { "name": "service_ref", "data_type": "string", "source": "literal", "value": "invoice_service" },
    { "name": "operation", "data_type": "string", "source": "literal", "value": "CreateInvoice" },
    { "name": "request", "data_type": "object", "source": "ref", "ref_node": "build_invoice", "ref_output": "invoice" }
  ],
  "outputs": [
    { "name": "response", "data_type": "object" }
  ]
}
```

- `service_ref`、`operation` 必填且只能是 Literal；
- `request` 必填、固定为 Object，允许 Literal/Ref；无参数操作使用 `{}`；
- 唯一 Output 固定为 `response: object`；空响应使用 `{}`；
- 作者不能设置地址、端口、协议、认证信息或任意 RPC Metadata；
- RPC 非成功状态令 Node failed；需要 Workflow 判断的业务结果必须建模为正常 Response 字段。

Web 和 Agent 可以读取无版本号的 Service Operation Description，包括自然语言说明、Request/Response Schema 和示例。Publish 将 `service_ref + operation` 解析为内部 Operation Revision 并固化到 DSL。Literal Request 在 Publish 时执行完整 Schema 校验；Ref Request 在 Publish 时校验顶层 Object，Runtime 调用前再执行完整 Schema 校验。Response 始终在 Runtime 按 Service Schema 校验。

### 6.2 Error 与重试

```text
RPC_SERVICE_NOT_FOUND
RPC_OPERATION_NOT_FOUND
RPC_FORBIDDEN
RPC_REQUEST_SCHEMA_MISMATCH
RPC_SERVICE_DISCOVERY_ERROR
RPC_AUTHENTICATION_ERROR
RPC_TRANSPORT_ERROR
RPC_DEADLINE_EXCEEDED
RPC_REMOTE_ERROR
RPC_RESPONSE_SCHEMA_MISMATCH
RPC_OUTCOME_UNKNOWN
```

内部 Service Operation Description 必须声明幂等能力。幂等操作可以按平台策略重试；非幂等操作不得业务重试。发生 Worker Lost 等结果不确定的基础设施故障时，只有服务支持稳定调用幂等键或服务端去重才允许 Recovery；否则以 `RPC_OUTCOME_UNKNOWN` 失败，不能盲目重复调用。

## 7. Worker Pool 与 Kafka 路由

```text
Builtin Task Topic
→ Builtin Worker Pool
   ├─ HttpExecutor
   └─ RpcExecutor

Sandbox Task Topic
→ Sandbox Worker Pool
   └─ CodeExecutor
      → Sandbox Runtime
```

HTTP 和 RPC 是不同 Node Type，但共享相同信任和资源边界，因此由同一个 Builtin Worker Pool 执行。Code 使用独立 Sandbox Worker Pool。

Topic 按 Resource Class 划分，不按 Node Type 划分；每个 Topic 可以拥有多个 Physical Partition。IR/DSL 不包含 Topic 名称，Runtime Routing Policy 负责从 Operation 能力解析 `resource_class` 和实际 Topic。

## 8. 节点身份与版本坐标

Workflow 中节点的稳定身份是 IR 的 `node.id`。作者可见的表达与平台内部版本坐标必须分开：

| 坐标 | 可见范围 | 作用 |
|---|---|---|
| `node.id` | IR / Web / Agent | Workflow 内具体节点的稳定身份 |
| `node.type` | IR / Web / Agent | 不带版本号的业务类型，如 `http` |
| `ir_version` | IR / Web / Agent | 整个 IR 通用格式版本 |
| `catalog_revision` | Draft 外层记录 / 平台内部 | 该 Draft 校验和编译时采用的节点契约集合 |
| `dsl_version` | DSL / Runtime | 整个 DSL 通用格式版本 |
| `operation_version` | DSL / Runtime | Runtime Operation 的不可变语义版本 |

Agent 和 Web 不读取、选择或提交节点契约版本号。Executor 的实际构建版本也不是 Workflow 定义身份。每次 Attempt 记录：

```text
executor_name
executor_build_version
sandbox_runtime_version（适用时）
```

这些字段用于审计、问题定位和回归分析；兼容实现的升级不要求重新发布所有 Workflow。

## 9. Node Description 与内部 Catalog

第一阶段不建设独立 Node Manifest/Registry 服务。平台向 Web 和 Agent 发布不带版本号的 Node Description：

```text
NodeDescription
├─ type
├─ natural_language_description
├─ allowed_inputs
├─ outputs
└─ examples
```

Node Description 不是 IR，而是帮助作者选择节点、生成统一 IR Node 并获得字段约束的说明书。Web 用它渲染和校验画布；CLI/Agent 用它生成和快速校验 IR；服务端始终执行最终权威校验。

第一阶段 `data_type` 固定为 `string/integer/number/boolean/object/array`。Node Description 为每个 Input 声明允许类型、必填性、允许的 `literal/ref` 来源及枚举或范围约束，并声明固定 Output 或作者可选的 Output 类型。IR 不内嵌完整 JSON Schema。

M1 的公共 Node Description 具体包含 `type/kind/natural_language_description/allowed_inputs/additional_inputs?/outputs/examples`。Branch 的六类 Operator Matrix、First-Match-Wins 和简单字段 Path 规则作为 `cases` Input 的结构化约束发布，不能只埋在自然语言说明中。公共描述不包含 Catalog Revision、Node Contract Revision、Operation Version、Worker、Kafka、Lease、Retry 或 Timeout。

平台内部 Node Catalog 对节点契约进行版本化，并关联 Compiler Handler、运行时 Operation 版本和执行策略。Draft 外层记录其 `catalog_revision`，但具体版本号不进入作者提交的 IR。Compiler 和 Worker 可以分别使用进程内 Handler Map 与 Executor Map；Catalog 在第一阶段不是必须独立部署的数据库或远程服务。

第一份内置 Catalog 使用内部坐标 `catalog-v1`，Start、End、Branch、Code、HTTP、RPC 各自从不可变 Contract Revision 1 开始。Catalog 通过 Node Type 到 Contract 的注册表分派通用约束与节点专用校验；新增普通 Task Node 增加注册项，不修改 IR Validator 的中心 `switch-case`。对 Web/CLI 返回的 Description 使用防御性副本，调用方不能修改进程内权威契约。

## 10. 演进不变量

IR Node 使用稳定的通用外壳：

```text
id
type
title
inputs
outputs
```

未来新增普通 Task Node 时：

- 不修改 IR 通用外壳；
- 不修改 Engine 中央拓扑算法；
- 新增内部 Node Catalog 契约与对外 Node Description；
- 新增 Compiler Handler；
- 新增或复用 Executor；
- 更新 Runtime Routing Policy。

版本演进必须满足：

1. 修改 IR 通用结构才升级 `ir_version`，增加 Node Type 不自动升级 IR Version。
2. 节点 Input/Output 契约出现不兼容变化时，在内部 Node Catalog 中创建新契约版本；不得要求 Agent 或 Web 指定版本号。
3. Runtime Operation 语义出现不兼容变化时升级 `operation_version`。
4. 旧 Schema、Compiler Handler 和 Runtime Operation Handler 不得被新语义原地覆盖。
5. Published Version 保存不可变 IR、DSL、Source Map 和 Compiler Version，且不自动重新编译。
6. Copy 旧 Published Version 时，以其不可变 IR 创建 Draft，并依据当前 Catalog 显式校验或迁移；原 Published Version 保持不变。
7. Executor 可以修复实现，但不得改变既有 Operation Version 的可观察语义。

## M8 实现补充：Managed Resource Runtime

M8 将本决策中的资源边界落到运行时 Port：Worker 通过 Worker API 携带 Attempt Lease/Fencing 请求 Connection 或 Service Operation 的运行时材料；Control Plane 重新校验 Project Execution Identity、Grant、Contract Revision 和资源启用状态，并记录 Attempt Resource Revision。Execution Context 仍只含非敏感操作与输入，不含 Secret。

Builtin Worker 提供 HttpExecutor 与 RpcExecutor。HTTP 只接受受管 Connection 的相对路径，并强制 Origin、方法、路径前缀、大小、Protected Header、重定向和 JSON 响应约束；RPC 第一阶段使用受限 `http-json` Service Discovery 适配，协议细节不进入 IR/DSL。两个 Executor 都使用稳定 `run_id:execution_node_id` 幂等键；Secret 仅在最后一跳由 Secret Resolver Port 注入。
