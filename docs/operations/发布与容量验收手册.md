# 发布、容量与安全验收手册

> 适用范围：EvalFrog 第一阶段 M12 发布候选。本文是可执行的验收清单，不是
> 对生产吞吐量的预先承诺；只有附带硬件、Profile 和原始指标的实测报告才能
> 声称 `tasks/min`。

## 1. 发布状态与责任边界

发布候选必须先通过 M0-M11 的 CI，再完成本手册的安全、恢复、容量和最终
E2E 检查。任一项尚未测量、基础设施未按清单配置或出现 P0/P1 问题时，状态
只能是 **Release Candidate**，不能标记 **Production Ready**。

PostgreSQL 是 Run、Attempt、Output、Outbox 与 Inbox 的权威来源；Kafka 只
负责至少一次投递；Scheduling Redis 是可从数据库重建的协调状态；Cache
Redis 是 Cache-Aside 读取缓存。备份、回放和回滚都不得绕过该分工，尤其不得
手工修改 Run/Node/Attempt 状态或把 Redis 当作待回写的权威数据。

## 2. 环境部署清单

| 项目 | `local` | `test` | `production-default` |
|---|---|---|---|
| PostgreSQL | 单实例，应用 Pool `1/5` | 独立实例/Schema，Pool `2/10` | 高可用 PostgreSQL，单 Control Plane Pool `5/20`，所有实例 Pool Max 总和不超过 `max_connections` 的 70% |
| Kafka | 1 partition / topic，RF 1 | Task 3、Runtime 6 partitions，RF 1 | Builtin/Sandbox 各 12、Runtime 24 partitions，RF 3、Min ISR 2、禁止自动建 Topic |
| Scheduling Redis | 独立 Endpoint、`maxmemory=256mb`、`noeviction` | 独立 Endpoint、显式 `maxmemory`/水位 | 独立高可用 Endpoint、显式 `maxmemory`、`noeviction`；首版使用单逻辑同槽分片，扩展必须由容量证据触发 |
| Cache Redis | TTL 清理 | 独立 Endpoint | 独立高可用 Endpoint、`allkeys-lfu`；丢失后允许回源 |
| Worker | Builtin 4 / Sandbox 2 slots | Builtin 8 / Sandbox 4 slots | 起点为 Builtin 32 / Sandbox 12 slots；以压测校准 |
| Sandbox | `runc` 协议测试 | `runc` 协议测试 | `runsc`、已验证的不可变镜像 digest、独立 Sandbox Runtime 服务 |

生产部署前还必须确认：两个 Worker Pool 都不能访问 PostgreSQL 和两类 Redis；
Builtin Worker 的 HTTP/RPC egress 只能通向受管理的 allow-list 代理，Sandbox
Worker 没有 egress；Worker 无卷挂载、只读根文件系统、无 Linux capability、启用
`no-new-privileges`。普通 Worker **不得**挂 Docker root socket。若使用容器
Sandbox，Sandbox Runtime Controller 是受隔离的专用部署单元，负责以受限 API
创建 per-attempt 容器；它不是 Worker 的 root socket 透传。Worker 通过私有
HTTPS 和 Secret-Manager 注入的服务令牌调用 Controller；若运行平台要求双向
TLS，则由网络边界或 sidecar 明确配置，不能把“HTTPS”误写成已实现的 mTLS。

`deployments/compose.yaml` 是 local 参考拓扑，并通过架构测试保护上述网络与
凭据边界。它不等同生产部署：生产环境需要 TLS、Secret Manager、网络策略、
多副本以及经审核的 Sandbox Runtime Controller。

## 3. 负载模型与测量方式

发布候选使用下面的固定分布，并将实际生成的每类数量记入报告：

| 类别 | 占比 | 图形 | Operation / Pool | 目标耗时 |
|---|---:|---|---|---:|
| S1 | 35% | 单 Task 深度 1 | HTTP / Builtin | 25 ms |
| S2 | 25% | 串行深度 3 | RPC / Builtin | 50 ms |
| S3 | 25% | 并行宽度 4 后汇合 | Python / Sandbox | 75 ms |
| S4 | 15% | Branch 两条不均衡路径 | HTTP + Python | 25 / 100 ms |

所有 Task 输入和输出仅使用小 JSON Object；这次基准明确不覆盖 Artifact 或大文件。
用一个持续运行的大 Project 和至少三个小 Project 同时提交，验证更早一秒时间桶
不会被后来 Project 越过、同桶内 Project Load/最近准入序号能够打散突发，且在
可持续负载下最老 Ready 等待时间会回落。Builtin 与 Sandbox Topic 保持不对称，
并验证任一 Topic 无空位不会阻塞另一 Topic。

完整发布候选按以下阶段运行：60 分钟稳态、15 分钟突发（目标进入速率为稳态
的 2 倍）、至少 15 分钟恢复观察。任何阶段发生错误、重启或配置变更都必须
重新开始该阶段，报告不得把不连续数据拼接为一次成功运行。

每次运行在独占的 `test` 或生产候选命名空间执行，记录：

```text
UTC 起止时间、提交 commit、镜像 digest、Profile、CPU/Memory/磁盘/网络、
Control Plane 和每个 Worker Pool 副本/Slot、Kafka partition、PostgreSQL
规格和 max_connections、Redis Endpoint 类型、四类负载数与目标时长。
```

## 4. 指标、公式和通过门槛

Control Plane 暴露 `/metrics`。M12 新增以下低基数指标，禁止附加
`project_id/run_id/attempt_id/trace_id` 标签：

| 指标 | 计算 | 门槛 |
|---|---|---:|
| `evalfrog_ready_to_queued_seconds` | `histogram_quantile(0.95, sum by (le) (rate(...[5m])))` | P95 ≤ 1 s |
| `evalfrog_postgres_pool_acquire_seconds{outcome="success"}` | 同上，代表连接池获取等待 | P95 ≤ 100 ms |
| `evalfrog_execution_context_cache_access_total` | `sum(rate(...{outcome="hit"}[5m])) / sum(rate(...[5m]))`；仅在预热后统计 | ≥ 80% |
| `evalfrog_outbox_oldest_unpublished_age_seconds` | 最大观测值 | ≤ 30 s |
| `evalfrog_kafka_consumer_lag_records` | Task group/topic Lag 对比当期 Topic Queue Window | 突发后回落；不得持续超 Window |
| `evalfrog_scheduler_topic_queue_window` | Worker 实际完成速率 EWMA × 约 5 秒并按 Profile 上下界夹取 | 与当期完成速率匹配，不读取 Slot 分额度 |
| `evalfrog_scheduler_topic_queue_occupancy` | 未确认 Reservation + Queued Attempt | 每类 ≤ 对应 Window；下降发生在 Claim |
| `evalfrog_scheduler_worker_completion_ewma_per_second` | Worker 实际完成 Attempt 的 5 秒采样 EWMA | Worker 停止完成后逐周期衰减 |

同时查询 PostgreSQL：非法状态转换数、`effective_attempt_id` 重复接受数、跨
Project 查询失败数、未发布 Outbox 数与 Inbox 去重冲突数均应为零。每项失败时
先保留 Metrics、Kafka Lag、`trace_id` 和安全诊断，再按
[故障恢复与DLQ运行手册](./故障恢复与DLQ运行手册.md) 排障；禁止先清 Redis、
重置 offset 或修改权威状态。

最大可持续 `tasks/min` 定义为：在 60 分钟稳态中同时满足上表门槛、错误率为零、
突发后 Lag 回落、没有状态/隔离/Secret 违规的最大**已完成** Task 速率。没有
该实测记录时，任何 Profile 的 Slot、Kafka Partition 或理论公式都不能被写成
容量声明。

Compose Controller 冒烟测试使用 `EVALFROG_M12_COMPOSE=1` 运行
`TestM12ComposeSandboxControllerCompletesProductionRun`。默认通过 local 映射的
PostgreSQL；如果执行者位于 Docker network 内，应同时设置
`EVALFROG_M12_POSTGRES_DSN=postgres://evalfrog:evalfrog@postgres:5432/evalfrog?sslmode=disable`。
若需要让现有 PostgreSQL Integration Harness 同样运行在该网络，还应设置同值的
`EVALFROG_INTEGRATION_POSTGRES_DSN`。
它只验证 Sandbox 的真实执行链路，不代替本节的容量实验。

## 5. 安全门禁

每个发布候选执行：

```powershell
go run golang.org/x/vuln/cmd/govulncheck@v1.6.0 ./...
npm.cmd --prefix web audit --omit=dev --audit-level=high
docker scout cves --exit-code --only-severity critical,high <immutable-image-digest>
```

`govulncheck` 只对可达 Go 漏洞失败；扫描时间、数据库版本和任何不可达发现也
必须进入报告。Web 使用锁文件，即使当前零依赖也必须执行审计。镜像扫描应使用
已认证的受限扫描身份；没有 Docker Scout/扫描数据库访问权限时，结果是
**未完成**，不是“零漏洞”。

本仓库的 Pull Request CI 自动执行 `govulncheck` 和 Web 审计；镜像扫描保留为
发布环境的必过项，因为它必须扫描最终的不可变镜像 digest，而不是开发机的
标签。M12 本地验收若因未登录 Scanner 无法运行，只能记录为 `Release Candidate
blocked`，不可删掉命令或降级为成功。

还必须自动验证：Project A 的合法 Principal 不能读取 Project B 的 Run、诊断、
Connection 或 Service；HTTP Node 拒绝绝对 URL、Host 覆盖、路径逃逸和重定向；
Secret 不进入 IR、DSL、Kafka、Context、普通日志、Metrics 或诊断；Sandbox
拒绝网络、主机文件系统、环境凭据和资源逃逸。已知 Escape 集、1000 次
创建/销毁压力与实际 `runsc` 验证只能在专用 Sandbox 环境运行，不能以 local
`runc` 协议测试替代。

## 6. 备份、恢复、回放和回滚

### PostgreSQL 备份与恢复演练

1. 使用受限备份身份执行一致性逻辑备份，并保存 PostgreSQL 版本、Schema、
   UTC 时间、校验和和 KMS 加密版本：

   ```bash
   pg_dump --format=custom --no-owner --no-privileges \
     --schema=evalfrog_production_default "$EVALFROG_POSTGRES_DSN" > evalfrog-<utc>.dump
   sha256sum evalfrog-<utc>.dump > evalfrog-<utc>.dump.sha256
   ```

2. 在隔离的恢复目标执行 `pg_restore --clean --if-exists`，运行迁移和只读一致性
   检查；不得先覆盖正在服务的生产数据库。
3. 恢复完成后启动 Control Plane，但先保持 Scheduler 停止准入。验证 Outbox /
   Inbox、Run、Attempt、Output 的计数与抽样 Hash；再启动 Relay、Engine、
   Scheduler。重复 Runtime Event 由 Inbox/CAS 收敛，重复 Task 由 Claim/Fencing
   收敛。
4. Scheduling Redis 不从备份恢复：清空其命名空间并运行既有数据库重建流程；
   重建期间维持 Fail Closed。Cache Redis 可清空并由 Cache-Aside 回源。

### Kafka Replay

Kafka Replay 先固定 consumer group、topic、partition、起止 offset 和预期影响
范围，在隔离 group 或维护窗口验证。只能 replay 已持久化的 Runtime / Task
wake-up；消费者仍须从 PostgreSQL 读取当前事实。运营人员不能手工伪造完成事件。
面向业务状态的人工补发使用受权限约束的 `evalfrog run replay` / API，它会验证
actionable 条件并原子写 Outbox + Audit。

### 应用回滚

Migration 只前向追加。回滚先暂停发布、保留全部诊断和 offset，再把 Control
Plane/Worker 镜像切回已验证的不可变 digest；仅当旧二进制与当前 Schema 兼容才
允许启动。不能执行未审计的 down migration。Kafka topic、Redis Lane、Snapshot
和已发布 Definition 不随应用回滚被删除。

## 7. 第一阶段 Release Checklist

- [ ] M0-M11 的远端 CI 成功，版本化 Contract 无未处理兼容性问题。
- [ ] `local/test/production-default` 清单已按目标环境核验，生产 Secret、TLS、
  Kafka RF/ISR、NetworkPolicy 和 Sandbox Controller 已由对应负责人批准。
- [ ] Go、Web 和不可变镜像安全扫描均有本次报告；不存在未处置 High/Critical。
- [ ] Project 隔离、SSRF、Secret、Worker 零信任、Sandbox Escape/1000 次压力
  均通过或有明确阻断发布的结论。
- [ ] 数据库恢复、Outbox/Inbox 回放、Scheduling Redis 重建、Kafka 回放和
  应用回滚均在隔离环境演练成功。
- [ ] 60m 稳态、15m Burst、15m Settling 的原始 Metrics 和容量报告已归档，且
  所有指标满足第 4 节。
- [ ] 最终 CLI + Web 正常路径与 Worker Crash/Lease Recovery 路径均自动化通过。
- [ ] 值班、告警、Owner、变更窗口和回滚责任已确认。

所有项目勾选后才允许把 README 与实施计划的里程碑改为 `Production Ready`。

## 8. 本机与远端执行记录（2026-08-14，非容量声明）

本节保留可重复的 local 与 CI 证据，避免把“开发机上的协议和恢复验证”误写成生产
容量或 hardened-runtime 安全结论。本机执行 commit 为
`28ee7a9955779bd058eb9a500f4277b6b90071f2`，环境是 Docker Desktop Linux
container、12 vCPU、约 3.7 GiB Docker 可用内存，Profile 为 `local`。该环境只
提供 `runc`，没有 `runsc`。

已完成的实测：

- 2026-08-27 的 Engine/Scheduler/Kafka/Worker 高并发闭环重构通过全仓 Unit/Vet/
  Build、20 次核心稳定性、Linux Race、核心包 90% 覆盖率门禁，以及真实
  PostgreSQL/Redis/Kafka 全套 Integration。当前源码重新构建完整 Compose 后，
  CLI Doctor 和 `TestM12ComposeSandboxControllerCompletesProductionRun` 均通过；
  该结果是正确性与部署闭环证据，不是 60/15/15 分钟容量声明。
- `TestDockerSandboxIntegration` 通过，覆盖 Code 输出、禁止 import、文件写入
  拒绝和执行超时；其 Containment Probe 还会假设 Python 语言级 import allowlist
  已被标准运行时对象绕过，并验证 OCI 层仍禁止网络 egress、Docker socket、根目录
  写入和 Sandbox Controller Token 暴露。结束后没有带
  `evalfrog.sandbox=python-v1` 标签的容器残留。
- 显式开启的
  `TestDockerSandboxRuncCreateDestroyStress` 顺序完成 1,000 次受限
  `runc` create/run/destroy，耗时 `13m42.941s`；每次返回预期 JSON，最终逐个
  检查本次容器均已被删除。执行命令必须将 Go 测试超时设为不低于 25 分钟：

  ```powershell
  $env:EVALFROG_M12_SANDBOX_STRESS = "1"
  go test -count=1 -v -timeout 25m -tags="integration stress" `
    ./internal/adapters/sandbox -run '^TestDockerSandboxRuncCreateDestroyStress$'
  ```

- 在 `authority` 内网以当前源码连接真实 PostgreSQL、Scheduling Redis 和
  Kafka，以下恢复语义通过：Attempt Lost 的 durable wake-up/旧 Fencing 拒绝、
  Deadline 优先于 Retry、Outbox 发布前后崩溃重放、Scheduling Redis
  Fail-Closed 后从 PostgreSQL 重建。
- 使用 `pg_dump --format=custom` 从运行中的 local PostgreSQL 备份，并在全新、
  未暴露端口的 `postgres:16.4-alpine` 容器以
  `pg_restore --clean --if-exists` 恢复。传输前后 SHA-256 一致，
  `evalfrog_local` Schema 的表数均为 32。该恢复目标随后已删除，源数据库未被
  覆盖。
- Scheduling Redis 与 Kafka 分别进行了真实容器重启；Redis 重启后重建测试通过，
  Kafka 重启后持久 Topic 仍存在，`TestM7KafkaWorkerCoordinatorEngineEndToEnd`
  通过。该 M7 用例中的到 `127.0.0.1:1` 的 Redis 日志是测试刻意注入的
  Cache 故障回源，不代表依赖不可用。
- `go test ./...`、Linux Go 1.26.6 + GCC 下的 `go test -race ./...`、
  `govulncheck`（0 个可达漏洞）和 `npm audit --omit=dev --audit-level=high`
  （0 个漏洞）均通过。
- 2026-08-15 已重新拉取锁定 Go、Node 和 Nginx 基础镜像，并以当前源码重建
  Control Plane、两个 Worker、Sandbox Runtime Controller 与 Web。Compose
  E2E `TestM12ComposeSandboxControllerCompletesProductionRun` 通过；Web 曾因
  缺少 `evalfrog-control-plane` 的 Edge DNS alias 而启动失败，现已由 Compose

  Repository 安装并注册 `runsc`，验证 runtime 可用后，执行同一 Sandbox
  Contract（包括上述 Containment Probe）与 1,000 次 `runsc`
  create/run/destroy。PR CI `31824410787`（commit `93cc38f`）已在
  `runsc release-20260810.0` 下通过该 Contract（`3.30s`）、1,000 次
  create/run/destroy（`10m25.027s`）和最终无受管容器残留检查。这是 hardened
