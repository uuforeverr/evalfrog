## 1. 计划目标

本计划不以“尽快堆出大量节点”为目标，而是分阶段建立以下可证明的核心闭环：

```text
Human Web / Agent CLI 编辑统一 IR
→ 保存不可变 Draft Revision
→ Validate / Compile
→ Draft Test
→ Publish 并自动激活不可变 Version
→ 创建绑定 Execution Snapshot 的 Run
→ Engine 推进控制图
→ Engine 原子创建 Attempt 与 Task Outbox
→ Kafka 异步派发 Task
→ Worker 执行并通过 Coordinator 完成
→ Engine 接受 Effective Output 并继续推进
→ Error 通过 Source Map 回到 IR
```

每个阶段都必须形成可运行、可测试、可回归的增量。任何阶段不得用临时捷径破坏已经冻结的状态所有权，不能以“后面再重构”为理由让 Worker 直连数据库、Runtime 执行 IR、Gateway承担任务分发，或让 Redis/Kafka 成为权威状态。

## 3. 全局质量门槛

### 3.1 每次合并必须通过

- `go test ./...`；
- `go test -race ./...`，外部依赖集成测试可在独立 Job 执行；
- 格式化、静态检查、依赖边界检查和生成物一致性检查；
- PostgreSQL Migration 在空库执行成功，并能从上一已发布 Schema 升级；
- IR Schema、OpenAPI 和 Kafka Message Schema 的兼容性检查；
- 不允许新增 Flaky Test；同一提交的核心测试重复执行 20 次不得随机失败；
- 核心状态机、Compiler、Engine、Attempt/Lease 包行覆盖率不低于 90%，且每条合法/非法状态迁移必须有显式测试，覆盖率数字不能替代状态矩阵测试。

### 3.2 测试分层

| 层级 | 目的 | 默认执行时机 |
|---|---|---|
| Unit | 领域规则、状态转换、编译算法 | 每次提交 |
| Golden/Fixture | IR→DSL/Source Map、Error Contract、Message DTO 稳定性 | 每次提交 |
| Contract | HTTP、Kafka、Executor SPI 的提供方/消费方一致性 | 每次提交 |
| Integration | PostgreSQL、Redis、Kafka、Sandbox 的真实语义 | Pull Request |
| End-to-End | Web/CLI 到 Worker 的完整闭环 | 主分支与发布候选 |
| Fault Injection | Crash、重复、乱序、网络分区、Lease 失效 | Nightly 与发布候选 |
| Performance | 吞吐、延迟、公平性、连接池与缓存命中 | 发布候选 |
| Security | Project 隔离、SSRF、Secret、Sandbox Escape | Pull Request + 发布候选 |

### 3.3 阶段退出规则

一个阶段只有在以下条件同时满足时才能进入下一阶段：

1. 阶段产物已经合并且有版本化 Contract；
2. 本节指定测试全部自动化，不能只靠人工演示；
3. 阶段达标要求有 CI 证据；
4. 没有通过跳过测试、关闭 Fencing、降低事务原子性等方式临时绕过；
5. 新增架构决策已经回写现有决策文档，而不是只存在于代码注释或聊天记录。
6. 已按根目录 `项目准则.md` 完成学习文档价值评估，值得沉淀的内容已经更新到 `docs/learning/学习文档.md`；
7. 以上门槛全部通过并报告验收结果后，才为该模块创建独立 commit 并推送远端。

- PostgreSQL、两个逻辑 Redis、Kafka 的本地编排；

- 包依赖规则检查，禁止 Domain 导入 Adapter，禁止 Worker 导入 PostgreSQL Adapter；
- CI 基线和 Migration Runner。

### 测试内容

- 四个二进制编译和启动 Smoke Test；
- 配置缺失、Profile 混用、非法容量参数必须启动失败；
- 本地依赖健康检查；
- 架构测试故意引入非法 Import 时能够失败；
- Shutdown 时 HTTP Server、Kafka Consumer 和后台 Job 能在期限内退出。

### 达标要求

- 新开发者只需一条文档化命令即可启动依赖并运行全部空壳进程；
- CI 在全新环境可重复通过；

- 不包含任何从 smart-workflow 复制来的业务实现或 Migration。

## M1：IR、Node Catalog Contract 与公共契约

> 实施状态：Completed（2026-08-11）。本阶段只实现作者态 Contract、解析、校验与确定性 Hash，不包含 Compiler、DSL 或 Runtime。

### 目标

冻结代码层的作者态输入边界，使 Human Web 与 Agent CLI 能生成同一种 Canonical IR。

### 交付内容

- IR v1 JSON Schema 和 Go Model；
- Node、Input、Output、Edge、Layout、Logical ID 规则；
- 六种顶层 JSON Type 及兼容规则；
- Node Description 和内部 Catalog Revision Contract；
- Start、End、Branch、Code、HTTP、RPC 的第一阶段描述；
- Canonical JSON、Hash 和结构化 Diagnostic Model；
- Draft Save 使用的宽松 Parser 与 Test/Publish 使用的严格 Validator 边界。

### 测试内容

- Human/Web 风格随机 ID 与 Agent 语义 ID Fixture 均可解析；
- Literal/Ref 互斥、Input/Output 唯一、Edge 引用、Layout 规则；
- 六种类型的 Literal 校验和 `integer → number` 唯一提升规则；
- Canonicalize 对 Object Key 顺序稳定，对数组顺序敏感；
- Fuzz Test 覆盖 JSON Parser、ID、极端深度、超大字段和非法 Unicode；
- Node Description 与 IR Schema 的一致性 Contract Test。

### 达标要求

- 同一 IR 重复 Canonicalize 100 次得到完全相同字节和 Hash；
- 所有已冻结 IR 正反例都进入版本化 Fixture；
- Draft Save 可以保存语法有效但尚未完整的 IR，Test/Publish 必须拒绝不完整 IR；
- IR Contract 不包含 Node Version、Kafka Topic、Worker、Lease 或 Retry/Timeout 作者配置。

## M2：Compiler、DSL、Source Map 与 Control Graph

### 目标

实现纯函数式、确定性的服务端编译链路，使 Runtime 不需要读取 IR 或 Node Description。

### 交付内容

- Compiler Pipeline 与 Compiler Handler SPI；
- Control Graph 静态校验；
- Start/End/Branch 与 Task Operation DSL v1；
- 确定性 Execution Node/Edge ID；
- Source Map Node/Edge/Field Key-Value Mapping；
- Compiler Manifest、IR/DSL/SourceMap/Definition Hash；
- Runtime DSL 自校验和 Operation Version Compatibility Checker。

### 测试内容

- IR→DSL 与 Source Map Golden Test；
- 相同 IR、Catalog、Policy 重复编译的确定性测试；
- DAG、Start/End、可达性、Branch Route、OR-Join 静态校验；
- `Active(Target) ⇒ Active(Source)` 安全引用校验；
- Branch 六种类型与 Operator 矩阵；
- 每个 DSL Node、Edge 和可报错字段的 Source Map 覆盖；
- Compiler Handler 注册测试，新增 Task Handler 不修改中心 Switch；
- 未支持 Operation Version 在执行前被整体拒绝。

### 达标要求

- 相同输入连续编译 100 次，DSL、Source Map 和全部 Hash 字节级一致；
- Source Map 覆盖率为 100%，缺失映射时编译失败；
- 所有结构性错误在 Test/Publish 阶段返回，不延后到 Runtime；
- Compiler 包不导入 PostgreSQL、Redis、Kafka 或 HTTP Server Adapter。

## M3：Access、Managed Resources 与 Definition 生命周期

状态：已实现并通过 Unit、Contract、Architecture、Linux Race、真实 PostgreSQL 并发/事务故障注入与完整 Compose Integration 验收。

### 目标

建立 Project 隔离、统一权限和不可变定义生命周期，完成 Draft→Test Snapshot→Publish 的权威持久化；完整 Test Run 在 Runtime 持久化完成后的 M5 接通。

### 交付内容

- User、Service Account、Project Membership、Permission、Execution Identity；
- Connection 与 RPC Service 元数据、Secret Reference；
- Workflow、Draft Pointer、Draft Revision、Published Version、Execution Snapshot；
- SaveDraft 乐观锁；
- ValidateDraft、CompileDraftTestSnapshot、Publish、Rollback、CopyPublishedVersion；
- Publish 自动激活和 Idempotency；
- Definition PostgreSQL Repository 与 Migration；
- 第一批 External HTTP/JSON API。

### 测试内容

- 两个并发 SaveDraft 只有一个成功，失败方得到 Revision Conflict；
- Publish 请求在客户端超时后重放不会增加 Version Number；
- Publish 创建 Snapshot、Version、Active Pointer、Audit 的事务原子性；
- Published Version 与被引用 Snapshot 不可更新、不可删除；
- Copy 从保存的 IR Snapshot 创建新 Workflow Draft，不经过 DSL 反编译；
- 没有 Published Version 时，Production Definition Resolution 返回 `WORKFLOW_NOT_PUBLISHED`；
- 权限矩阵与不可见跨 Project 资源统一返回 `RESOURCE_NOT_FOUND`；
- Connection/Service 在 Test/Publish 阶段执行作者授权；
- 所有 Repository 查询必须携带 `project_id` 的隔离测试。

### 达标要求

- Draft、Version、Snapshot 的并发与幂等集成测试在真实 PostgreSQL 上通过；
- 任意事务注入失败后不存在半个 Version 或已更新但无 Snapshot 的 Active Pointer；
- 服务端不存在 DSL Upload 或 Source Map Override 入口；
- Test 与 Publish 调用同一 Compiler，而不是维护两套规则。
- 本阶段只证明 Test Snapshot 的编译与持久化；对外 `TestDraft` 创建真实 Run 的入口必须等 M5 完成后再启用。

- Branch 排他路由、OR-Join、Skipped；
- Output Binding、Effective Attempt、Fail-Fast；
- Retry Decision、Termination Intent、Cancel/Timeout；
- Deterministic In-Memory Engine Harness。

### 测试内容

- 所有合法与非法状态迁移的表驱动测试；
- Start/End/Branch 无 Attempt 的不变量；
- 并行路径、排他分支、OR-Join、全部 Inactive 路径；
- 激活节点不得进入 Skipped；

- Fail-Fast 不允许另一条路径掩盖失败；
- Property Test 随机生成小型合法 DAG，重复事件后状态仍收敛。

### 达标要求

- 状态机测试覆盖每一条冻结迁移和拒绝路径；
- 同一事件序列重复、重排后不会产生重复有效 Output 或非法终态；

- Engine Harness 可以完整跑通至少 20 个代表性 Workflow Fixture。

## M5：Runtime PostgreSQL、Outbox/Inbox 与事件驱动推进

> 状态：已于 M5 验收完成。真实 Kafka Broker Adapter、Scheduler 派发与 Worker Transport 不属于本里程碑。

把 M4 的语义模型落到 PostgreSQL 事务、CAS、Outbox/Inbox 和可恢复事件循环中。

### 交付内容

- CreateRun Transaction；
- TestDraft 与 Production CreateRun 对不可变 Snapshot 的来源校验；
- Engine Inbox Consumer；
- Run 初始化原子事务与批量 Node Run Insert；
- Attempt Completion 两阶段接受链路；
- Outbox Relay、Inbox Deduplication 和 Runtime Event DTO；
- 多实例数据库 Claim/Lease Primitive。

### 测试内容

- CreateRun 只能写 Pending Run + RunCreated Outbox，不初始化半张图；
- Engine 崩溃前后重放 RunCreated 只得到一套 Node Run；
- Attempt 终态、Output Candidate、Completion Outbox 同事务；

- Kafka 重复、乱序、延迟 Event 的 Inbox/CAS 测试；

## M6：Project 公平 Scheduler 与 Scheduling Redis（历史里程碑）

> 状态：初始实现已通过当期验收；其 Max-Min、Lane/Credit、后续一秒时间桶FIFO、Project Load、Topic Queue Window及Scheduling Redis方案均已被最新目标废止。本节只保留历史交付记录；后续代码按架构决策01第12节删除独立Scheduler。

### 目标

实现仅以 `project_id` 为公平单元的等权 Max-Min、空闲借用、固定 Lane 和有界预派发。

### 交付内容

- Ready Candidate Index 与 Project 内稳定顺序；
- Stable Hash Scheduling Lane；
- Active Project/Epoch/Credit/Inflight Reservation；
- Credit Balancer Lease 与 Fencing；
- Global/Pool Dispatch Window；
- `ready → queued + Attempt + Task Outbox` 原子 Dispatch；
- Redis 丢失后的 Fail Closed 与数据库重建。

### 测试内容

- 1、2、10、100 个竞争 Project 的公平性仿真；
- 低需求 Project 空闲额度被其他 Project 借用；
- 新 Project 加入后既有 Attempt 不抢占，但新派发及时恢复公平；
- Project 内 `priority DESC, ready_at ASC, node_run_id ASC`；
- 多 Scheduler 对同一 Ready Node 竞争，只创建一个 Attempt；
- Dispatch Window 不被并发实例突破；
- Scheduling Redis 超时/不可用时暂停新准入；
- Redis 全量丢失后依据 PostgreSQL Ready/Queued/Running 重建；
- Lane 热点与 Credit Batch 边界测试。

### 达标要求

- 持续竞争时无 Project 饥饿；
- 在稳定负载窗口内，各充分需求 Project 的派发差异不超过一个 Credit Batch 加一个 Scheduling Epoch 的允许误差；
- 任意时刻已准入 Attempt 不超过计算后的 Dispatch Window；
- Redis 故障不会导致无上限派发、重复 Attempt 或权威状态丢失。

## M7：Kafka、Worker Runtime、Attempt API 与 Execution Context

> 状态：已实现并通过版本化消息、真实 Kafka/PostgreSQL/Redis、多 Control Plane/Worker 副本、Cache Redis 故障回源、Lease Lost/Recovery、Fencing、Poison/DLQ 与架构依赖验收。真实 HTTP/RPC 和 Python Sandbox Executor 分别属于 M8/M9。

### 目标

历史实现完成了 Scheduler→Kafka→Worker→Coordinator→Engine 的分布式执行骨架。最新目标保留Kafka、Worker、Coordinator和Engine协议，把Attempt与Task Outbox创建职责合并进Engine并删除Scheduler。

### 交付内容

- 三个正式 Topic 与对应 DLQ；
- Task/Runtime Event 版本化 JSON Envelope；
- Builtin/Sandbox 通用 Worker Runtime；
- Local Slot、Bounded Prefetch、Backpressure；
- Claim/Heartbeat/Complete HTTP/JSON Worker API；
- Lease/Fencing 与 Claim 后 ACK；
- Execution Context Gateway；
- Snapshot、Run Context、Effective Output 的 Cache-Aside；
- Worker Capability 与 Resource Class 校验。

### 测试内容

- Task 使用 `attempt_id`、Runtime Event 使用 `run_id` 分区；
- Message 超过 64 KiB 被拒绝，消息中不含 DSL、Context、Output、Secret；
- Worker 无本地 Slot 时不预取；
- Claim 成功才 ACK，ACK 不等待执行完成；
- Worker 在 Claim 前、ACK 后、执行中、Complete 前后崩溃；
- Lease 到期和旧 Fencing Token 的迟到 Heartbeat/Result；
- 重复 Task、Poison Task、Consumer Rebalance；
- Cache Hit、Miss、Redis Timeout、PostgreSQL 回源与回填；
- Worker 进程配置和网络策略中不存在 Workflow PostgreSQL 凭证。

### 达标要求

- 端到端测试 Executor 可以在多 Control Plane、多 Worker 副本下完成 Workflow；
- Worker Crash 最终形成 Lost/Recovery，而不是永久 Running；
- 旧 Worker Result 100% 被 Fencing 拒绝；
- Redis Cache 整体不可用时执行正确性保持，只有读取延迟上升；
- Kafka 重投不会产生第二个 Effective Output。

## M8：HTTP/RPC 节点与 Managed Resource Runtime

### M8 交付记录（2026-08-13）

- 已实现 `internal/worker/executor/http`：仅接受 Connection 的相对路径，强制 Origin、方法、路径前缀、请求/响应大小、受保护 Header、重定向和 JSON 响应约束，并注入稳定 `run_id:execution_node_id` 幂等键。

### M10 实现状态与验收说明

M10 新增 `workflowapp` 作为 External HTTP、CLI 与 Web 共用的应用命令边界，并补全 OpenAPI v1 的 Draft Test、Production Run、Run Read、Cancel、SSE wake-up、Node Type 与安全 Connection Directory 接口。所有 Authoring 请求仍只接受 IR；发布和 Run Command 响应不暴露 DSL、Source Map 或 Execution Snapshot。

`evalfrog` CLI 已支持 `workflow create|pull|copy`、`draft push|validate`、`publish`、`run test|create|status|cancel`、`node-type list` 与 `connection list`。后续增量交付的 `workflow builder` 在本地显式 Session 中提供 Node/Edge/Input/Binding/Output/Layout 的小步编辑，并在 Create/Pull/Copy/Push 时仍只调用同一 IR External API；它不新增 DSL 或私有后端入口。常规 CLI 把最新 Draft Revision 与 IR 写入 project/workflow 隔离的本地 Workspace，Builder Session 则额外保存显式 `ir.json + meta.json` 以服务 Agent 的最小修改。两者都先做有界 IR 外壳检查，再由服务端执行权威 Validator、Compiler、权限与 Idempotency；Revision Conflict 明确提示先 Pull。

Human Web Canvas 是可独立构建的静态产物：目录节点可添加示例 Node、JSON IR 直接编辑 Node/Edge/Input、拖拽写回 Layout，并通过同一 API 执行保存、校验、测试、发布、Run 状态读取和 SSE 进度刷新。Runtime Failure 使用 Run Read Model 中的 Source Map 映射高亮 IR Node/Edge，显示 Field 路径与安全 Details。

Run Read Model 始终从 PostgreSQL Runtime 表和不可变 Snapshot Source Map 构建；Cache Redis 仅 Cache-Aside 缓存投影。状态或 Node 变化提交后删除缓存并发布可丢失 Pub/Sub wake-up，浏览器只把 SSE 当作重新 GET 权威投影的信号。Cancel 写持久请求时间和 `RunCancelRequested` Outbox，Engine 异步收敛状态，保持其唯一状态推进权。

自动化验收包括：CLI Create→Pull→Push→Validate→Test→Publish→Run→Status→Cancel 与 Copy 命令契约链路；同一 Draft 的 Revision Conflict；无 DSL/Source Map Upload Surface；未发布 Production Run 拒绝；User/Service Account 一致授权；取消事件在初始化前的收敛；Redis 投影缺失回源；Source Map Node/Edge/Field 回映；SSE 只传 wake-up；Web 外部 API 契约与静态构建。真实 PostgreSQL Integration 测试覆盖 Draft Test、自动激活 Publish、Production Run、Cancel 与 Run Read Model。

## 7. 最终验收场景

第一阶段最终验收必须至少自动化以下场景：

```text
Agent 使用 evalfrog 创建语义 ID IR
→ Push Draft Revision
→ 服务端 Validate
→ Draft Test 成功
→ Publish 自动激活 Version 1
→ Production Run
→ Branch 选择路径
→ HTTP 或 RPC Node 成功
→ Python Code Node 在 Sandbox 中执行
→ End 输出 JSON Object
→ CLI/Web 查询 succeeded 与完整 Trace
```

以及对应失败场景：

```text
Worker 在执行中崩溃
→ Lease 过期
→ Attempt Lost
→ Recovery 创建新 Attempt
→ 旧 Worker 迟到结果被 Fencing 拒绝
→ 新 Attempt 被 Engine 接受
→ Effective Output 唯一
→ Runtime Error 或恢复历史可通过 Source Map/Attempt Trace 回到 IR
```

只有正常闭环和故障闭环同时通过，EvalFrog 第一阶段才算完成。
