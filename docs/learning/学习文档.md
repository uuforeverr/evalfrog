# EvalFrog 学习文档

本文档用于项目完成过程中的持续复盘，以及一周后的面试集中复习。内容只记录已冻结的设计或已实现并验证的能力；尚未完成的部分会明确标为“待实现”。

## 1. 一分钟项目介绍

EvalFrog 是一个同时面向 Human Web Canvas 与 Agent CLI 的企业级 Workflow Platform。Human 和 Agent 都编辑 Canonical JSON IR，平台在服务端完成校验和编译，Runtime 只执行不可变 DSL Snapshot。系统用 Source Map 把 DSL 运行错误无损映射回 IR Node、Edge 和字段路径；用 Engine、Scheduler、Attempt Coordinator、Worker 的职责分离保证状态推进、项目公平调度和节点执行可以独立扩展。

第一阶段重点不是扩充节点生态，而是跑通“创建 IR → 校验 → 测试 → 发布 → 正式运行 → 错误定位”的最小闭环，并确保 PostgreSQL、Redis 和 Kafka 的职责清晰。

## 2. 当前架构心智模型

```text
Human Web / Agent CLI
        ↓ Canonical IR
Modular Control Plane
  Definition → Compiler → Immutable DSL + Source Map
  Runtime Engine ↔ Scheduler ↔ Attempt Coordinator
        ↓                 ↓
PostgreSQL            Scheduling Redis
        ↓ Outbox           ↓ bounded dispatch
      Kafka → Builtin Worker / Sandbox Worker
                    ↓
             Execution Context Gateway
                    ↓
          PostgreSQL + Cache Redis
```

核心职责：

- PostgreSQL：Definition、Runtime State、Output、Outbox/Inbox、权限和审计的唯一权威来源；
- Scheduling Redis：维护可重建的一秒时间桶 Ready Index、Project Load、Topic Queue Window/Occupancy、Reservation 和紧凑 Inflight，加速高频调度；
- Cache Redis：缓存 Snapshot、Run Context、Effective Output 和 Read Model，Cache Miss 回源 PostgreSQL；
- Kafka：承载 Task 与 Runtime Event 的至少一次传递，不保存权威业务状态；
- Worker：只执行一个已 Claim 的 Attempt，不直接推进 Workflow 状态。

## 3. 高频面试问答基线

### Q1：为什么不能直接让 Runtime 执行 IR？

IR 服务 Human 和 Agent 的编辑、理解、Diff、Copy 与布局表达，允许 Draft 不完整；DSL 服务 Runtime，需要强约束、版本化和确定性。分离后，编辑模型可以演进，历史发布版本仍由不可变 DSL 稳定执行。代价是必须维护 Compiler、兼容性规则和 Source Map。

### Q2：为什么 Draft 测试也必须执行不可变快照？

测试可以从 Draft Revision 触发，但 Run 创建时必须绑定当时编译出的不可变 Execution Snapshot。这样执行期间继续编辑 Draft 不会改变本次 Run，也能复现错误。正式运行只能绑定 Published Version；没有发布版本不能正式调用。

### Q3：数据库、Redis、Kafka 为什么要这样分工？

PostgreSQL 提供事务、约束和可恢复的权威状态；Redis 解决短期高频读取和调度索引问题，但数据可丢失并可从数据库重建；Kafka 解耦生产者与消费者、吸收流量波动并提供至少一次传递，但消息偏移不能替代 Workflow 状态机。三者是权威状态、派生加速和异步传输的分工，不是为了堆技术栈。

### Q4：为什么权威运行数据不使用 Redis Write-Behind？

Node Output 和状态迁移会决定后续节点能否运行，先写缓存再异步落库会产生丢失、乱序和成功响应后不可恢复的问题。正确路径是先在 PostgreSQL 原子提交状态、Output 与 Outbox，再删除或刷新 Cache；后续读取命中 Redis，不命中回源。缓存不在关键写入的正确性路径上。

### Q5：Kafka 已经投递任务，为什么还需要 Attempt、Lease 和 Fencing？

Kafka 是至少一次传递，重复消费、消费者崩溃和延迟消息都正常存在。Worker 必须先通过数据库 CAS Claim Attempt，获得 Lease 与 Fencing Token；只有当前有效 Attempt 的完成结果才能成为 Effective Output。Kafka ACK 表示任务已被可靠接管，不表示节点已经成功执行。

### Q6：Scheduler 为什么采用一秒时间桶 FIFO，而不是严格全局 FIFO 或 Max-Min Credit？

企业内部评测 Workflow 通常不超过 20 个节点，Ready Node 随上游完成逐步涌现，不会由单个 Project 瞬间形成极深队列。Scheduler 因此先按数据库 `ready_at` 的一秒时间桶 FIFO，保证旧任务不会被持续到来的新项目越过；只有同一时间桶内才比较跨 Builtin/Sandbox 的 `Project Load` 和最近准入序号，打散同一秒并发突发。Project 内再按 `priority DESC, ready_at ASC, node_run_id ASC` 稳定选择。这比每秒重建 Max-Min Credit 更符合负载模型，也减少了全局协调状态。

### Q7：为什么 Kafka 前需要五秒 Topic Queue Window？

如果把全部 Ready Task 提前塞入 Kafka，Broker 队列会固化旧调度决策并放大取消、故障和负载变化的响应时间。Builtin/Sandbox 分别以 Worker 最近实际完成速率 EWMA 乘约五秒缓冲得到 Topic Queue Window；占用只计算未确认 Reservation 与 Queued Attempt。Worker Claim 后立即释放 Topic 空位并持续补充，Running 并发仍由 Worker 本地 Slot 控制。这样 Kafka 能吸收约五秒突发，又不会退化为无限深队列。

## 5. M0：仓库骨架与架构护栏

- 验收状态：已通过本地 Unit、Race、Vet、Build、Architecture、Compose、Integration 与 Graceful Shutdown 验收，并已通过远端 CI、合并到 `main`。
- 学习价值判断：写入。
- 判断理由：M0 体现了模块化单体、Composition Root、启动时配置校验、数据库迁移、健康检查、优雅停机和自动化架构测试，是面试中解释“如何防止架构只停留在图上”的关键证据。

### 解决的问题

M0 不实现 Workflow 业务，而是先建立可执行的边界：四个程序能独立构建和启动，Control Plane 与 Worker 拥有不同依赖权限，三套环境配置遵守同一可靠性语义，本地依赖和 CI 可以重复创建与验证。

### 核心边界与不变量

- `cmd` 只有 `evalfrog`、`control-plane`、`worker-builtin`、`worker-sandbox` 四个 Composition Root；
- `cmd` 只做配置、依赖装配和生命周期管理，领域逻辑不得进入 `main`；
- Worker 只装配 Kafka 与 Worker API Client，没有 PostgreSQL Client 或凭证；
- 版本化 Profile 不保存数据库密码，Compose 只向 Control Plane 与 Migration 注入 PostgreSQL/Redis 连接变量；
- Domain 不得导入 Adapter，Runtime 不得读取 IR/Definition/Catalog，Scheduler 不得导入 Engine；
- `local/test` 继承 `production-default`，只覆盖容量和环境隔离项，可靠性边界不会因环境变小而改变；
- Profile 只在启动时选择，不支持运行期热切换。

### 最终方案及原因

采用模块化单体 Control Plane 加独立 Worker 进程，而不是立即拆微服务。代码边界先通过包结构和自动化依赖测试固定；未来部署拆分只需替换进程内 Port 的 Adapter，不重新定义状态所有权。

所有环境使用严格 YAML：先加载完整 `production-default`，再递归覆盖 `local/test`，最后应用有限的环境变量。解码拒绝未知字段，启动校验检查 Profile 隔离、Kafka 分区、Lease/Heartbeat、Reservation、Inbox Retention 和 PostgreSQL 连接预算，避免错误配置进入运行期。

容器运行层使用静态 Go 二进制和 `scratch` 镜像。每个服务二进制提供自身 HTTP Probe，因此健康检查不依赖 Shell、curl 或 wget，镜像更小且攻击面更低。

### 被放弃的方案及原因

- 大量微服务：M0 没有独立扩缩容和团队所有权证据，提前拆分只会增加网络与一致性成本；
- 全局 `common/utils/service` 包：容易让任意模块绕过所有权，形成新的大泥球；
- Worker 复用 Control Plane 数据库 Client：部署方便但破坏状态写入边界，执行层漏洞也会获得数据库权限；
- 每套环境复制完整配置：容易发生参数漂移，测试环境无法代表生产语义；
- 配置热更新：Lease、分区、Topic Window 边界和连接池参数跨实例不一致会产生难以推理的运行行为，第一阶段只允许重启生效；
- 应用启动时自动执行 Migration：多实例启动会把发布与 Schema 变更耦合，M0 使用带 Advisory Lock 和 checksum ledger 的独立 Migration 模式。

### 数据库、Redis 与 Kafka 在 M0 的角色

- PostgreSQL：只创建 Profile 隔离 Schema 与 Migration Ledger，尚无 Workflow 业务表；
- Scheduling Redis：独立 Endpoint、`noeviction`，为 Ready/Load/Topic/Reservation 协调状态提供独立故障域；
- Cache Redis：独立 Endpoint、`allkeys-lfu`，证明读取缓存可以独立淘汰；
- Kafka：禁用自动建 Topic，由部署脚本显式创建 Builtin Task、Sandbox Task、Runtime Event 和 DLQ；M0 尚不投递业务消息。

这一步的重点是提前证明三者能够独立启动、健康检查和配置隔离，不是用它们假装已有业务吞吐能力。

### 一致性与故障恢复

Migration Runner 使用 PostgreSQL Advisory Lock 串行化多实例迁移，以版本号和 SHA-256 checksum 记录不可变历史；每个事务用 `SET LOCAL search_path` 锁定目标 Schema，避免复用连接池时把 SQL 执行到错误环境。重复执行幂等，已应用 SQL 被修改时直接失败。进程收到 SIGTERM 后按逆序关闭服务，并受统一 Shutdown Deadline 限制。实测三个长运行进程在约 3.36 秒内以退出码 0 停止并能健康重启。

### 高频面试题

#### Q：什么是 Composition Root，为什么只允许它依赖具体 Adapter？

Composition Root 是创建对象、选择实现并连接依赖的唯一位置。领域模块只依赖 Port，具体 PostgreSQL、Redis、Kafka 实现在最外层注入，业务代码因此可以独立测试，也能在不改变领域模型时替换传输或存储实现。

#### Q：模块化单体和普通单体有什么区别？

区别不在进程数量，而在依赖方向、数据所有权和稳定接口。EvalFrog 第一阶段同一 Control Plane 进程内包含多个模块，但禁止反向 Import 和绕过 Owner 写状态；未来拆服务是部署变化，不是重新发明领域边界。

#### Q：Liveness 与 Readiness 有什么区别？

Liveness 只回答进程是否活着，不应因为下游短暂故障而触发无限重启；Readiness 检查当前实例能否接流量。Control Plane Readiness 检查 PostgreSQL、双 Redis 和 Kafka，Worker Readiness 只检查 Kafka 与 Control Plane，不检查它无权访问的数据库。

#### Q：为什么迁移需要 Advisory Lock 和 checksum？

Advisory Lock 防止多个发布实例并发应用同一批迁移；checksum 防止已经在某环境执行过的 SQL 被原地修改。前者解决并发，后者保护历史不可变性，两者不能互相替代。

#### Q：为什么配置错误必须启动失败？

Heartbeat、Lease、Kafka Partition、Redis Reservation 和数据库连接池之间存在硬约束。若实例带着不一致配置运行，问题只会在故障或高并发时出现，恢复成本远高于部署时 Fail Fast。

### 一分钟讲法

M0 的核心不是“建目录”，而是把架构图转成可执行约束。我建立了四个 Composition Root，Control Plane 可以访问 PostgreSQL、双 Redis 和 Kafka，Worker 只能访问 Kafka 与 Worker API；自动化架构测试会拒绝反向依赖。三套配置通过继承保持相同可靠性语义，并在启动时校验容量关系。本地 Compose 显式创建基础设施和 Kafka Topic，Migration Runner 用 Advisory Lock 与 checksum 保证并发和历史安全，所有进程支持健康检查、Trace、Metrics 与统一优雅停机。

### 易错点与追问

- M0 还没有 Workflow、IR、DSL 或 Task 消息，不能把健康栈描述成完整平台；
- 两个 Redis 是不同职责和 Endpoint，不等于已经建设 Redis Cluster；

## 6. M1：IR、Node Catalog Contract 与公共契约

- 验收状态：已通过 Unit、Contract、Golden Fixture、20 次重复、Bounded Fuzz、Vet、Build 与 Linux Race 验收；远端 CI 由本模块分支提交触发。
- 学习价值判断：写入。
- 判断理由：IR 是 Human Web 与 Agent CLI 的共同语言，Logical ID、类型系统、Catalog Version、Canonical Hash 和宽松保存/严格发布边界都是后续难以迁移的底层决策，也是编译器、DSL 和错误回溯的前置条件。

### 解决的问题

M1 把“作者可以提交什么”从聊天中的 JSON 示例变成版本化机器契约。Web 随机 ID 与 Agent 语义 ID 使用同一种 IR；节点差异由 Catalog Description 表达，不能把运行时 Operation Version、Worker 或 Kafka 细节泄漏给作者。

### 核心边界与不变量

- IR 顶层只有 `ir_version/nodes/edges/layout`，Node 统一为 `id/type/title/inputs/outputs`；
- Input 通过 `source=literal|ref` 互斥表达值或上游命名 Output，不存在 `params`、Port 或 Binding ID；
- Node/Edge Logical ID 由作者离线生成，支持 UUID 和语义 ID；Node Version 不进入 IR；
- 顶层类型只有 `string/integer/number/boolean/object/array`，顶层不允许 Null，只有 `integer → number` 隐式提升；
- Draft Parser 允许语义不完整但安全的 IR 外壳，Strict Validator 必须显式绑定 Catalog；
- Catalog 内部版本化，Web/Agent 只获得无版本号且不可修改权威状态的 Description 防御性副本；
- Canonicalize 对 Object Key 顺序不敏感、对 Array 顺序敏感，Hash 使用 SHA-256；
- Diagnostic 使用稳定 Code 和 IR Location，排序确定且最多返回 100 项。

### 最终方案及原因

Go Model 保持浅层统一外壳，`json.RawMessage` 只用于 Literal Value，使十进制 Number 不被提前转成 `float64`。Parser 在模型解码前执行文档大小、深度、Collection、String、Number、UTF-8、Unicode Surrogate 和重复 Object Key 检查；成功后再拒绝未知作者字段。

Strict Validator 先检查 ID、Input/Output、Literal、Edge、Layout 和 Ref 类型，再通过接口调用固定 Catalog Revision。`internal/ir` 不导入具体 `internal/catalog`，Catalog 反向实现 Node Contract Port，因此新增普通 Task Node 不需要修改 IR Validator 的中心分支。

Canonical JSON 使用精确十进制归一化，不经过二进制浮点；Object Key 排序、Array 保序、Number 和 String 编码规则均由 Golden Test 固定。这样 Draft Revision、Published Snapshot 和未来 Definition Hash 才能跨实例稳定复现。

### 被放弃的方案及原因

- 为每个 Node Type 定义不同 JSON 外壳：Agent 必须理解大量私有结构，新增节点会修改 IR 核心 Schema；
- 把 Node Version 放进 IR：Web/Agent 被迫参与内部兼容性选择，旧 Draft 容易静默改变语义；
- 只有 JSON Schema：Schema 无法校验 Input/Output 唯一、跨节点 Ref、Catalog 规则和稳定 Diagnostic Location；
- 只有 Go Validator：Web、CLI 和其他语言无法消费版本化机器契约；
- 服务端生成 Logical ID：离线 Agent 无法独立生成和最小化修改 Workflow；
- 直接使用 `map[string]any` 和 `float64`：字段边界不清晰，大整数和 Decimal 会发生精度损失；
- Draft Save 直接执行完整校验：Web 自动保存会因临时断边或半成品节点失败；
- 接受重复 JSON Key 或非法 Surrogate：不同解析器可能得到不同语义，Canonical Hash 失去可信度。

### 数据库、Redis 与 Kafka 在 M1 的角色

M1 是纯 Contract/Domain 模块，不读写 PostgreSQL、Redis 或 Kafka。IR Hash 将来由 Definition 持久化，但 M1 不为了展示技术栈而给确定性解析和校验引入基础设施依赖。

### 一致性、安全与容量

确定性来自三层证据：版本化 Schema/Fixture、Canonical Golden、同一 Fixture 重复 100 次得到相同字节和 Hash。安全边界包括 1 MiB 文档、64 层深度、256 KiB String、10,000 Collection、128 Port 和 100 Diagnostic 上限，防止 Agent 生成的异常 JSON 消耗无界 CPU/内存。Fuzz 覆盖随机字节、极深结构、超大字段、非法 UTF-8/Surrogate 和 Logical ID。

### 高频面试题

#### Q：为什么 Draft Save 不能直接复用 Publish Validator？

Web 自动保存时画布经常暂时断边、缺节点或字段未填完。Parser 只保证输入是有界、无歧义、字段属于 IR 的安全文档；Publish Validator 则保证引用、类型、节点契约以及后续 Control Graph 全部可执行。放宽保存不能等价于放宽执行。

#### Q：JSON Schema 已经存在，为什么还要 Go Validator？

Schema适合跨语言约束单个 JSON 文档的形状，但不能完整表达跨 Node Output 的 Ref 存在性、名称唯一、Catalog Revision 语义和面向 Agent 的稳定错误位置。两者是外部形状契约与领域语义校验的分工，不是重复实现。

#### Q：为什么 Canonical JSON 不能直接 `json.Marshal(map)`？

Hash 要跨进程和版本稳定，需要明确 Object Key、Array、String、Number 与重复 Key 规则。尤其 Number 不能先转 `float64`，否则大整数和十进制值可能改变。Canonical 规则必须由 Golden Fixture 固定，而不是依赖“当前库碰巧输出一致”。

#### Q：为什么 Catalog Revision 不放进 IR？

IR 是作者意图，Catalog Revision 是平台解释该意图时使用的内部契约坐标。Draft 外层固定 Catalog，Published Snapshot 固定编译产物；Web/Agent 只提交无版本号 Node Type，从而不会被内部版本升级污染。

### 一分钟讲法

M1 把 Human Web 和 Agent CLI 的共同作者语言做成了真正的 Contract。IR 采用统一浅层 Node 外壳，Web UUID 与 Agent 语义 ID 同时受稳定词法规则约束；六种 JSON 顶层类型只有 integer 到 number 的提升。Draft Parser 允许安全半成品保存，Strict Validator 必须绑定内部版本化 Catalog，公开 Description 不暴露 Node Version。Canonical JSON 使用精确十进制、Object 排序和 Array 保序生成 SHA-256 Hash，并用版本化正反例、100 次重复、Fuzz 和 Race Test 固定行为。

### 五分钟展开提示

1. 先解释 IR 是作者态权威、DSL 是运行态产物；
2. 展开统一 Node/Input/Output/Edge/Layout 与离线 Logical ID；
3. 对比 Draft Parser 和 Strict Validator 的失败边界；
4. 说明 JSON Schema 与领域 Validator 为什么缺一不可；
5. 解释 Catalog Revision 内部化和新增 Node 的注册路径；
6. 展开 Decimal、Canonical JSON、Hash 与重复 Key/Unicode 安全；
7. 最后给出 Fixture、Contract、100 次重复、Fuzz 和 Race 证据链。

### 易错点与追问

- M1 的 Strict Validator 单独使用时不包含 DAG、Branch Route 完整性和 `Active(Target) ⇒ Active(Source)`；Test/Publish 必须继续组合 M2 Compiler Pipeline；
- M1 有 IR Contract，不等于已经存在 Draft API、数据库版本模型或 CLI 上传命令；
- Catalog 是进程内版本化契约，不是独立 Registry 微服务；
- `number` 是精确 JSON Decimal 语义，不是 `float32/float64`；
- Object 内部允许 Null，但六种顶层类型不包含 Null；
- Layout 参与 IR Hash，但未来 Compiler 必须忽略 Layout，因此布局变化不应改变 DSL Hash。

## 7. M2：Compiler、DSL、Source Map 与 Control Graph

- 验收状态：已通过 Unit、JSON Schema Contract、Golden、100 次确定性、20 次 Contract Repeatability、Vet、Build、Linux Race 与集成测试；远端 CI 由本模块分支提交触发。
- 学习价值判断：写入。
- 判断理由：IR/DSL 职责、Execution ID、Source Map、Control Graph 激活语义和 Compiler SPI 都属于一旦错误便会污染所有历史发布版本的底层边界，也是面试中编译器、DAG 静态分析、插件化和确定性构建的高价值主题。

### 解决的问题

M2 把 M1 的作者意图转换为 Runtime 可独立执行的不可变契约。Runtime 不需要读取 Draft、IR、Layout 或 Node Description；结构性错误、Branch Route 错误和不安全数据引用在 Test/Publish 阶段失败，不能拖到 Worker 执行后才暴露。

### 核心边界与不变量

- Compiler 是纯 Domain Module，不导入 HTTP、PostgreSQL、Redis、Kafka 或任何 Adapter；
- DSL 与 IR 使用独立 Go Model，DSL 只保存 Execution ID、Operation、Binding、Output Contract 和最终 Execution Policy；
- 第一阶段保持一个 IR Node 对应一个 DSL Node，但 ID 命名空间仍分离；
- Control Edge 只编译为 `always` 或 `route` Activation，数据引用编译为 `node_output` Binding；
- Start/End/Branch 是 Control Operation，不创建 Attempt；Code/HTTP/RPC 是 Task Operation；
- Runtime 开始任何 Node 前扫描完整 DSL 的 Operation Version，不能执行一半才发现 Handler 不兼容；
- Source Map 覆盖每个 Execution Node、Edge 和可报告 Field；精确 Field 缺失时只回退到 Node，不猜测位置；
- 相同 IR、Catalog、Policy 和 Resource Bindings 必须产生字节级相同的 DSL、Source Map、Manifest 和 Hash。

### 编译流水线

```text
Strict IR + Catalog Validation
→ Control Graph Validation
→ Active/Reference Safety Analysis
→ Deterministic Execution ID
→ Policy + Resource Binding Resolution
→ Handler Registry 编译 Operation
→ DSL Self Validation
→ Full Operation Compatibility Check
→ Source Map Coverage Validation
→ Canonical JSON + Hash
```

任何阶段出现 Error Diagnostic 都停止产生执行产物。Compiler 不返回“部分可运行 DSL”，因为部分产物一旦被错误持久化，就会破坏 Published Version 的不可变性和可恢复性。

### DSL v1 为什么不是 IR 的复制

Code 的 `source_code` 从 IR Input 进入 `operation.config`，普通数据进入 Runtime `inputs`；HTTP 的 `connection_ref` 被授权后的稳定 `connection_id` 替代；RPC 固化 `service_id/contract_revision/idempotent`；Edge Route 变成强类型 Activation。IR 的 Title 与 Layout 完全不进入 DSL。

Literal Binding 保存 Canonical JSON；Ref Binding 使用：

```json
{
  "kind": "node_output",
  "data_type": "object",
  "output": {
    "node_id": "xn_...",
    "name": "payload"
  }
}
```

这使 Engine 只按 Execution Snapshot 工作，也让未来 IR 编辑体验演进时不必改写历史 Runtime 语义。

### `Active(Target) ⇒ Active(Source)` 如何实现

仅检查 Source 能到达 Target 不够。排他分支汇合后，Target 可能通过另一条 Route 激活，而 Source 所在 Route 未激活。M2 先用 DAG 位集合闭包检查 Source 确实是控制上游，再使用有序多值决策图 MDD 表达每个 Node 的激活条件：

```text
Start = true
普通 Edge = Active(Source)
Branch Edge = Active(Branch) AND SelectedRoute == Edge.Route
多入边 Node = OR(所有入边条件)
```

最后判断 `Active(Target) AND NOT Active(Source)` 是否存在可满足赋值。MDD 的 Unique Table 与 Apply Memo 共享等价子图，不枚举 Route 笛卡尔积；超过安全复杂度上限时失败关闭，不能近似放行。

经典 Dominator 不够，因为普通 Node 多出边会并行激活：并行节点可能始终一起运行，但彼此不在所有路径上。单纯穷举 Route 又会随独立 Branch 数量指数增长。

### Source Map 与错误定位

Source Map 是三个直接索引：

```text
nodes[execution_node_id] → logical_node_id
edges[execution_edge_id] → logical_edge_id
fields[execution_node_id][dsl_field] → ir_field
```

例如 Worker 报告 `operation.config.source_code`，Control Plane 可定位为 `inputs.source_code`；Worker 只报告 Execution Coordinate，不携带 Source Map 或 IR。字段不存在映射时保留 Node 定位，这比编造错误字段更可靠。

### 确定性 ID、Manifest 与 Hash

Execution ID 使用带 DSL Version 和对象类别命名空间的 SHA-256 截断值，分别加 `xn_`/`xe_` 前缀。它不依赖数据库发号、Node 数组下标或部署拓扑，并执行碰撞检测。

```text
ir_hash         = Hash(Canonical Full IR，包含 Layout)
dsl_hash        = Hash(Canonical DSL)
source_map_hash = Hash(Canonical Source Map)
definition_hash = Hash(三个 Hash + Compiler Manifest)
```

Manifest 固定 `compiler_version/catalog_revision/policy_revision`。只改 Layout 时，IR/Definition Hash 改变，但 DSL/Source Map Hash 不变；只改 Policy Revision 且最终 Policy 内容不变时，只有 Definition Hash 变化。这能区分“作者内容变化”“运行语义变化”和“编译解释坐标变化”。

### Compiler Handler SPI 与节点扩展

Compiler 使用 `node_type → Handler` Registry。Handler 声明 Node Type、Control/Task Kind、Operation Coordinate，并编译 Operation Config 与 Runtime Binding。Catalog 另行保存内部 Runtime Contract，Compiler 会检查两者一致。新增普通 Task Node 的路径是：

```text
Catalog Contract + Compiler Handler + DSL Operation Contract + Executor + Routing Policy
```

不修改 IR Validator 的中心 `switch-case`，也不修改 Engine 或 Scheduler。Start/End/Branch 属于 Control 语义，新增 Control Node 仍需要受控升级 Compiler 与 Engine。

### Managed Resource 与 Policy 输入

M2 不访问资源数据库。M3 将负责 Principal/Project 授权并把 `connection_ref/service_ref/model_ref` 解析为只含稳定 ID、Contract Revision、Digest 和幂等能力的 Resource Bindings。Compiler 只消费这个不可变值对象，因此既能固化 DSL，又不让 Secret、Endpoint 或外部 I/O 破坏确定性。

Execution Policy 来自 Catalog Default 与 Project Policy，不来自作者 IR。DSL v1 固化 Attempts、Recoveries、Attempt Timeout、固定 Backoff 和 Retryable Error Codes。默认采用保守单次业务 Attempt；Code 不允许业务自动重试，非幂等 HTTP/RPC 也不能被策略强行配置为多次业务 Attempt。

### 数据库、Redis 与 Kafka 在 M2 的角色

三者在 M2 都没有运行时角色：

- PostgreSQL 将在 M3 保存 IR/DSL/Source Map/Manifest/Hash 的不可变 Execution Snapshot；M2 只产生值对象；
- Redis 不能参与编译或 Hash，否则缓存命中、TTL 或实例切换可能改变发布产物；
- Kafka 不发送 Definition Event，也不承载 Compiler Pipeline；没有消费者的发布事件只会增加一致性负担。

这是“技术栈服务领域边界”的例子：简历可以展示 PostgreSQL、Redis、Kafka，但不能把它们硬塞进应当纯函数化的 Compiler。

### 一致性、安全与水平扩展

Compiler 无状态且输出确定，同一请求可以在任意 Control Plane 实例重复执行并得到相同 Hash，因此天然支持水平扩展。真正的 Publish 幂等与 Snapshot 事务在 M3 完成；M2 不通过 Redis 锁或 Kafka 顺序制造伪一致性。

安全方面，作者 Resource Ref 必须先变成已授权稳定绑定，Secret 没有进入 DSL 类型的表达方式；Runtime DSL 会重新检查容器、Binding、Operation Config、图结构和全部 Operation Version。Source Map 缺失、Compiler/Catalog 坐标不一致、ID 碰撞和分析复杂度超限都失败关闭。

### 高频面试题

#### Q：既然第一阶段 Node 一对一，为什么还要 DSL？

一对一只描述节点数量，不代表字段语义相同。Compiler 需要固化 Operation Version、资源 ID、执行策略、强类型 Binding 和 Edge Activation，并移除 Layout/Title。Runtime 直接执行 IR 会同时耦合作者体验、Catalog 当前版本和基础设施解析，历史发布版本无法稳定复现。

#### Q：为什么 Source Map 不直接塞进 Kafka Task？

Worker 只需执行当前 Attempt 并报告 Execution Coordinate。Source Map 属于 Definition Snapshot，放进每个 Task 会放大消息、泄漏作者结构并产生多份一致性副本。Control Plane 在错误返回 Web/CLI 前统一增强即可。

#### Q：为什么不能只检查 DAG 和 Ref Source 可达？

可达只证明存在一条 Source 到 Target 的路径，不证明 Target 每次激活时 Source 都激活。排他分支的另一条 Route 可以绕过 Source，因此还必须证明激活蕴含关系。

#### Q：Compiler 为什么不查数据库或 Redis？

外部 I/O 会让相同输入受瞬时状态影响，破坏可重复构建。应用层先把授权后的 Catalog、Policy、Resource Bindings 固化为输入值，Compiler 再纯函数化生成产物；数据库事务负责保存，不参与语义计算。

#### Q：Operation Version 和 Executor Build Version 有何区别？

Operation Version 是不可变运行语义坐标，不兼容变化必须升级；Executor Build Version 是实现构建，用于审计和修复，同一 Operation Version 下不能改变可观察语义。Runtime 必须先检查 Operation Version，不能依赖“最新 Worker 大概兼容”。

### 一分钟讲法

M2 把作者态 IR 编译为 Runtime 独立的 DSL v1，同时生成 Source Map、Compiler Manifest 和四类 Hash。Compiler 是无基础设施依赖的确定性 Domain Module；Task Node 通过 Handler Registry 扩展，不靠中心 Switch。Control Graph 在发布前检查单入口单出口 DAG、Branch Route、OR-Join 和数据引用激活蕴含，后者用多值决策图精确分析。Runtime 在执行前自校验完整 DSL 和 Operation Version，Worker 错误再通过 Source Map 精确回到 IR 字段。100 次重复编译、Golden、Schema、Source Map 覆盖和架构依赖测试共同固定了这条边界。

2. 展开 Operation Config、Runtime Binding、Edge Activation 与 Execution Policy；

### 易错点与追问

## 8. M3：Access、Managed Resources 与 Definition 生命周期

- 验收状态：已通过 Unit、Contract、Architecture、Linux Race、真实 PostgreSQL 并发/故障注入及完整 Compose Integration 验收。
- 学习价值判断：写入。
- 判断理由：M3 把 M1-M2 的纯契约接入权威持久化，集中体现多租户隔离、乐观并发、不可变版本、事务原子性、请求幂等、资源双重授权和水平扩展边界，是数据库与分布式一致性的高频面试内容。

### 解决的问题

M3 建立从 Human Web/Agent CLI 共用 Draft IR 到不可变 Execution Snapshot 和 Published Version 的 Definition 闭环。它只负责“执行什么”，不创建 Workflow Run，也不推进 Node 状态；因此定义编辑故障不会污染 Runtime，历史发布版本也不会随最新 Catalog、资源元数据或 Draft 变化。

### 核心模型与不变量

- `Workflow` 是稳定业务身份，`Draft` 是可变 Pointer，`Draft Revision` 是每次保存产生的不可变作者事实；
- `Execution Snapshot` 固化 IR、DSL、Source Map、Compiler Manifest 与 Hash，`Published Version` 只引用 Snapshot；
- Publish 永远自动激活新版本；Rollback 不复制或修改 Version，只原子移动 Active Pointer；
- Production Definition Resolution 没有 Active Version 时返回 `WORKFLOW_NOT_PUBLISHED`；
- Copy 读取原 Version 保存的 IR Snapshot 创建目标 Workflow 的 Draft Revision 1，不做 DSL→IR 反编译；
- Test 与 Publish 对同一 Draft Revision 调用完全相同的资源解析和 Compiler Pipeline；Test 目前只生成 Snapshot，不冒充真实 Test Run。

### Draft 保存为何采用不可变 Revision + 乐观锁

前端画布和 Agent 可能同时基于 Revision N 修改。`SaveDraft(expected_revision=N)` 在事务中锁定 Draft Pointer，只有当前仍为 N 才插入 N+1 并移动 Pointer；另一方得到 Revision Conflict，不能静默覆盖。

保存阶段只解析和 Canonicalize 有界 IR 外壳，允许用户暂存未接完的画布。严格 Schema、Catalog、Control Graph、资源引用和数据依赖校验留在 Validate/Test/Publish，避免“可保存”与“可执行”混成同一个状态。

### Publish 的事务与幂等设计

编译是无状态且可能耗时的纯计算，不应长时间占用数据库事务。Publish 先完成权限检查，按不可变 Draft Revision 解析 Resource Binding 并编译；最终短事务再次校验 Revision，然后原子完成：

```text
Execution Snapshot（按 Definition Hash 复用）
→ Published Version（Workflow 内单调 Version Number）
→ Active Version Pointer
→ Publish Audit
→ Idempotency Result
```

任一步失败，整个事务回滚，不会出现“有 Version 没 Snapshot”或“Pointer 已移动但 Audit 缺失”。同一 Idempotency Key 绑定 Request Hash：相同请求返回原结果，不增加 Version；不同请求复用同一 Key 明确冲突。

客户端可能在服务端已提交后超时。重放请求通过身份授权后，会在重新解析资源和编译前读取已完成结果；即使资源 Grant 随后被撤销，也能返回原 Version。并发的首次到达则由 PostgreSQL Transaction Advisory Lock、事务内重查和唯一约束收敛。Redis 锁不能替代这一设计，因为锁过期、故障切换与数据库提交之间无法原子化。

### Managed Resource 为什么需要双重授权

Connection 与 RPC Service 同时检查：

1. 作者 Principal 是否有 `connection.use` / `service.use`；
2. Project Execution Identity 是否被授予 Test/Production 执行权限。

前者回答“谁可以把资源写进定义”，后者回答“运行时以什么身份使用资源”。二者分开后，编辑权限不会自动变成生产凭证权限。不可见或跨 Project 资源统一返回 `RESOURCE_NOT_FOUND`，避免枚举；Compiler 只接收稳定 ID、Contract Revision、Digest 等 Binding，Secret 和 Endpoint 永远不进入 IR/DSL/Snapshot。

### PostgreSQL、Redis 与 Kafka 在 M3 的角色

- PostgreSQL 是 Principal、Project、Resource Metadata、Draft、Snapshot、Version、Pointer、Audit 与 Idempotency 的唯一权威来源；事务、外键、唯一约束和 Trigger 共同维护不变量；
- Redis 在 M3 不参与权威写入，也不做分布式锁。不可变 Snapshot 的 Cache-Aside 会在 Runtime 高频读取阶段引入，但 Cache Miss 必须回源 PostgreSQL；
- Kafka 在 M3 没有消费者，因此不发送 Definition Event，也不写无消费者的 Definition Outbox。M5 起 Kafka 只承载 Runtime 状态推进相关事件，不能成为 Definition 权威存储。

这体现“按问题选择技术栈”：为了简历把 Redis/Kafka 硬塞进 Publish，只会增加双写、失效和恢复问题，并不会提升正确性。

### 一致性、安全与水平扩展

Control Plane 无会话状态，可多副本部署；UUIDv7 避免中心 ID 服务，Repository 查询始终携带 `project_id`，复合唯一约束与复合外键防止 Adapter 漏条件后发生跨 Project 关联。未来 Definition 数据可按 `project_id + workflow_id` 路由。

同一 Workflow 的 Draft Pointer 和 Publish Version Number 是必须串行化的小粒度热点，但不同 Workflow/Project 互不竞争。当前使用行锁和 Workflow 内 `MAX(version_number)+1` 足以保证正确性；只有单 Workflow 发布吞吐成为真实瓶颈时，才值得改成受约束计数器，不能提前用 Redis 分号破坏事务。

历史 Draft 绑定 `catalog_revision`，通过 Catalog Registry 选择相应编译契约；新增 Catalog 不会让旧 Draft 被“最新节点定义”重新解释。Published Snapshot 已固化完整运行契约，因此 Runtime 更不依赖当前 Registry。

### 高频面试题

#### Q：为什么 Draft 不直接覆盖一行 JSON？

覆盖一行无法可靠处理 Web 与 Agent 并发编辑，也丢失可审计的保存事实。不可变 Revision 保留历史，Pointer 提供当前视图，expected revision 让冲突显式化；成本只是多行存储，而 IR 在第一阶段是小 JSON。

#### Q：为什么 Publish 不把编译全过程放在数据库事务中？

Compiler 只依赖不可变输入，适合事务外计算；最终事务重新检查 Draft Revision 并原子保存结果。这样既避免长事务占用连接和锁，又不会发布已经漂移的 Draft。

#### Q：为什么不能用 Redis 实现 Publish 幂等和版本号？

Publish 的成功事实、Version、Pointer 与 Audit 都在 PostgreSQL。Redis 锁或计数器与数据库没有共同事务，崩溃时会出现锁已释放但事务未知、号已分配但 Version 未提交等分裂状态；数据库锁、唯一约束和 Idempotency Row 才能与业务事实原子提交。

#### Q：Test Snapshot 和 Test Run 有什么区别？

Test Snapshot 证明某个 Draft Revision 已通过资源解析与编译，并保存不可变执行材料；Test Run 还必须创建 Run/Node Run/Attempt 并由 Engine 推进。M3 只有前者，后者属于 M4-M5。

### 一分钟讲法

M3 将 Human 与 Agent 共用的 Draft IR 接入 PostgreSQL 权威生命周期：Draft 用不可变 Revision 加 Pointer，SaveDraft 通过乐观锁防止覆盖；Test 与 Publish 共用绑定 Catalog Revision 的 Compiler，产出不可变 Snapshot。Publish 使用 Request Hash 和数据库 Advisory Lock 幂等，并在一个短事务中提交 Snapshot、Version、Active Pointer、Audit 与结果。Connection/RPC 同时校验作者和 Project Execution Identity，Secret 不进入 DSL。Redis/Kafka 此阶段没有必要角色，避免为展示技术栈制造双写。真实 Workflow Run 从 M4-M5 开始。

### 五分钟展开提示

1. 从 Definition 与 Runtime 分离讲为什么 Run 只能绑定不可变 Snapshot；
2. 用 Web/Agent 并发编辑说明 Draft Revision、Pointer 和 CAS；
3. 展开事务外确定性编译与事务内 Revision 二次校验；
4. 用客户端超时重放说明 Idempotency Result 的查询顺序和 Request Hash；
5. 解释 Version/Pointer/Audit 原子性、故障注入测试和数据库 Trigger；
6. 说明作者权限与 Execution Identity Grant 的差异；
7. 解释 Redis/Kafka 为何暂不介入，以及未来 Cache-Aside/Runtime Event 的位置；
8. 最后说明 `project_id` 复合约束、无状态 Control Plane 和未来分片键。

### 易错点与追问

- SaveDraft 成功不表示 Workflow 可执行；严格校验发生在 Validate/Test/Publish；
- Publish 自动激活，但 Latest Version 与 Active Version 仍是两个概念；Rollback 只移动 Active Pointer；
- Snapshot 内容可按 Definition Hash 复用，但 Published Version 仍是独立不可变业务事实；
- Published Version 不可更新/删除；被 Version 引用的 Snapshot 不可删除，未引用 Test Snapshot 可后续回收；
- Idempotency Replay 必须先验证调用者权限，但不能重新要求已提交请求的资源授权仍然存在；
- Copy 使用保存的 IR Snapshot；第一阶段明确没有 DSL Upload 和 DSL→IR Decompiler；
- 第一批 API 是 Definition API，不包含 Project/Principal 管理面，也不包含真实 Run API；
- Catalog Registry 兼容旧 Draft，Published Runtime 则直接执行固化 DSL，不读取当前 Catalog。

## 9. M4：Runtime Domain 与 Engine

- 验收状态：已通过全量状态迁移矩阵、并行/Branch/OR-Join/Skipped、重试与恢复、重复乱序、终止竞争、20 个代表性 Workflow、100 个随机合法 DAG Property Test、全仓 Unit/Architecture 验收。
- 学习价值判断：写入。
- 判断理由：M4 是 Workflow Runtime 的语义核心，集中体现状态机封装、事件幂等、控制流激活、Effective Output、Fail-Fast 和终止竞争；它决定后续 PostgreSQL、Kafka、Scheduler 和 Worker 能否在不重写业务规则的前提下水平扩展。

### 解决的问题与边界

M4 回答“一个不可变 Snapshot 应当如何执行”，但暂不回答“状态存在哪里、事件怎样传输、任务由谁执行”。Runtime Domain 保存 Run/Node Run/Attempt 的合法状态和不变量；Engine 读取 DSL、解释控制图并调用领域操作；Deterministic Harness 只注入 Attempt Fact。M5 才把这些操作映射为 PostgreSQL Transaction/CAS 与 Outbox/Inbox。

### 三层状态模型

- Workflow Run：`pending → running → succeeded/failed/canceled/timed_out`，节点重试期间仍为 Running；
- Node Run：Task 经 `pending → ready → queued → running`，之后成功、失败、超时、取消或进入 Retry Wait；Control Node 从 Pending 直接结算且永不创建 Attempt；
- Node Attempt：物理执行身份，`queued → running → terminal`；`attempt_seq`、业务 Attempt Count 和 Recovery Count 语义分离。

状态字段保持私有，所有迁移只能走明确领域操作。每次有效变化增加 State Version，为 M5 的数据库 CAS 留出稳定契约；重复事实不增加版本，非法迁移返回结构化 Transition Error。

### Control Graph 如何在 Runtime 推进

Start 将 Run Input 暴露为 `workflow_input` 并激活全部出边。普通 Task 成功后激活全部出边。Branch 按 DSL Cases 顺序求值，第一个匹配 Route 胜出，只激活该 Route 的边；六种 JSON 顶层类型和有限 Operator 使用 Decimal/递归结构相等，不做隐式类型转换。

多入边 Node 等待全部直接入边结算：全 Inactive 才 Skipped，至少一条 Active 则只激活一次。激活后还要等待全部必填 Ref Source 成功才能 Ready。失败或取消造成的未执行 Node 使用 Canceled，不伪装成 Skipped。

### Effective Attempt 与 Output

Attempt Completion 只是候选事实。Engine 先校验它仍是 Current Attempt，再按 DSL Output 名称和类型验证结果；只有成功接受后，Node Run 才同时设置 `effective_attempt_id` 和 Effective Outputs。下游只读 Effective Outputs，因此重复、旧 Attempt 或格式错误结果不会污染变量池。

稳定外部幂等键是 `run_id:execution_node_id`，同一 Node 的业务 Retry 和 Recovery 共享它；物理 Attempt ID 只用于 Fencing 和审计。

### Retry、Recovery 与乱序

Retryable Error 且未耗尽 `max_attempts` 时进入 Retry Wait，并按 DSL 固定 Backoff 持久化语义上的 `next_retry_at`；时间到达后的 RetryDue 才回到 Ready。Attempt Lost 使用独立 `max_recoveries`，不消耗业务重试预算。Worker 不自行 Sleep 重试。

旧 Attempt 的迟到 Completion 在修改 Attempt/Node 前就被 Current Attempt 检查拒绝；相同终态 Completion 重放幂等，不同结果重放失败；已进入新 Attempt 后的迟到 RetryDue 是 No-op。正确性不依赖 Kafka 顺序，这正是 M5 至少一次事件模型的前提。

### Fail-Fast 与终止竞争

节点最终失败首先写入 Failed Termination Intent，立即停止产生新 Ready Node；Pending/Ready/RetryWait Node 取消，Queued/Running Attempt 等待终态或取消确认。用户取消和 Workflow Deadline 使用同一 Intent 模型，第一个成功写入者决定最终 `failed/canceled/timed_out`，后续竞争事件不能覆盖。

Run Succeeded 不是“End 到达就成功”：必须没有 Termination Intent，End 已激活，所有其他 Node 均为 Succeeded 或 Skipped，并将 End Succeeded、Workflow Output、Run Succeeded 建模成一个不可分领域操作。M5 会把它实现为单个 PostgreSQL Transaction。

### PostgreSQL、Redis 与 Kafka 在 M4 的角色

三者都不参与 M4 执行。M4 是确定性领域语义：PostgreSQL 会在 M5 承载权威状态、CAS 和原子事务；Kafka 会在 M5/M7 传递至少一次唤醒事件与 Task，但事件不是状态；Redis 从 M6 起只负责公平调度和后续 Cache-Aside。把这些设施提前塞入 M4 会让状态机难以穷举测试，也会把技术故障误当成业务状态。

### 一致性、安全与水平扩展

Engine 只消费深拷贝的 DSL Snapshot，初始化前检查完整 DSL 和 Operation Compatibility，不导入 IR、Definition 或 Catalog。Runtime Failure 保存 Run、Snapshot、Definition Hash、Execution Node/Edge、Attempt、Phase 与 DSL Field 坐标，接口层再用 Source Map 增强 IR 坐标。

Engine 本身不靠单进程内存所有权保证并发；M4 的 State Version、幂等操作和 Current Attempt 检查是 M5 数据库行锁/CAS 的语义依据。未来多 Engine 实例只是竞争同一权威状态，不能各自在内存中独占一个 Run。

### 高频面试题

#### Q：为什么需要 Node Run 和 Attempt 两层？

Node Run 表示业务语义执行一次，Attempt 表示一次物理执行。网络错误和 Worker Lost 可以创建新 Attempt，但不能让下游看到两份 Output，也不一定消耗业务 Retry。只有 Current Attempt 被 Engine 接受后才成为 Effective Attempt。

#### Q：Kafka 保证同 Partition 顺序后，为什么还处理乱序？

重试、消费者重平衡、补偿扫描、Outbox 重放以及多个事件来源都会产生重复或相对乱序；Partition 顺序只是优化，不是数据库事实。Current Attempt、State Version、Inbox 和幂等领域操作才构成正确性。

#### Q：为什么 End 成功不能直接让 Run 成功？

另一条并行路径可能已经失败或仍在运行。只看 End 会让成功路径掩盖失败。Run Success 还必须检查无终止意图、全部 Node 已结算和 Output 已固化，并在一个事务提交。

### 一分钟讲法

M4 在没有数据库和消息系统的条件下实现 Runtime 语义核心：Run、Node Run、Attempt 使用封闭状态机和 State Version；Engine 只解释不可变 DSL，处理 Branch、OR-Join、Skipped、Output Binding、Retry/Recovery 和 Fail-Fast。Attempt Result 只有在仍是 Current 且输出符合 DSL 后才能成为 Effective Output；取消、失败和超时用首个 Termination Intent 收敛。20 个 Workflow Fixture 和 100 个随机 DAG 证明重复、乱序、迟到事件不会制造双输出或非法终态。M5 只需把同一语义落到 PostgreSQL CAS 与 Outbox/Inbox。

### 五分钟展开提示

1. 从 Definition Snapshot 与 Run Binding 讲 Runtime 不读取 IR；
2. 展开 Run/Node Run/Attempt 三层状态与 State Version；
3. 用排他 Branch、OR-Join 和 Skipped 解释控制边结算；
4. 用 Current/Effective Attempt 解释重复输出隔离；

### 易错点与追问

- M4 Engine Harness 不是生产内存 Repository，也不表示已有真实 Run API；
- Control Node 有 Node Run，但没有 Attempt；Scheduler 只看 Ready Task Node；
- Skipped 只表示全 Inactive 控制路径，失败/取消/超时使用 Canceled；
- Attempt Succeeded 不等于 Node Succeeded，必须先通过 Current Attempt 和 Output Contract；
- `max_attempts` 包含首次业务 Attempt，不包含 Lost Recovery；
- Run Timeout 只来自 Workflow Deadline；Attempt Timeout 耗尽后通常令 Run Failed；
- Branch 嵌套字段类型在 Runtime 才能确定，类型错配必须失败，不能走 Default；
- M4 的 State Version 是 CAS 契约，但真正的并发锁、Inbox 和事务原子性由 M5 实现。

## 10. M5：Runtime PostgreSQL、Outbox/Inbox 与事件驱动推进

- 验收状态：已通过 CreateRun 来源/幂等、初始化逐语句故障、12 Engine 并发竞争、8 Worker Claim 竞争、Attempt 两阶段接受、100 次事件重放、乱序/迟到、Relay 双崩溃窗口、Lease/Fencing 和 SQL 索引计划测试；定向加固后 Engine 90.5%、Compiler 90.2%、Attempt/Lease 97.5%、Eventing 100.0%，并通过全仓 Unit、Race、20 次稳定性、Integration 与静态检查。
- 学习价值判断：写入。
- 判断理由：M5 集中体现 PostgreSQL 事务、CAS、Outbox/Inbox、Lease/Fencing 和至少一次事件如何组合成可恢复 Workflow Runtime，是数据库、Kafka 与分布式一致性的高频面试主题。

### 从 M4 语义到数据库事实

M5 没有在 PostgreSQL Adapter 复制第二套状态机。Runtime Aggregate 暴露只读 `Snapshot` 和受不变量校验的 `Restore`；Engine Consumer 在一个 Run 事务中写 Inbox、锁 Run/Node/Attempt 行、从 Snapshot 恢复 M4 Aggregate、调用明确领域操作，再用旧 State Version 做 CAS 写回。数据库拥有事实与并发裁决，Engine 仍唯一拥有 Run/Node Run 语义。

Edge State 不单独落表，因为它可由不可变 DSL、Source Node 终态与 Branch Selected Route 确定重建。Start 的 Workflow Input 属于 Run 权威数据，恢复时按 Start DSL Contract 投影，不创建另一份漂移副本。

### CreateRun 为什么拆成两个事务

外部 CreateRun 事务只完成：来源校验、Idempotency Result、Pending Run 和 RunCreated Outbox。它不在 API 请求内创建整张 Node Run 图，避免大 Workflow 拉长 API 锁时间。Engine 收到 RunCreated 后，另一个事务完成 Operation 全量兼容性预检、所有 Node Run 批量初始化、Start 推进和 Run Running；任何语句失败都会连 Inbox 一起回滚，外部永远看不到半张 Running 图。

TestDraft 编译写入不可变 `draft_revision_id ↔ snapshot_id` 关系；创建 Run 携带确定的 `draft_revision_number + snapshot_id` 并精确校验该绑定。不能只看 `origin_kind`：相同 Definition Hash 的 Snapshot 可被 Test/Publish 复用，其最初来源不等于本次 Run 的调用来源；也不能靠 IR/Catalog 近似匹配，因为资源绑定或 Policy 变化可能让同一 Revision 产生不同 Snapshot。Production CreateRun 则在事务内解析 Active Published Version；Run 建立后只绑定 `snapshot_id + definition_hash + definition_source`，后续 Active Pointer 变化不影响它。

### Attempt Completion 为什么是两阶段接受

Attempt Coordinator 事务校验 `attempt_id + attempt_seq + lease_token + fencing_token + running state`，原子写 Attempt 终态、按 Attempt 保存的 Output Candidate 与 Completion Outbox。此时 Node Run 仍是 Running，Output 还不可见。

Engine 消费 Completion Event 后通过 Inbox 去重，重新从 PostgreSQL读取 Attempt Result，确认它仍是 Current Attempt，并按 DSL 输出契约验证；成功后才 CAS 设置 `node_runs.effective_attempt_id` 并推进下游。下游回源查询固定联接这个指针，因此迟到旧 Attempt 即使留下 Candidate，也不能覆盖有效值。

### Outbox/Inbox 与崩溃窗口

Outbox 与业务事实位于同一 Project/Run 数据分片和事务。Relay 用 `FOR UPDATE SKIP LOCKED` 批量 Claim，保存 Owner、Token 与到期时间：

- Publish 前崩溃：业务事实和 Outbox 已提交，Claim 释放或过期后重新发布；
- Publish 成功、MarkPublished 前崩溃：同一 Event 会再次发布，这是预期的至少一次语义；
- Consumer 在业务事务内先插入 `UNIQUE(consumer_name,event_id)` Inbox；失败则 Inbox 回滚，成功后重复 Event 不再产生第二次业务效果。

因此 Kafka 不是跨 PostgreSQL 的 Exactly-Once 事务协调器，也不是权威状态。M5 只提供版本化 Runtime Event DTO、Publisher Port 与 Relay；真实 Kafka Adapter 在 M7 接入。测试中的重复、乱序和发布崩溃模拟的是 Kafka 至少一次行为，不是假装 Broker 已完成。

### Lease、Fencing 与多实例

多个 Engine 实例不永久拥有 Run；同一 Event 通过 Inbox 唯一键与 Run 行锁收敛。多个 Worker 竞争同一 Queued Attempt 时，只有一个数据库 CAS 能建立 Running Lease。`attempt_seq` 是物理执行序号，Fencing Token 与 Lease Token 共同拒绝旧 Worker Heartbeat/Result；数据库服务端时间决定 Lease 是否过期，Worker 本地时钟不参与裁决。

Outbox Relay、Engine Consumer 和 Attempt Reaper 都可以水平扩展。所有 Runtime Repository 调用都必须携带 `project_id + run_id`，为未来按 Project 分库保留稳定路由；Outbox/Inbox 与 Run 同分片，不需要跨项目分布式事务。第一阶段不做 Table Partition，也不建立通用 JSONB GIN，而是验证 Ready、Retry、Lease 与 Outbox 的 Partial B-Tree Index 访问路径。

### PostgreSQL、Redis、Kafka 的角色

- PostgreSQL：Run/Node Run/Attempt、Lease/Fencing、Output Candidate/Effective Pointer、Idempotency、Outbox/Inbox 的唯一权威；事务、行锁、CAS 与唯一约束保证正确性；
- Kafka：M5 只冻结轻量 Runtime Event Contract 与 Publisher Port，M7 才接 Broker；它用于唤醒和传输，不携带 DSL/Context/Output，也不决定最终状态；
- Redis：M5 不参与写入正确性。M6 用 Scheduling Redis 做可重建公平协调，M7 用 Cache Redis 做 Execution Context Cache-Aside；Redis 不存权威 Lease、Effective Output 或 Inbox。

### 性能与水平扩展

CreateRun 短事务与 Engine 图初始化长事务分离，Outbox Relay 使用小批次 Claim，Inbox/Outbox 均可多副本。热点边界是单个 Run：同一 Run 的语义必须串行裁决，而大量 Run 可按 Project/Run 并行。极大单图的批量初始化事务是已知上限，后续需要用容量测试约束单 Workflow Node 数，而不是牺牲“完整图原子可见”不变量。

### 高频面试题

#### Q：为什么用了 Kafka 还需要 Outbox 和 Inbox？

数据库事务不能和普通 Kafka Publish 原子提交。没有 Outbox，会出现数据库成功但消息丢失，或消息成功但数据库回滚；没有 Inbox，至少一次重投会重复推进。Outbox 把“待发布”变成同事务数据库事实，Inbox 把“已处理”放进业务事务，CAS/状态机再处理乱序。

#### Q：Attempt Succeeded 后为什么 Node 还不能立即 Succeeded？

Attempt 是物理执行候选，可能已经过期或不再是 Current。Coordinator 只负责可靠保存 Result；Engine 才能结合 Workflow DSL、Current Attempt 和 Output Contract 决定它是否成为 Effective Output。分两阶段才能同时保留审计事实并隔离迟到结果。

#### Q：行锁和 CAS 为什么同时使用？

行锁让一次事务读取到一致的 Run Aggregate 并串行化同 Run 推进；CAS 用旧 State Version 表达领域前置条件，防止未来修改锁范围、恢复扫描或跨事务调用时静默覆盖新状态。锁是并发机制，CAS 是显式业务契约，二者职责不同。

#### Q：行覆盖率没有 100%，是否代表交付质量不高？

不是。行覆盖率只说明语句是否执行过，不证明断言有效，也不覆盖所有状态组合、并发时序和故障窗口。M5 的质量门槛是“核心包不低于 90% + 关键不变量场景必须有测试”：重复/乱序事件、Current Attempt、Lease/Fencing、CAS 冲突、事务回滚和崩溃恢复都要有明确断言。不可由合法公开契约到达的防御分支不应通过伪造内部损坏状态来追求 100%；这类状态应由 Aggregate Restore 拒绝。覆盖率用于发现盲区，不能代替场景、Race、Integration 与故障注入测试。

### 一分钟讲法

M5 将 M4 状态机落到 PostgreSQL：CreateRun 只原子写 Pending Run 与 RunCreated Outbox，Engine 用 Inbox、Run 锁和 CAS 在独立事务一次性初始化整张图。Attempt Coordinator 用 Lease/Fencing Claim，并把 Attempt 终态、Output Candidate、Completion Outbox同事务提交；Engine 只有确认 Current Attempt 后才设置 effective_attempt_id。Relay 允许发布后未标记导致重复，Consumer 通过 Inbox 和状态机收敛。Redis 不参与正确性，真实 Kafka Adapter 留到 M7。故障注入、100 次重放和多实例竞争证明崩溃可恢复且业务效果一次。

## 11. M6：Project 公平 Scheduler 与 Scheduling Redis

- 验收状态：初始 M6 的 Max-Min/Lane/Credit 方案曾通过当期验收；2026-08-27 完成目标算法重构，并通过全仓 Unit/Vet/Build、20 次核心稳定性测试、Linux Race、核心包 90% 覆盖率门禁、真实 PostgreSQL/Redis/Kafka 集成、Docker Sandbox 与完整 Compose E2E。60/15/15 分钟目标环境容量报告仍未完成，因此不能称为 Production Ready。
- 学习价值判断：写入。
- 判断理由：当前设计体现了负载模型驱动的 FIFO/公平折中、Redis 原子协调、数据库最终裁决、五秒 Kafka 缓冲和可重建派生状态，是 Redis、数据库与分布式系统面试的核心案例。

### 当前实现：一秒 FIFO、Project Load 与五秒窗口

Scheduler 对 Builtin/Sandbox 分别准入，但两个 Topic 共享 `Project Load = Reservation + Queued + Running`。候选先比较一秒 `ready_at` 时间桶；同桶内选择 Project Load 最低、最近准入最早的 Project，Project 内再按 `priority DESC, ready_at ASC, node_run_id ASC`。因此持续到来的小项目不能越过更早时间桶，大项目的后继节点也不会长期饥饿；Project Load 只负责打散同一秒的并发突发，不是长期配额。

Builtin/Sandbox 各自维护 `Topic Queue Window = clamp(Worker 完成速率 EWMA × 5 秒, min, max)`。窗口占用只包含未确认 Reservation 与 Queued Attempt。Claim 提交后释放 Topic Occupancy，允许 Scheduler 立即补充 Kafka 缓冲；Running 仍计入 Project Load，直到 Attempt 终态才释放。Lost 不计入有效完成速率。

Scheduling Redis 使用 `noeviction`，业务生命周期主动删除过期 Reservation、Claim 后的排队占用和终态 Inflight。达到高水位后停止写入新 Candidate/Reservation，只排空已有状态；降到恢复水位后再从 PostgreSQL 权威快照重建并恢复准入。Redis 只保存可重建协调状态，`ready → queued + Attempt + Task Outbox` 仍由 PostgreSQL CAS 最终裁决。

### 历史实现回顾：Max-Min、Lane 与 Credit

以下内容用于解释初始 M6 为什么选择过 Max-Min/Lane/Credit，以及本次重构减少了哪些协调成本；它不再描述当前代码。

### 公平性如何计算

公平身份只有 `project_id`。每个 Epoch 从 PostgreSQL 权威快照读取仍有 Ready 需求的 Project，以及其 Queued/Running Inflight。Planner 使用 Progressive Filling：总是给当前 `inflight + 本 Epoch 已授予` 最小且仍有需求的 Project 下一个额度，因此得到等权 Max-Min；需求不足的 Project 自动退出竞争，空闲容量被其余 Project 借用。新 Project 加入后，既有 Attempt 不被抢占，Inflight 已高的 Project 停止获得新 Credit，直到差距收敛。

同一 Project 内不是无序选择，而是 `priority DESC, ready_at ASC, node_run_id ASC`。平局 Project 的起点随 Epoch 轮转；否则 Window 小于 Project 数时，固定字典序会长期饿死尾部 Project。

权威快照不会把每个 Project 的全部 Ready 队列搬进 Control Plane，而是按上述稳定顺序对每个 Active Project 最多读取一个 Global Dispatch Window。这个上限仍允许“一个项目只有 1 个任务、另一个项目承担剩余窗口”的空闲借用；若简单读取 `window / project_count` 条，则前者未使用的份额无法由后者补满，会破坏 Work-Conserving。

### Lane 和 Credit 为什么能水平扩展

`lane_id = fnv1a(project_id) & (lane_count-1)`，Lane Count 必须是 2 的幂。每个 Lane 使用 Redis Cluster Hash Tag，共享固定的 Ready Hash、Active Project ZSet、Project Credit Hash、Grant Queue、Reservation Hash 和 Expiry ZSet；Lua 脚本的所有 Key 都显式同槽。每个 Task 的候选选择、Credit 扣减和 Reservation 建立只访问一个 Lane，跨 Lane 仅由 Credit Balancer 每 Epoch 批量汇总和发放，不制造每 Task 全局热点。

Credit Balancer 的 Redis Lease/Fencing 只决定谁能重建 Lane 和发放额度，不独占调度执行。Fencing 基值取 Redis 服务端微秒时间，并与 Redis 内计数器取单调最大值；即使 Redis Key 全量丢失，新 Epoch 也不会回退到旧 token。非 Leader Scheduler 仍可消费 Leader 已发放的共享 Credit，并共同竞争 PostgreSQL CAS，因而增加 Scheduler 实例能提高 Admission 并发，而不是只增加热备。

### Dispatch Window 与 Reservation

`admitted = queued + running + 未落库 reservation`，不得超过 Global Window；Pool Window 只检查目标 Resource Class 的短期可行性，不形成第二套公平身份。Window 由健康 Worker Slot 乘 Buffer Factor 得出，并在 Redis Balancer State 中限制每 Epoch 的上调幅度，避免容量探测抖动造成瞬时深度预派发；容量下调立即生效，不能在 Worker 槽位已经消失时为“平滑”而继续派发。

Redis `ReserveNext` 原子消费一条 Project Credit、取出该 Project 的首个候选并按 `attempt_id` 建立带 TTL Reservation。数据库随后在短事务内锁定 Ready Node、再次验证 Operation Routing 和 State Version、调用领域 `QueueAttempt`，原子写 Queued Attempt、Node Run CAS 与 Node Task Outbox。Reservation 成功后标记 Confirmed；Rebalance 只为 PostgreSQL 仍存在的 Queued/Running Attempt 续期。未确认 Reservation 不会被无限续期，进程在 Reserve 后、数据库提交前崩溃时，TTL 到期后 Ready Node 会重新进入调度。

### Redis 丢失为什么不会破坏正确性

Scheduling Redis 不保存权威 Workflow State。Redis 为空或不可用时 Lane 默认 Paused，不允许新准入。获得 Balancer Lease 的实例依次暂停所有 Lane，合并数据库 Inflight 和尚未落库的 Reservation，重建 Ready/Active/Reservation，批量授予 Credit，最后才开放 Lane。Redis 全量丢失只影响短期可用性；PostgreSQL Ready/Queued/Running、Attempt 与 Task Outbox 不丢失，数据库 CAS 仍阻止重复 Attempt。

### Operation Routing 为什么落在 Node Run

IR/DSL 不携带 Topic 名；Runtime Router 根据版本化 DSL Operation 解析 `builtin` 或 `sandbox`。Run 初始化时把 `operation_type + operation_version + resource_class` 作为不可变运行元数据落到 Node Run，避免 Scheduler 每 Epoch 展开 Snapshot JSON。Scheduler 读取该投影后仍用 Router 复核，新增 Node Type 只扩展 Catalog/Compiler/Router/Executor，不修改 Scheduler 中央流程。

### PostgreSQL、Redis、Kafka 分工

- PostgreSQL：Ready/Queued/Running、Attempt、Task Outbox 与 CAS 的唯一权威；
- Scheduling Redis：可丢失的 Ready 加速索引、Lane、Credit、Window 和 Reservation；不 Write-Behind；
- Kafka：M6 尚未发布 Task。M7 将从 `node_task_outbox` 可靠发布到 Resource Class Topic；Broker 积压不能反向替代公平准入。

### 高频面试题

#### Q：既然 Redis 已经原子扣 Credit，为什么 PostgreSQL 还要 CAS？

Redis 只看到派生候选，可能因重建延迟、进程崩溃或并发 Epoch 变旧。PostgreSQL 才知道 Node 是否仍为相同 State Version 的 Ready。Redis 决定“谁获得尝试准入的资格”，数据库 CAS 决定“这次业务状态迁移是否成立”。前者失败可重试，后者是最终裁决。

#### Q：为什么不使用一个全局 Redis Sorted Set 做公平调度？

全局 Key 会让全部 Scheduler 的每 Task 操作竞争同一 Slot/CPU 热点，Redis Cluster 也无法拆分。固定 Lane 把高频操作局部化，允许 Redis Slot 迁移扩容；跨 Lane 只做低频 Credit 批量协调。代价是短 Epoch 内近似公平，因此用跨 Epoch 轮转和无饥饿测试约束误差。

#### Q：Balancer Lease 过期或 Redis 丢失会怎样？

所有 Lane 操作同时校验 Fencing 和 Redis 服务端到期时间，旧 Balancer 不能继续重建或发 Credit。Redis 丢失后 Meta 不存在，Reserve 返回 Paused；只有完整 PostgreSQL 重建并最后 Activate 后才能恢复准入。系统选择 Fail Closed，牺牲短期可用性换取不会无限派发。

### 一分钟讲法

M6 以 Project 为唯一公平单元，用 Progressive Filling 做等权 Max-Min，并把 Project 内顺序固定为 Priority、Ready Time、Node Run ID。Redis 使用固定 Lane 和同槽 Lua 原子扣 Credit、取候选、建 Attempt Reservation；Balancer Lease/Fencing 只负责每 Epoch 的批量额度，所有 Scheduler 都能消费共享 Credit。真正 Dispatch 仍由 PostgreSQL CAS 原子写 Node Queued、Attempt 和 Task Outbox。Redis 丢失时默认暂停，从数据库 Ready/Queued/Running 重建后再开放，所以 Redis 提供高频协调性能但不拥有正确性。

### 易错点与追问

- M6 已写 Task Outbox，但尚未把 Task 发布到 Kafka；真实 Publisher/Worker 是 M7；
- Fixed Capacity Provider 当前读取配置槽位，是 M6 的生产接线起点；动态 Worker 健康槽采集属于 M7；
- Resource Class 只约束 Pool 可行性，不参与公平份额；
- Confirmed Reservation 仍是 Redis 派生状态，数据库 Inflight 才决定是否续期；
- Credit Batch 是发放摊销粒度，不是每 Lane 的吞吐上限；
- Redis Cluster 扩容迁移 Slot，不改变 Lane Count；改变 Lane Count 必须版本化迁移。

## 12. M7：Kafka、Worker Runtime、Attempt API 与 Execution Context

- 验收状态：已通过版本化消息 Contract、真实 Kafka/PostgreSQL/Scheduling Redis、Cache Redis 整体不可用、双 Control Plane API、双 Worker/Engine Consumer 副本、Slot 背压、Poison/DLQ、Lease Lost/Recovery、旧 Fencing Result 拒绝与 Worker 无数据库依赖验收。
- 学习价值判断：写入。
- 判断理由：M7 把前六个阶段的定义、状态机、事务和公平准入连成第一个真实分布式执行闭环，集中体现 Kafka 至少一次语义、Worker 无状态化、Cache-Aside、Lease/Fencing 和故障恢复。

### M7 解决了什么问题

M6 只把 Ready Node 原子变成 Queued Attempt 和 Task Outbox。M7 负责可靠发布 Task、让独立 Worker Claim 并执行、保存 Completion，再用 Runtime Event 唤醒任意 Engine 实例接受 Effective Output。这里的目标是验证协议与边界，不是提前实现 HTTP、RPC 或 Python 的真实业务逻辑。

完整路径为：

```text
Scheduler PostgreSQL Transaction
→ node_task_outbox
→ Task Relay
→ Kafka Resource-Class Topic
→ Worker Poll
→ Attempt API Claim + Lease/Fencing
→ ACK Kafka
→ Execution Context Gateway
→ Executor
→ CompleteAttempt + runtime_outbox
→ Kafka Runtime Event
→ Engine Inbox/CAS
→ Effective Output
```

### 为什么是 Claim 后 ACK，而不是执行成功后 ACK

ACK 前，Kafka 负责让未被可靠接管的 Task 重投；Claim 成功后，PostgreSQL 已记录 Running Attempt、Lease Owner 和 Fencing Token，执行责任从 Kafka 转移到 Attempt 状态机。因此 ACK 不等待长时间执行：Worker 崩溃后 Reaper 依据数据库时间把过期 Attempt 置为 Lost，Engine 决定 Recovery，而不是依赖 Kafka 分区被同一 Worker 长期占有。

如果执行完成后才 ACK，长任务会让 Kafka Consumer Group 的 Rebalance、Max Poll Interval 和重复投递与业务超时强耦合；如果 Claim 前 ACK，则 Worker 在 ACK 后、Claim 前崩溃会令 Queued Attempt 永久丢失。Claim 后 ACK是两个系统间明确的责任转移点。

### Kafka Rebalance 如何不破坏 Offset

Consumer 在 `Poll → Claim/Inbox → Commit Offset` 的短窗口阻止 Rebalance，避免分区已被撤销后旧消费者仍提交 Offset，导致新消费者进度回退或跨过未处理消息。ACK、NACK、DLQ 或进程 Close 都会释放 Gate；Executor 运行发生在 ACK 之后，不持有 Gate。Worker 内多个 Slot 共用一个 Consumer 时，这段领取路径串行化，避免后一个 Offset 先提交而跨过前一个尚未 Claim 的 Task。

Kafka 仍是至少一次：Publish 成功但 Outbox 未标记、Commit Offset 响应丢失、Consumer 崩溃都可能导致重复。Attempt Claim、Engine Inbox、Run CAS 和 Effective Attempt Pointer 负责把重复收敛为一次业务效果，而不是宣称跨 PostgreSQL/Kafka Exactly Once。

### 为什么 Task/Event Envelope 很小

Task 只携带 Attempt、Run、Node、Resource Class、Trace 等定位信息；Runtime Event 只携带 Aggregate/Event 身份。两者上限 64 KiB，并明确禁止 DSL、Execution Context、Output 和 Secret。这样可以：

- 让数据库仍是 Snapshot、Input、Output 和运行状态的唯一权威；
- 避免消息体随 Workflow/Data 放大，保护 Kafka Broker、Consumer Memory 和重放成本；
- 重投时重新读取当前权威状态，让迟到消息能被 Current Attempt/CAS 拒绝；
- 不让 Secret 进入保留期更长、读权限更广的日志和消息系统。

不能识别 Attempt 身份的 Poison Message 进入 DLQ；若身份完整但版本/字段不兼容，Worker 先 Claim 再将 Attempt 终结为 `TASK_MESSAGE_INVALID`，避免数据库永远停留在 Queued。

### Worker Runtime 与能力同构

Worker Runtime 只包含 Consumer、本地 Slot、Attempt/Context Client、Heartbeat、Timeout、Telemetry 和 Executor Catalog。它根据 DSL Operation Coordinate 在 Catalog 中查 Executor，没有随 Node Type 增长的中央 `switch`。Builtin 和 Sandbox 是安全/资源边界，不是“一个 Node Type 一个 Worker”。

同 Resource Class 的 Consumer Group 必须能力同构，因为 Kafka 可把该 Topic 任意 Partition 分配给任意组成员。M7 用三层检查：

1. Worker 启动时 Catalog 必须覆盖 Routing Policy 对该 Class 的完整能力集；
2. Worker Heartbeat 上报 Resource Class、Build、Slots、Capabilities，Scheduling Redis 只统计匹配当前能力指纹且未过期的 Slot；
3. PostgreSQL Claim 逐 Attempt 复核持久化 Operation、Resource Class 和 Worker Capability。

这使错误部署或滚动升级中的旧 Worker Fail Closed，不会先把不兼容 Attempt 置为 Running 再靠运行错误发现。

### Execution Context 为什么通过 Gateway

Worker 没有 Workflow PostgreSQL 凭证，只凭有效 Lease/Fencing 调用 Worker API。Gateway 先校验 Attempt 仍为当前 Running Lease，再装配不可变 Snapshot 中的 Operation/Policy/Output Contract、Run Input、Engine 已解析的 Input，以及只来自 `effective_attempt_id` 的上游 Output。Worker 不能绕过 Gateway 读取候选 Output，也不能修改 Run/Node Run。

入口控制节点是其中的特例：控制节点没有 Attempt，也没有 `node_output_values` 行。`start` 的唯一输出 `workflow_input` 本质就是 Run Input，因此 Task Node 的 `node_output` Binding 指向 Entry Node 的 `workflow_input` 时，Gateway 直接复用已经装载并校验的 Run Input，而不是按 `effective_attempt_id` 查输出表；其余上游引用仍只接受 Engine 已接受的有效输出。`TestM7ExecutionContextLoadsEntryNodeInput` 覆盖这一路径；修复前该场景会在 Claim 成功后返回 `ATTEMPT_NOT_FOUND`，Sandbox Task 还没启动代码 Lease 就过期，并在恢复中反复被标记为 `LEASE_LOST`。

Cache Redis 对 Snapshot、Run Input 和 Effective Output 使用 Cache-Aside：读命中且内容校验有效才返回，Miss、Timeout 或缓存坏值都回源 PostgreSQL，成功后 Best-Effort 回填。权威写入绝不 Write-Behind。Cache Client 对不可达节点快速失败，避免“非关键缓存的默认网络重试”把节点启动延迟放大；Redis 整体不可用时测试仍能成功执行，只增加数据库读取和延迟。

### PostgreSQL、Redis、Kafka 的角色

- PostgreSQL：Attempt 状态、Lease/Fencing、Snapshot/Input/Output、Outbox/Inbox 和 Effective Pointer 的权威；
- Scheduling Redis：保存可重建的 Ready/Load/Topic/Reservation/Inflight 协调状态；Worker Slot 注册和能力指纹只用于健康与 Claim 能力校验，不参与 Topic Queue Window 公式；
- Cache Redis：加速只读 Execution Context，失败即回源，不决定执行正确性；
- Kafka：Resource Class Task 和 Runtime Event 的异步至少一次传输；Offset 不等于 Attempt/Run 状态。

### 故障窗口如何收敛

- Publish 前 Relay 崩溃：Outbox Claim 过期后重试；
- Publish 后、MarkPublished 前崩溃：重复 Task/Event，由 Claim/Inbox 收敛；
- Claim 前 Worker 崩溃：未 ACK，Kafka 重投；
- Claim 成功、ACK 前崩溃：可能重投，同一 Running Lease/Attempt 幂等收敛；
- ACK 后或执行中崩溃：Lease 到期，Reaper 写 Lost Event，Engine 进入 Recovery；
- PostgreSQL 或 Context Gateway 暂时不可用：保持已 Claim Attempt 为 Running，交给 Lease Recovery；不能伪装成节点失败并消耗业务重试预算；
- Complete 成功、响应丢失：数据库事实和 Runtime Outbox 已提交，旧 Worker 重试 Completion 只得到相同结果；
- 旧 Worker 迟到：Lease/Fencing 和 Current Attempt 检查拒绝，不能产生第二个 Effective Output；
- Cache Redis 故障：Gateway 回源 PostgreSQL，正确性不变；
- Kafka Rebalance：只影响谁消费，Run/Attempt 权威状态不迁移。

### 水平扩展与容量边界

Control Plane 可多副本：Task/Runtime Relay 用 `SKIP LOCKED` 分担 Outbox，Engine Consumer 用 Kafka Group + Inbox/CAS，Attempt API 无本地权威状态，Reaper 通过数据库条件更新收敛竞争。Worker 按 Resource Class 独立增加副本和 Slot；Topic Partition 决定同时活跃的 Consumer 上限，Worker 实际完成速率决定 Scheduler 维持的约五秒 Topic Queue Window，Slot 只约束 Worker 本地 Running 并发。

M7 没有给出“每分钟固定 Task 数”承诺。吞吐近似受 `min(Worker Slots / 平均执行时间, Kafka Partition 消费能力, Attempt/Engine PostgreSQL 事务能力)` 约束；production-default 的 Partition、Slot、Batch 和 Timeout 只是压测起点，不是 SLO。M11 会用容量和故障注入校准这些参数。

### 高频面试题

#### Q：Kafka ACK 以后 Worker 崩了，任务不是丢了吗？

Kafka 消息层面已完成责任转移，但业务任务没有丢：PostgreSQL 中 Running Attempt 的 Lease 会过期，Reaper 原子标记 Lost 并写 Runtime Outbox，Engine 根据独立 Recovery Budget 重新把 Node 置为 Retry Wait/Ready，Scheduler 创建新 Attempt。旧 Attempt 的迟到结果被 Fencing 拒绝。

#### Q：为什么 Worker 不直接读 PostgreSQL，少一次 HTTP 不是更快吗？

Worker 执行用户可影响的任务，是更高风险和更易扩缩容的边界。给它数据库权限会让任意 Executor 漏洞绕过 Run 状态机、Project 隔离和 Effective Output 规则。Gateway 统一校验 Lease、裁剪资源、缓存热点数据；HTTP 可在以后替换为 gRPC，但权限和状态所有权不能换。

#### Q：为什么不用 Kafka Message 直接带所有输入？

那会复制权威状态、扩大消息、泄露 Secret，并让消息创建时的旧上下文与执行时 Current Attempt 脱节。轻量 Wake-up + Lease-scoped Gateway 让重复/迟到消息重新面对数据库真相，代价是一到数次只读访问，使用 Cache-Aside 缓解。

#### Q：Cache-Aside 为什么不会产生错误旧值？

Snapshot 不可变，按 Snapshot ID 缓存天然无需失效；Run Input 在 Run 生命周期内不可变；Effective Output 只有 Engine 接受后才缓存，按 Run + Node 键读取。缓存 JSON 损坏或 Snapshot Operation 与持久化 Coordinate 不一致时按 Miss 处理并回源；若 PostgreSQL 权威值自身非法则立即报错。若未来允许修改这些值，必须先改变领域不变量和失效协议，不能直接沿用当前键。

#### Q：引用 `start.workflow_input` 时，Gateway 为什么不查 `node_output_values`？

控制节点（start/branch/end）不创建 Attempt，因此没有 Output Candidate 行。`start` 的唯一输出就是 Run Input，`branch`/`end` 没有输出；只有 Task Node 的上游输出才按 `effective_attempt_id` 查询。若 Entry Node 引用也走输出表，任何以 start 输入开头的 Workflow 都会在 Claim 后 Context 装配失败，表现为 Lease 过期后的 `LEASE_LOST`，而不是节点失败——基础设施故障不能伪装成业务失败并消耗业务重试预算。

### 一分钟讲法

M7 用 Kafka 接通了 Scheduler 到 Worker 和 Engine：Task 是 64 KiB 内的轻量 Wake-up，Worker 有空闲 Slot 才 Poll，先通过 Attempt API 在 PostgreSQL Claim 获得 Lease/Fencing，再 ACK Kafka并通过 Gateway 读取 Context。ACK 后崩溃不靠 Kafka恢复，而由 Reaper 把过期 Lease 变成 Lost，Engine 创建 Recovery；旧结果被 Fencing 拒绝。Snapshot、Run Input、Effective Output 用 Cache-Aside，Redis 故障回源 PostgreSQL。Worker 无数据库凭证，同一个 Resource Class 的副本必须能力同构。真实双 Control Plane、双 Worker/Engine 副本和 Cache 故障测试证明了分布式边界。

### 五分钟展开提示

1. 画 Outbox → Kafka → Claim → ACK 的责任转移；
2. 枚举 Claim 前、ACK 后、执行中、Complete 前后的崩溃窗口；
3. 解释 Rebalance Gate 为什么只覆盖短数据库事务；
4. 展开 Lease、Fencing、Current Attempt、Inbox/CAS 四层幂等；
5. 对比 Scheduling Redis Worker Slot 与 Cache Redis Context 的不同职责；
6. 说明完整 Capability Set、能力指纹与滚动发布；
7. 最后说明多副本扩展、Partition/Slot 上限和 M8/M9 范围边界。

### 易错点与追问

- ACK 表示 PostgreSQL 已接管 Attempt，不表示节点执行成功；
- Kafka Key 保序只在同 Topic Partition 内成立，最终正确性仍靠数据库状态机；
- Worker Slot 是实际并发，`task_poll_limit` 还会受 Kafka Poll 上限和 Rebalance/Claim 时间安全余量约束，不是无限本地队列许可；
- Cache Redis 不可用不能阻止 Context 读取，Scheduling Redis 不可用则必须暂停新准入；
- Worker Capability Heartbeat 是调度容量派生事实，Claim 校验才是数据库最终防线；
- M7 的 Echo Executor 仅验证协议，不能声称 HTTP/RPC/Python Sandbox 已实现；
- DLQ 不能代替 Attempt 终态：可识别坏 Task 必须先让数据库中的 Attempt 可收敛；
- 多副本测试证明协议可并行和故障接管，不等于已完成 M11 的吞吐/SLO 压测。

## M8：HTTP/RPC 与 Managed Resource Runtime

M8 的关键不是把网络请求塞进 Worker，而是保留资源边界：IR/DSL 只保存 `connection_ref` 或编译后的稳定资源 ID；Worker 通过 Control Plane 的运行时 Port，以 `project_id + run_id + attempt lease/fencing` 再次校验 execution identity、grant 和 resource revision。Worker 不连接 PostgreSQL/Redis，资源撤权可以在运行时生效，且每次 Attempt 都能审计实际使用的 Resource Revision。

HTTP Executor 只解析受管 Connection 的相对路径。拒绝绝对 URL、Host 覆盖、路径逃逸、重定向和超限响应；认证 Header 由 Secret Resolver 在最后一跳注入。外部副作用使用稳定 `run_id:execution_node_id` 作为 Idempotency-Key，避免 Worker Lost 后恢复重试产生重复业务写入。

RPC Executor 只解析 Service Catalog 登记的 `service_id + operation + contract_revision`，服务发现和协议（第一阶段 `http-json`）属于 Executor Port，不进入 IR/DSL。非登记服务、操作或契约 revision 不兼容都在调用前失败。

高频面试题：为什么不让 Worker 直接读数据库？因为那会绕过 Attempt Lease、Project 隔离、Execution Identity 和 Effective Output 规则；为什么 Secret 不进 Context？因为 Context 会被缓存、传输和诊断，短暂凭据应只存在于 Executor 调用栈；为什么资源 revision 要审计？因为受管资源可变，而不可变 Workflow Snapshot 不能假设运行时资源永远不变，审计才能重现“当时实际调用了哪一版资源”。

M8 已通过 HTTP httptest 安全负例、RPC Contract Revision/幂等键、Worker API 资源端口和全仓 `go test ./...`。M9 在此基础上完成 Python Sandbox，两个 Resource Class 均已有真实 Executor；这不等于已完成 M11 的容量、安全 Escape 与漏洞扫描发布门禁。

## M9：Python Per-Attempt Sandbox

M9 的关键不是“在 Worker 中运行 Python”，而是把用户代码与 Worker 主进程、控制面凭据及宿主机隔开。CodeExecutor 只打包 `source_code + resolved JSON inputs`，调用 Sandbox Orchestrator；OCI Adapter 才创建并回收容器。Worker 保持无数据库/Redis 依赖，也不加载、编译或执行用户 Python。

固定 `python-sandbox-v1` 不允许 IR、CLI 或 Agent 覆盖：`0.50 CPU / 128 MiB Memory / 32 PIDs / 16 MiB tmpfs / 1 MiB output`，以及 `network none`、只读 rootfs、无 Host Mount、Capability Drop、`no-new-privileges` 与非 root UID。Python Runner 只允许小型标准库白名单，要求唯一 `main(inputs)`，并必须返回与 DSL Output Contract 完全一致的 JSON Object。Go 发布预检做语法、入口与显式 Import 校验；真正的安全边界是 OCI 运行时配置，而不是静态扫描。

错误链路也在 M9 闭合：Executor 返回 `dsl_field=operation.config.source_code` 与可安全公开的行列号，Attempt Coordinator 持久化后由 Engine/Source Map 定位 IR 的 `inputs.source_code`。源码、输入、stderr 和 Worker 凭据不进入错误对象、Kafka 或遥测。普通 Docker `runc` 只用于本地/CI 验证；生产 profile 强制 `runsc + digest-pinned image`，并禁止把 Docker root socket 直接交给普通业务 Worker。

### M12 Release Candidate：容量、安全与发布门禁

M12 的学习价值判断是“写入”，但当前事实是 **Release Candidate 进行中**，不是
`Production Ready`。它补齐的是把设计边界落实到发布前证据的机制：Control Plane
记录 PostgreSQL Pool acquire 直方图；Execution Context 按 `snapshot`、`run_input`
和 `effective_output` 记录低基数 Cache hit/miss；因此 `Ready→Queued P95`、连接池
等待 P95、热缓存命中、Outbox age 和 Kafka lag 可以在一个可重复负载实验中共同
验证。指标不能携带 Project、Run、Attempt 或 Trace ID，否则监控本身会成为高基数
故障源。

Sandbox 的部署边界也被收紧为“Worker 请求、Controller 执行”：Sandbox Worker
只有私有 HTTP Controller Client、Kafka 与 Worker API 路径，既没有 Docker CLI
也没有 Docker socket；独立 Sandbox Runtime Controller 才拥有 OCI 凭据。local/CI
可用 `runc` 做协议验证，生产 profile 则要求 `runsc` 与 digest-pinned image。Worker
到 Controller 的应用层认证是 Secret-Manager 注入的服务令牌；HTTPS 不自动等于
mTLS，若平台需要客户端证书，必须由 Network boundary 或 sidecar 显式配置。

**为什么 PostgreSQL Pool Wait 需要单列而不是只看 API P95？** API 变慢时，原因
可能是调度、Kafka、数据库或远端节点；Acquire P95 直接回答“连接池是否被耗尽”。
它是容量扩展时调整 Control Plane 副本数与每实例 `pool_max` 的约束，并受数据库
`max_connections` 70% 安全预算限制。

**为什么不能把 M12 本地通过称为 Production Ready？** 真正的容量数值取决于
CPU、磁盘、网络、Kafka partition、Control Plane/Worker replicas、Pool slots 与
负载分布。必须归档目标环境中的 60 分钟稳态、15 分钟 burst、15 分钟恢复原始指标，
并完成最终 digest 的镜像扫描、`runsc` Escape/1000 次压力、备份恢复、Kafka replay
和 Redis rebuild 演练。没有这些证据，正确状态只能是 Release Candidate。

2026-08-14 的 local 实测把这条边界变得很具体：12 vCPU / 约 3.7 GiB Docker
内存的 Docker Desktop 环境以 `runc` 顺序完成了 1,000 个 Sandbox
create/run/destroy，耗时 13 分 42.941 秒且无最终容器残留；真实 PostgreSQL
备份在隔离容器恢复时校验和一致，Redis/Kafka 重启后的恢复用例也通过。这些是
协议、清理和恢复的有效证据，不是 production `tasks/min`，更不是 `runsc`
Escape 结论。第一次使用 Go 默认 10 分钟测试上限时，执行到约 700 次后被硬终止并
留下一个已退出容器；这说明正常路径的 deferred cleanup 不能覆盖进程被强杀，
也说明 Controller 启动 `Sweep` 和生产环境的孤儿清理流程不可省略。正式 1,000 次
演练必须给足外层测试期限（本机使用 25 分钟），而不是把超时后减少次数写成通过。

2026-08-15 又发现了一个很典型的部署边界问题：Web 镜像虽然能成功构建，Nginx
却因 Compose 服务名 `control-plane` 与部署级上游名
`evalfrog-control-plane` 不一致而在启动阶段失败。正确修复不是把 Web 改为直接
访问数据库或把上游地址硬编码成宿主机端口，而是在 Edge 网络为 Control Plane
发布这个逻辑 DNS alias，并用架构测试守住该约束。这个例子说明“构建成功”不等于
“部署可用”，网络命名与服务发现也是发布契约的一部分。

Sandbox 的 Python import allowlist 也不能被误说成安全边界。解释器对象图可让
恶意源代码绕过这类语言级限制并取得标准导入能力；因此 M12 的 Containment Probe
刻意按该更强假设执行，再由 OCI 配置验证 `--network none`、无 Docker socket、
只读根目录和 Controller Token 不注入 per-attempt 容器。`runsc` 是生产隔离的
关键一层，Python parser/runner 只负责作者体验和纵深防御。这是面试中“输入校验、
应用沙箱与内核级隔离各自负责什么”的典型追问。

该 Probe 已在 GitHub Ubuntu Runner 的 `runsc release-20260810.0` 下通过；同一
环境的 1,000 次 Sandbox create/run/destroy 压力耗时 `10m25.027s`，没有受管容器
残留。它证明 CI 能以 hardened runtime 重复执行隔离契约和清理链路，仍不构成目标
环境的容量数字或最终镜像安全扫描结论。

相关实现和验证位置：`internal/platform/metrics/`、`internal/adapters/postgres/client.go`、
`internal/runtime/context/gateway.go`、`internal/adapters/sandbox/`、
`internal/architecture/compose_test.go`、`tests/integration/m12_*` 与
`docs/operations/发布与容量验收手册.md`。

高频面试题：为什么静态 Import 黑名单不能代替 Sandbox？用户代码可通过动态导入、解释器漏洞或语言特性绕过静态规则；即使代码审计失效，`network none`、只读文件系统、PID/Memory/CPU cgroup、Linux capabilities 与 hardened runtime 仍限制可造成的影响。为什么不把容器任务深度预派给 Kafka？Kafka 只负责唤醒 Attempt；真正的并发由 Scheduler credit、Worker slot 和每个 Attempt 一个容器共同限制，避免积压任务在未来无控制地创建沙箱。

## M10：External API、CLI、Human Web 与 Run Read Model

- 验收状态：已完成本地 Unit、OpenAPI Contract、CLI 完整命令链路、真实 PostgreSQL Integration、Web 静态构建与 CI 验证；远端 PR CI/合并状态以本阶段交付记录为准。
- 学习价值判断：写入。
- 判断理由：M10 把“架构正确”转化为 Human/Agent 可以实际使用的产品闭环，同时说明如何不因增加 UI/CLI 而破坏 IR/DSL、运行时状态所有权和 Redis 的非权威边界。

### 解决的问题

此前系统已经能编译、调度与执行，但产品入口缺少完整闭环。M10 让两个不同使用者通过同一版本化 API 完成创建、拉取、乐观并发保存、校验、草稿测试、发布、正式运行、查状态和取消；Web 画布和 CLI 都不拥有第二套 Workflow 业务逻辑。

### 核心边界与不变量

- `workflowapp` 是 HTTP、CLI 与 Web 共同调用的应用命令边界；HTTP Handler 不直接读写 Repository。
- Authoring Client 只能提交 Canonical JSON IR。DSL、Source Map 和 Execution Snapshot 由服务器生成、保存和执行，既不能上传，也不作为产品 API 的依赖返回值。
- `EF_SERVER`、`EF_PROJECT`、`EF_TOKEN` 是 CLI 的默认连接上下文；显式 Flag 只作单次覆盖。这样本地 Agent 不需要在每条命令重复或回显 Token，仍可安全地切换目标 Project。
- Draft Test 与 Production Create 的 Command Response 只返回最小 Run DTO；当前状态必须由 `GET Run` 的投影读取，避免数据库 Record 成为一经发布就无法修改的公共协议。
- Run Read Model 从 PostgreSQL Runtime State 和该 Run 固定 Snapshot 的 Source Map 生成。运行错误定位为 `logical_node_id/logical_edge_id/ir_field/details`，字段不存在时退化为 Node 高亮。

### CLI 严格解码与完整传输 DTO

CLI 对 External API 响应使用 `DisallowUnknownFields`，它能尽早暴露服务端契约漂移，但命令内部只声明“准备打印的几个字段”会产生反效果：服务端已原子创建 Draft，客户端却因 `draft_revision_id` 之类的正常字段未在局部 struct 中声明而误报失败。正确做法是在 CLI 边界为版本化 API 定义完整的传输 DTO，再由命令只读取其所需字段；测试必须返回真实完整响应形状。这样既保留严格契约检查，也避免幂等重试场景把“成功写入”错误呈现为失败。

### Agent Skill 为什么采用渐进式分层

CLI 完成不等于本地 Agent 就能稳定使用 CLI。`skills/evalfrog-workflow/` 将 Agent
操作知识打包为可安装 Skill：`SKILL.md` 只放触发条件、执行顺序、确认边界和参考
路由；`references/` 按启动发现、IR 创作、Definition 生命周期和 Run 操作拆分。这样
未来增加节点或新的运行能力时，只加载与当前任务有关的说明，不会把所有指南塞入
一个持续膨胀的提示词。

这只是 Agent 的本地操作层，不改变 External API 或 Definition/Runtime 所有权。
它仍强制只上传 IR、写操作先确认、Revision Conflict 先 Pull 再合并；安装脚本只把
Skill 放入本地 Codex 发现目录，Token、Project 和平台授权仍由用户/部署方提供。

为避免 Agent 每次修改都重写整份 JSON，CLI 的 `workflow builder` 进一步将一份
完整 IR 拆成可审计的本地小步操作：Session 中增删 Node/Edge、设置 Literal、绑定
上游 Output、声明 Output 和调整 Layout，最后仍把完整 IR 与 `expected_revision`
提交给既有 Draft API。小步编辑是本地体验层，不能演变成服务端的局部 Patch API，
否则会绕过 Canonical Hash、完整图校验和不可变 Revision 语义。
- Cancel 只持久化请求并写 `RunCancelRequested` Outbox；Engine 是唯一可以改变 Run/Node 语义状态的组件。即使 Cancel 先于 `RunCreated` 消费，Engine 也能把 Pending Run 收敛为 Canceled。

### Redis、PostgreSQL、Kafka 的角色

PostgreSQL 仍保存 Run、Node、Cancel 请求、Outbox 和 Source Map 引用，是 Run Read Model 的唯一可重建来源。Cache Redis 只以 Cache-Aside 方式保存短生命周期投影；每次 Run 或 Node 提交后 Best-Effort 删除缓存。Redis Pub/Sub 只发 SSE wake-up，消息没有状态内容，丢失后浏览器重新 GET 即恢复。Kafka 保持原有 RunCancelRequested/Runtime Event 的可靠异步传递，不用 Redis 通知代替持久事件。

### 为什么不用 EventSource 直接带 Token

浏览器原生 `EventSource` 不能安全地附带 Bearer Authorization Header。M10 采用 `fetch` 流式读取 SSE：仍然是标准 `text/event-stream`，但能携带 Authorization；收到 `update` 只触发重新读取 Run Read Model。这样也恰好强制客户端不把瞬时消息当权威状态。

### 高频面试题

**问：为什么 Publish/Run API 不直接把 DSL 返回给 Agent，Agent 不是也需要理解工作流吗？**

答：Agent 的 authoring source of truth 是 IR，Copy 读取已保存的 IR Snapshot，不需要从 DSL 反编译。DSL 暴露会让 Agent 开始依赖 Compiler 的内部 Operation Version、资源绑定和嵌套结构，未来 Compiler 演进会变成外部兼容性负担。错误定位由 Source Map 增强后的 Read Model 提供，既满足修改指导，也不泄露执行内部表示。

**问：Redis Pub/Sub 丢了进度消息，Web 会不会展示错误状态？**

答：不会影响最终正确性，因为消息不带状态。Web 首次打开、收到 update、以及流断开重连后都 GET PostgreSQL 派生的 Run Read Model。丢消息最多让一次刷新延后；缓存失效或 Redis 不可用时同样回源 PostgreSQL。若需要严格可回放的事件历史，应以后增加持久 Event API/Kafka 消费投影，而不是把 Pub/Sub 假装成可靠队列。

### 一分钟讲法

M10 用一个 `workflowapp` 应用层把 Human Web 与 Agent CLI 接到同一套 IR→Compiler→不可变 Snapshot→Run 的链路。CLI 有带 Revision 的本地 Workspace，Web 画布可编辑 IR/Layout；两端都只能走 OpenAPI。运行进度由 PostgreSQL 派生 Run Read Model，Cache Redis 只加速读取，Pub/Sub/SSE 只是“请重新 GET”的可丢失信号。Cancel 经 Outbox 交给 Engine 收敛，所以产品入口没有绕过状态机。错误通过 Snapshot Source Map 直接回到 IR 节点、边和字段。

### 易错点与追问

- 本地 CLI IR 解析只做快速失败，不能替代服务器绑定 Catalog 的严格 Validate；
- 缓存删除/发布失败不能回滚 Run/Node PostgreSQL 事务；
- 不要把 DSL 或 Source Map 重新开放为“只读方便接口”，否则客户端会形成内部实现依赖；
- `cancel_requested_at` 不等同于 `RunCanceled`，后者只有 Engine 收敛后才能成立；
- Web 原生 EventSource 无法携带 Bearer Token；使用 `fetch` SSE 后仍要处理断线回读。

## M11：Retry、Recovery、可观测性与故障恢复

- 验收状态：已完成本地 Unit、Contract、Repeatability、Race、真实 PostgreSQL/Kafka/Redis Integration 与故障恢复场景验收；远程 PR CI/合并结果以交付记录为准。
- 学习价值判断：写入。
- 判断理由：M11 把“可执行”提升到“可恢复、可诊断”。它集中解释了定时恢复为何不能成为第二状态机、为什么 Kafka 时间戳不能裁决 Deadline，以及 PostgreSQL、Redis、Kafka 和可观测性如何在故障时各司其职。

### 核心边界与最终方案

Recovery 的输出不是状态迁移，而是一条 durable Runtime wake-up。Retry Timer、Deadline Scanner、Attempt Reaper、Reconciler 允许多副本并发扫描；它们在 PostgreSQL 事务内重查当前条件、写 Outbox/Audit，并使用 `runtime_recovery_wakeups` 进行冷却去重。Engine 收到消息后仍以 Inbox、行锁、CAS、Current Attempt 和领域状态机收敛。因此 Reconciler 不会把“数据库中有一个 Lost Attempt”直接改写为 RetryWait，也不会拥有一套偷偷分叉的业务语义。

`attempt_seq` 表示每一次物理执行，`retry_count` 只消耗业务失败重试预算，`recovery_count` 只消耗 Lease/Worker 基础设施恢复预算。Deadline 是新的恢复准入上限：Retry Scanner、Scheduler、Worker Claim/Heartbeat 与 Engine 均重新检查数据库事实。延迟 `RunCreated` 在 Deadline 后只能使没有 Node Run 的 Pending Run 收敛为 `timed_out`；取消请求在 Deadline 之前已经持久化时优先，否则 Deadline 优先。不能用 Kafka 的 `occurred_at` 判断“现在是否过期”，因为消息可能晚到或乱序。

### PostgreSQL、Redis、Kafka 的分工

- PostgreSQL：保存 Run 根 `trace_id`、终止意图、Lease、Attempt、Recovery Wakeup 去重、Audit 和两种 Outbox，是恢复与诊断的唯一权威事实；
- Redis：Scheduling Redis 重建失败时仍 Fail Closed；Cache Redis 丢失时只回源 PostgreSQL。TTL 不是 Retry/Deadline/Lost 的计时器；
- Kafka：传递 Runtime/Task wake-up 并提供按 group/topic 的 Lag 观测，但 Offset 和消息时间都不等于 Workflow 状态。

Kafka adapter 对短暂网络断连与 Kafka 明确标注可重试的 group-coordination 错误（例如 `COORDINATOR_NOT_AVAILABLE`、`NOT_COORDINATOR`）在同一 consumer 生命周期内退避并重新 Poll/join group。`REBALANCE_IN_PROGRESS`、非法 generation、未知 member 在 Kafka request 层表示“需要 rejoin”，也被归入这一恢复路径；这样 Broker 重启或 Rebalance 不会让 Engine/Worker 进程退出。Inbox、Claim、Fencing 使随后重复投递可安全收敛。认证、协议、Topic 配置和 static member fencing 等不可重试错误不应被吞掉，因为它们需要部署者修复。

Outbox Age 同时统计 Runtime Outbox 与 Node Task Outbox；否则 Scheduler 已经原子创建的 Task 若积压在第二条 Outbox 边界，会完全逃过告警。Metrics 只用有界标签；`trace_id/project_id/run_id/attempt_id` 只进入结构化日志和 Audit，避免 Prometheus 高基数失控。

### 诊断、DLQ 与人工 Replay

`GET /diagnostics` 和 `evalfrog run diagnose` 只显示安全的 Run 摘要、Attempt 元数据和 Audit，不显示输入、输出、Secret、Lease Token 或 executor stderr。普通 Run View 可以缓存；诊断包含实时 Lease 与追加 Audit，不进入该缓存。

人工 Replay 不是“向 Kafka 塞一段 JSON”。Project Admin 只能提交受枚举约束的 Runtime event type 和 Run/Attempt aggregate ID；服务端必须验证该事实仍 actionable，再原子写 Outbox 与 Audit。DLQ 用来定位有毒消息或协议问题，正确处置是先检查诊断和权威状态，再使用受限 Replay 或等待自动恢复；不能以 DLQ 为由绕过 Engine 直接修改状态。

### 高频面试题

**问：为什么 Reconciler 只补发事件、不直接修复状态？**

答：直接修复会复制 Engine 的状态机，并在业务规则演进时产生两套语义。Reconciler 只发现“该唤醒可能丢了”，Engine 重新读取 PostgreSQL 并按 Inbox/CAS/领域模型推进；多副本、消息重复和扫描重叠因此都会收敛。

**问：为什么要用 PostgreSQL 当前时间而不是 Kafka Event 时间？**

答：Kafka 至少一次且可以延迟/乱序，Event 时间只说明事件首次记录时刻，不能说明消费时是否已超过 Deadline。用数据库当前时间可让 Scanner、Engine、Scheduler、Claim 和 Heartbeat 对同一权威事实作出一致裁决。

**一分钟讲法：**

M11 让恢复不再依赖某一个常驻进程。所有定时器和 Reconciler 都只把 PostgreSQL 当前事实变成可重复的 Outbox wake-up；Engine 是唯一状态机。Run Trace 从 API 经 Outbox、Kafka、Worker、Completion 回到 Engine，诊断和 Audit 保留安全元数据。Redis 失效分别按 Fail Closed 或 Cache-Aside 处理，Kafka Lag 和 Outbox Age 只观测传输健康、不裁决工作流状态。这样 Worker Crash、消息晚到、Redis 丢失和 Control Plane 重启都不会留下永久卡住的 Run。

## M8 面试复习：Managed Resource Runtime

M8 的关键不是把网络请求塞进 Worker，而是保留资源边界：IR/DSL 只保存 `connection_ref` 或编译后的稳定资源 ID；Worker 通过 Control Plane 的运行时 Port，以 `project_id + run_id + attempt lease/fencing` 再次校验 execution identity、grant 和资源 revision。这样 Worker 没有数据库凭据，资源撤权可以在运行时生效，且每次 Attempt 都能审计实际使用的 Resource Revision。

HTTP Executor 只解析受管 Connection 的相对路径。拒绝绝对 URL、Host 覆盖、路径逃逸、重定向和超限响应；认证 Header 由 Secret Resolver 在最后一跳注入。外部副作用使用稳定 `run_id:execution_node_id` 作为 Idempotency-Key，避免 Worker Lost 后恢复重试产生重复业务写入。

RPC Executor 只解析 Service Catalog 登记的 `service_id + operation + contract_revision`，服务发现和协议（第一阶段 `http-json`）属于 Executor Port，不进入 IR/DSL。非登记服务、操作或契约 revision 不兼容都在调用前失败。

高频面试题：为什么不让 Worker 直接读数据库？因为那会绕过 Attempt Lease、Project 隔离、Execution Identity 和 Effective Output 规则；为什么 Secret 不进 Context？因为 Context 会被缓存、传输和诊断，短暂凭据应只存在于 Executor 调用栈；为什么资源 revision 要审计？因为受管资源可变，而不可变 Workflow Snapshot 不能假设运行时资源永远不变，审计才能重现“当时实际调用了哪一版资源”。
